# Проверка прайсов на 1 000 001 запись

Дата: 20 сентября 2026. Реальные PostgreSQL 16 и production `ScheduledJobWorker`, синтетические локальные источники XML/YAML/XLSX. Стенд Docker Linux/aarch64, 10 CPU, 7,75 ГиБ памяти Docker VM. Worker: Python 3.13, `--memory=1g --memory-swap=1g`; PostgreSQL — отдельный контейнер. Batch 1000, очередь 1, кеш строк XLSX 8 МиБ; lease 30 секунд, heartbeat 5 секунд, deadline 3600 секунд. Параллельно проходили проектные проверки; это функциональная нагрузочная проверка без SLA.

## Основной прогон

Четыре прайса одновременно: XML, YAML, XLSX, XML; в каждом 1 000 001 запись. XLSX содержит более миллиона уникальных shared strings. Все scheduled jobs завершились `done`; каждый прайс получил ровно 1 000 001 предложение и начальное состояние.

| Сценарий | Разбор + staging, с | Публикация, с | Импорт, с | SQLAlchemy statements |
|---|---:|---:|---:|---:|
| Первая загрузка 1, XML | 221.348 | 306.100 | 530.242 | 12540 |
| Первая загрузка 2, YAML | 216.431 | 307.365 | 524.085 | 12044 |
| Первая загрузка 3, XLSX | 346.846 | 273.394 | 620.263 | 12044 |
| Первая загрузка 4, XML | 218.765 | 307.848 | 527.382 | 12044 |
| Повтор без изменений | 58.044 | 86.001 | 144.166 | 10078 |
| Изменение 1% | 60.859 | 92.002 | 152.937 | 11081 |
| Массовое отсутствие | 0.006 | 151.069 | 151.078 | 3079 |

Полный сценарий с генерацией файлов, повторами и очисткой занял **1094.109 с**. Длительность импорта в таблице не включает последующую пакетную очистку staging. SQL-счётчик включает служебные операции worker/heartbeat; native COPY RPC не попадают в SQLAlchemy events. Число запросов пропорционально пакетам, а не отдельным предложениям.

Результаты:

- Неизменённый повтор: 1 000 001 `unchanged`, 0 новых состояний.
- Изменение цен: ровно 10 001 новое состояние, 990 000 `unchanged`.
- Сокращение источника до 10 строк: 999 991 `missing`, итоговая история — 2 009 993 состояния.
- Пиковый RSS процесса: **148.53 МиБ**.
- Пик памяти cgroup, включая файловый кеш: **551.40 МиБ** при лимите **1024 МиБ**.
- Пик временных файлов стенда: **351.12 МиБ**.
- WAL за окно основного прогона: **23,759,233,696 байт (22.13 ГиБ)**. Это кластерный LSN delta; в том же тестовом кластере выполнялись небольшие регрессионные проверки. Значение не является оценкой WAL одного импорта.

Сравнение с четырьмя прайсами по 10 001 строке: RSS **124.16 МиБ**, cgroup **133.66 МиБ**. Увеличение источника в 100 раз не увеличило RAM пропорционально; добавились прежде всего файловый кеш и ограниченный XLSX LRU.

Скачивание сети заменено local-source портом с вычислением checksum. Четвёртый прайс читает тот же XML fixture, что первый; временный диск и page cache стенда учитывают три физических исходных файла. В production каждая загрузка имеет собственный файл и бюджет `MAX_TEMP_BYTES`. Скорость сети и реальных поставщиков данным прогоном не измерялась.

## Окончательный обход отсутствующих товаров

После основного прогона обход дополнительно ограничен диапазоном кандидатов **до** `NOT EXISTS`. Это исключает зависимость стоимости каждого пакета от выбора плана сортировки полного прайса. Окончательный вариант прошёл весь сценарий на 10 001 строке и отдельный реальный прогон на 1 000 001 записи (`--missing-only`) под тем же лимитом 1 ГиБ.

В отдельном прогоне первая загрузка заняла **299.063 с**, массовое отсутствие — **150.484 с**. Обработаны ровно **999 991** отсутствующее предложение; история содержит **1 999 992**.

RSS отдельного прогона — **115.03 МиБ**, cgroup peak — **264.96 МиБ**. Оба scheduled job завершились `done`.

## PostgreSQL и проверки

Сохранены `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`:

- Поиск 1000 текущих предложений через уникальный индекс/LATERAL: 42,603 мс.
- Выбор 1000 ID кандидатов через индекс пакетного обхода: 0,628 мс.
- Ограниченный missing lookup для этих ID: 1,648 мс.
- Страница истории одного предложения: 0,953 мс.
- Общая первая страница предложений после основного прогона: 549.667 мс.

Это единичные измерения на прогретом/частично прогретом стенде, не перцентили и не гарантия времени ответа. После прогонов проверены миграции нового tenant и обновление с `0005`, сохранение quarantine, отсутствие Alembic drift, атомарная видимость, rollback, pause/lease fencing, повтор после commit, cursor и HTTP.

Обязательный проектный `check` включает backend/PostgreSQL, 98 Helm-тестов, frontend lint, typecheck и production build. Три необязательных теста требуют отдельно предоставленных real-Core/партнёрских fixtures или специального Redis окружения; они пропускаются с явной причиной. Финальный результат check фиксируется в итоговом сообщении задачи.
