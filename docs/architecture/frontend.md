# Архитектурные правила frontend

## Область применения и порядок работы

Frontend строится по модульной архитектуре: каждый модуль владеет своими
сценариями, API-контрактами, моделями, запросами, мутациями, состоянием и UI.
Правила применяются к `frontends/`; основной пример — Console на Vue 3,
TypeScript, Vue Router, TanStack Vue Query, Pinia и Axios.
Продуктовые сценарии и особенности Console описаны в
[docs/frontends/console.md](../frontends/console.md); читай нужные разделы по задаче.
Этот документ задаёт обязательные архитектурные правила, существующий код — примеры.

Перед реализацией:

1. Определи модуль-владелец и затрагиваемые пользовательские сценарии.
2. Перечисли входы и результаты сценариев: HTTP DTO, frontend-модели,
   значения форм и типы возвращаемых результатов.
3. Распредели файлы по ответственности: API, mapper, типы, query keys,
   queries, mutations, page state, страница, UI и маршруты.
4. Определи владельца каждого состояния, правила кеширования и обновления после
   мутаций, поведение при загрузке, пустом результате и ошибке.
5. Проверь API-контракт и существующие общие компоненты перед добавлением новых.

## Структура и границы модуля

Целевая структура нового или существенно перерабатываемого модуля:

```text
frontends/apps/console/src/modules/<feature>/
├── api/
│   ├── <entity>.api.ts
│   ├── <entity>.dto.ts
│   └── <entity>.mapper.ts
├── model/
│   ├── <entity>.types.ts
│   ├── <entity>.constants.ts
│   ├── <entity>.query-keys.ts
│   ├── use-<entities>-query.ts
│   ├── use-create-<entity>.ts
│   ├── use-update-<entity>.ts
│   ├── use-delete-<entity>.ts
│   └── use-<entities>-page-state.ts
├── pages/
│   └── <Entities>Page.vue
├── ui/
│   ├── page/
│   ├── results/
│   ├── item/
│   └── forms/
├── routes.ts
└── index.ts
```

Создавай только необходимые файлы. В `model/` структуры данных, запросы,
мутации и состояние разделяются по файлам; при росте модуля их можно группировать
в `queries/`, `mutations/`, `state/` внутри `model/`.
При узких изменениях сохраняй существующее расположение `pages/`, `components/`,
`queries/`, `mutations/` или `ui/page/`, соблюдая границы ответственности.
Расположение route-level Page в `ui/page/` не делает её обычным UI-компонентом:
для неё действуют правила страницы-оркестратора ниже.

В `app/` находятся сборка приложения, providers, router и session stores;
в `layouts/` — оболочки экранов. Общие технические компоненты и функции остаются
в `shared/`, `components/ui/` и `components/custom-ui/` согласно структуре проекта.
Общий код не импортирует бизнес-модули. Код одной фичи остаётся в своём модуле;
перенос в shared требует повторного применения и отсутствия бизнес-привязки.

Между модулями используй небольшой публичный контракт `index.ts`: необходимые
типы, маршруты, компоненты или функции. Глубокие импорты чужих API, query keys,
stores и внутренних composables запрещены. Циклические зависимости запрещены.

## Слои и направление зависимостей

| Слой / ответственность | Содержимое и допустимые зависимости |
| --- | --- |
| `api/` | HTTP-вызовы, request/response DTO и преобразования. Использует общий HTTP client и чистые frontend-типы; не знает о router, UI, query cache или stores. |
| `model/*.types.ts`, `*.constants.ts` | Frontend-модели, значения форм и чистые константы. Не импортируют API, DTO, Vue-компоненты, router или stores. |
| Queries в `model/` | Composables чтения: API-функции, query keys, параметры и TanStack Vue Query. Возвращают frontend-модели и состояние запроса. |
| Mutations в `model/` | Composables изменения: API-функции, pending/error, обновление или invalidation кеша. Не управляют разметкой и диалогами. |
| Page state в `model/` | Поиск, фильтры, сортировка, пагинация, вид отображения и синхронизация с URL. Не выполняет HTTP-вызовы. |
| Route-level Page | Собирает page state, queries, mutations, router и диалоги. Передаёт UI данные через props и обрабатывает emits. |
| `ui/` | Отображение и локальное взаимодействие. Использует props/emits, frontend-типы, дочерние UI и общие UI-компоненты. |

```text
Page → queries / mutations → API → общий HTTP client
Page → page state / router
Page → UI → дочерний / общий UI
API / queries / mutations / page state / UI → чистые frontend-типы
```

Обычный UI не импортирует API client, DTO, mapper, query keys, query/mutation
composables, router или session stores. Данные и действия приходят через
типизированные props/emits. Модели и API не импортируют страницы или UI.
Модули могут использовать публичные HTTP providers и session stores приложения;
это явные общие границы, а не разрешение импортировать внутренности `app/`.

## API, DTO и frontend-модели

- HTTP-запросы выполняются в `api/` через общий Axios client из
  `app/providers/http/`. Он задаёт `VITE_API_BASE_URL` (по умолчанию `/api`),
  `withCredentials`, CSRF и общую обработку транспортных ошибок.
  Компоненты и composables не создают собственные Axios instances.
- Request/response DTO в `*.dto.ts` точно отражают конкретные backend-контракты.
  Не подменяй их универсальным DTO или frontend-моделью; учитывай различие
  отсутствующего поля, `null`, пустой строки, `false` и `0`.
- `*.mapper.ts` преобразует DTO в frontend-модель и значения сценария в payload.
  Mapper — чистое преобразование без HTTP, кеша, router и изменения состояния.
- API-функции возвращают типизированные frontend-модели после mapping.
  DTO и Axios response не выходят в UI; значения форм описываются в `model/`.
  Для операции без результата используется `Promise<void>`.
- Сохраняй точность и смысл backend-значений: деньги/Decimal не преобразуются
  в floating point; идентификаторы, локали и даты преобразуются явно.
- Проверки формы помогают вводу; бизнес-инварианты и права проверяет backend.
  Ошибки полей и сценария передаются странице в пригодной для UI форме;
  формы не разбирают Axios response самостоятельно.

## Запросы, мутации и состояние

Разделяй источники состояния:

| Состояние | Владелец |
| --- | --- |
| Серверные коллекции и карточки, загрузка, ошибка, актуальность | TanStack Vue Query через query composables модуля. |
| Tenant, текущий пользователь, bootstrap и OTP | Session stores `useTenantStore` / `useUserStore` в `app/stores/`. |
| Поиск, фильтры, сортировка, пагинация, вкладка, вид | Page-state composable; параметры, которые должны переживать reload/ссылку, хранятся в URL. |
| Черновик формы, ошибки полей | Форма или отдельный composable черновика; общие черновики нескольких секций принадлежат их оркестратору. |
| Открытые диалоги, текущий выбор, локальное взаимодействие | Page или ближайший UI-владелец; глобальный store нужен только для состояния между экранами. |

- Query keys определяются централизованно для модуля и включают все влияющие
  на запрос параметры: tenant, ID, locale, серверные фильтры и пагинацию.
  Query function использует те же параметры; чтение передаёт `AbortSignal` в API.
- Queries не выполняют изменения данных. Каждое действие создания, обновления
  или удаления имеет свой mutation composable с конкретным входом и результатом.
  После успеха он обновляет или инвалидирует затронутые detail/list keys.
- Серверные данные не копируются в Pinia или локальный `ref` как второй кеш.
  Session stores остаются существующей границей auth: могут напрямую вызывать
  identity API и владеть текущим пользователем, OTP и profile update.
- Черновик отделён от результата query. Refetch не стирает несохранённый ввод;
  подтверждение сохранения очищает только отправленный снимок, сохраняя новый ввод.
- Повторный submit блокируется на время mutation. Optimistic update требует
  определённого rollback; неоднозначный результат создания или upload не запускает
  автоматический повтор, способный создать дубликат.
- При смене tenant/session очищай соответствующие кеши и черновики, отменяй
  запросы и игнорируй поздние ответы старого контекста. Таймеры, watchers и listeners
  освобождаются вместе с владельцем; данные разных tenant не смешиваются.
- Специфические очереди, debounce и autosave размещаются в `model/`, отдельно
  от UI. Их правила восстановления и повторов определяются конкретным сценарием.

## Страницы и UI-компоненты

Page — оркестратор экрана. Она соединяет участников сценария, а повторяемую
разметку, поля формы, карточки и ветки загрузки/пустого результата выносит в UI.
Создавай компоненты по реальной ответственности, без пустых заготовок под всё дерево.

| Компонент | Ответственность |
| --- | --- |
| `<Entities>Header` | Заголовок, описание, основное действие страницы. |
| `<Entities>Toolbar`, `<Entities>SearchBar` | Фильтры, сортировка, вид, массовые действия; поиск выделяется, если это самостоятельный элемент. |
| `<Entities>Body` | Выбирает `Skeleton`, `Empty`, `Error` или `Results`; сохраняет полезные данные при фоновом обновлении. |
| `<Entities>Results` | Выбирает загруженное представление `List`, `Grid` или `Kanban`. |
| `<Entities>List/Grid/Kanban` | Отображает коллекцию; не загружает данные и не получает `loading`/`empty` вместо состояния Body. |
| `<Entity>Card/ListItem/KanbanCard` | Отображает одну сущность. |
| `<Entity>Form` | Поля, валидация, типизированный submit; не вызывает API. |
| `Create<Entity>Dialog`, `Edit<Entity>Dialog` | Модальное взаимодействие и форма; передают submit оркестратору. |
| `Delete<Entity>Dialog` / `ConfirmDialog` | Подтверждение удаления; отдельная форма не нужна. |
| `<Entities>Footer` | Обычная или бесконечная пагинация; Results не управляет навигацией. |

Общие UI-компоненты не содержат бизнес-терминов, API и feature state.
Например, общий `PagePagination` получает числа и emits, а Footer модуля связывает
его со своим page state. Props не изменяются дочерним компонентом; изменение
состояния запрашивается событием или явно объявленным `v-model`.

Используй существующие semantic tokens, layouts, shadcn-vue primitives
из `components/ui/` и custom UI из `components/custom-ui/`.
Сохраняй адаптивность, keyboard navigation, labels и доступные состояния
loading/error/disabled. Имена компонентов: plural для коллекции, singular для
одной сущности; назначение выражается суффиксом Page, Form, Dialog, Body и т. п.
Публичные функции и контракты имеют типы входов и явные возвращаемые типы;
нетипизированный `any` не заменяет DTO или frontend-модель.

## Проверка перед завершением

1. Проверь весь diff по применимым правилам: границы модулей, импорты,
   разделение DTO/model, query/mutation/state и Page/UI.
2. Проверь наличие необходимых файлов и конкретных контрактов каждого сценария;
   общие компоненты не должны получать API, router или бизнес-зависимости.
3. Для изменений Console выполни из `frontends/`:
   `npm run lint:console`, `npm run typecheck:console`, `npm run build:console`.
   Запусти применимые тесты затронутых сценариев.
4. Для UI-изменений проверь в браузере основные действия и загрузку, пустой
   результат, ошибку, повтор, pending mutation и мобильный viewport.
   Для состояния проверь URL/reload, сохранность ввода и смену tenant/session,
   если они затронуты. Для других frontend-приложений используй их команды.
5. Для изменений только документации проверь ссылки, согласованность правил
   и diff; сборка приложения и UI-тесты не требуются.
6. Исправь нарушения до завершения. Успешная сборка не доказывает соблюдение
   архитектуры; в итоговом ответе укажи проверки и оставшиеся ограничения.
