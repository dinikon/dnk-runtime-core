# Console на Vue

Консоль операторов Runtime находится в `frontends/apps/console/` и использует
Vue 3, TypeScript, Vue Router, Pinia, TanStack Vue Query и общий Axios client.
Нормативные требования: [архитектура frontend](../architecture/frontend.md).

## Сборка приложения и границы модулей

- `src/app/router.ts` собирает маршруты и устанавливает authentication guards.
- `src/app/navigation/workspace-navigation.ts` описывает меню рабочего пространства.
- `src/layouts/workspace/AppLayout.vue` задаёт общую оболочку и область страницы.
- `src/app/stores/tenant.ts` и `user.ts` владеют tenant и текущей сессией.
- `src/app/providers/http/` задаёт base URL, cookies, CSRF и обработку 401.
- `src/modules/<feature>/` содержит API, модели, queries, состояние и UI фичи.

Новые модули подключаются через небольшой публичный `index.ts`, страницы
загружаются лениво. UI использует типизированные props/emits и существующие
компоненты из `components/ui/`, `components/custom-ui/` и `shared/`.

## Авторизация и tenant

Приватные страницы рабочего пространства находятся под существующим
`requiresAuth` guard. Tenant разрешается общей оболочкой. Данные серверных
коллекций принадлежат Vue Query, а не session stores.

Запросы выполняются общим HTTP client с базовым URL `/api` по умолчанию.
Изменяющие запросы используют общую CSRF-защиту. Ответ 401 сбрасывает текущую
сессию и переводит на вход с сохранением адреса назначения. Модули не создают
собственные Axios instances или обходные auth-механизмы.

## Складская номенклатура

Модуль `src/modules/inventory/` предоставляет страницу `/inventory/items`.
Пункт меню: **Склад → Номенклатура**. Backend-контракт описан в
[Inventory](../modules/inventory.md).

Текущий UI-срез содержит таблицу, поиск по SKU, серверную пагинацию, обновление
списка, создание номенклатуры, редактор полной карточки SKU и удаление с подтверждением.
Модуль также экспортирует выбор SKU и поиск для сценариев Catalog.

| Колонка | Представление |
| --- | --- |
| SKU | Канонический SKU; колонка закреплена слева |
| Базовая единица | Системный код, например PCS, KG или L |
| Шаг количества | Точная Decimal-строка без Number/округления |
| Прослеживаемость | Название TrackingMode |
| Учёт срока годности | Название ExpirationMode; OPTIONAL отображается как заметка |

Модуль читает `GET /api/console/inventory/items` через путь
`/console/inventory/items` общего client. HTTP DTO остаются в `api/`;
mapper создаёт frontend-модели с camelCase-полями. Список не содержит названий
товаров Catalog, остатков, штрихкодов или клиентской версии позиции.

### Поиск и URL

URL хранит `search`, `page` и `limit`, например
`/inventory/items?search=oil&page=2&limit=50`. Номер страницы переводится
в `offset=(page-1)*limit`; размер по умолчанию 50, варианты — 20, 50 и 100.
Некорректные значения нормализуются с сохранением посторонних параметров и hash.

Поиск применяется после 300 мс без ввода; Enter применяет его сразу.
Изменение поиска или размера страницы возвращает на первую страницу.
Поиск использует replace, переходы пагинации — push, поэтому reload и
навигация браузера восстанавливают состояние. Поиск выполняется сервером;
frontend не подменяет backend casefold преобразованием JavaScript.

### Кеш и состояния

Query key включает namespace inventory, tenant ID, user ID, sessionRevision,
поиск, offset и limit. Query function читает снимок параметров из того же ключа
и передаёт AbortSignal в API. Запрос разрешён после готовности tenant/session.
Актуальность кеша — 30 секунд, временная ошибка чтения автоматически повторяется
один раз; ответы 4xx автоматически не повторяются.

Смена tenant/session отменяет запросы и удаляет кеш прежнего контекста через
общий `useScopedQueryCache`, очищает поисковый черновик и сбрасывает поиск/страницу.
Первоначальная загрузка tenant сохраняет параметры входящей ссылки.
Таймер поиска отменяется при навигации, смене контекста и размонтировании.

Body модуля показывает Skeleton, таблицу, пустую номенклатуру, отсутствие
совпадений, пустую страницу за пределами списка или ошибку с повтором.
Фоновое обновление сохраняет текущую таблицу; его ошибка выводится рядом с ней.
Пустая страница с page>1 предлагает переход на первую и не показывает
пагинацию с ложным диапазоном строк. Запросы не копируются во второй кеш.

DataTable отвечает за размеры колонок, закрепление и внутреннюю прокрутку.
Заголовок, поиск и пагинация доступны на узком экране. Полные SKU и значения
шага доступны через Tooltip при наведении или фокусе.

### Создание номенклатуры

Кнопка «Создать» в заголовке открывает диалог с единственным полем — ручным
кодом SKU. Открытие и отмена не создают запись. Явное подтверждение отправляет
`POST /api/console/inventory/items` только с `{sku}`: frontend не передаёт значения
настроек по умолчанию. Их выбирает `InventoryItem.create` в Domain.
После успеха обновляются detail/list cache и открывается редактор новой позиции;
«Назад» возвращает исходные параметры списка. DTO, mapper, API и mutation
принадлежат модулю Inventory, диалог использует только props/emits.

На время POST повторный submit, закрытие диалога и уход со страницы блокируются.
Пустой код проверяется формой, нормализация и остальные ограничения — сервером.
Отказ 409/422 сохраняет ввод. Неоднозначный ответ сети/5xx не запускает повторный
POST: диалог предлагает проверить список по введённому SKU. Смена tenant/user/
sessionRevision очищает форму и ошибки, отменяет запрос и игнорирует поздний ответ
без перехода в карточку другого контекста. Новая mutation использует ключи scope
и отключённый автоматический retry.

### Редактирование настроек SKU

Маршрут `/inventory/items/:inventoryItemId` открывается по SKU/действию
«Редактировать» в таблице или кнопке «Настройки SKU» рядом со связью в редакторе
товара/варианта Catalog. Публичный `inventoryItemEditLocation` формирует переход;
`returnTo` сохраняет исходные параметры списка либо редактора Catalog, включая
локаль и выбранный вариант. Прямая ссылка и reload загружают карточку по ID.

`GET /api/console/inventory/items/{inventory_item_id}` возвращает карточку,
`GET /api/console/inventory/uoms` — системные единицы и размерности. Единый черновик
содержит SKU, строки штрихкодов и четыре настройки учёта: базовую единицу, точный
шаг, прослеживаемость и срок годности. «Сохранить» отправляет только изменённые поля
одним PATCH; пустой запрос пропускается. Автосохранения нет.

SKU нормализуется сервером через trim + casefold; frontend показывает ответ,
не подменяя casefold преобразованием JavaScript. Штрихкоды вводятся строками,
сохраняя регистр и ведущие нули. Можно добавить, изменить и удалить строку.
Пустая добавленная строка требует исправления или удаления. Дубликаты после trim
подсвечиваются. Коллекция barcodes передаётся целиком только при её изменении;
пустой массив очищает коллекцию. Неизменённые коды сохраняют серверные ID,
изменённое значение получает новый ID. Локальные ключи строк отделены от ID
сервера и связывают ошибки с отправленной строкой после удаления соседней.

Проверки настроек поддерживают Decimal в обычной и экспоненциальной записи без
преобразования в Number. Серийный учёт требует PCS и шаг ровно 1, обязательный
срок — партий или серий. OPTIONAL остаётся необязательной заметкой о дате.
Окончательное решение принимает Domain. Недоступность UOM блокирует изменение
настроек, но не запись только SKU/штрихкодов и не удаление позиции.

Карточка и справочник принадлежат Vue Query с ключами tenant/user/sessionRevision/ID.
Refetch сохраняет грязный черновик. Ответ PATCH подтверждает отправленный снимок,
сохраняя более новый ввод полей и коллекции. На время записи блокируются повтор,
сброс, удаление и уход; поля остаются доступными. Ошибки сохраняют ввод.
422 с loc поля относится к текущему значению только при совпадении с отправленным;
409 и строковые Domain-ошибки показываются ошибками операции без разбора текста.
403/404 скрывают недоступные данные. Неопределённый PATCH не повторяется:
«Проверить карточку» перечитывает сервер, обновляет основание сравнения и сохраняет
весь текущий ввод для явного последующего сохранения. Новое редактирование не
скрывает действие проверки. До проверки повторная запись и удаление заблокированы.

Уход с несохранённым вводом требует подтверждения, закрытие вкладки использует
beforeunload. Смена tenant/user/session/ID очищает черновик и ошибки, отменяет запросы
и игнорирует поздние результаты. После PATCH отменяются старые чтения карточки и
списков; ответ обновляет detail cache, списки Inventory и представления упаковок
инвалидируются. Сборка query client приложения через публичные контракты Inventory
и Catalog инвалидирует проекции Catalog. Прямого импорта Catalog в Inventory нет.

Удаление доступно из таблицы и заголовка редактора через общий AlertDialog.
Он показывает сохранённый SKU, предупреждает об удалении штрихкодов/упаковок и
о потере черновика. Первоначальный фокус — на отмене. Pending DELETE блокирует
повтор, закрытие/Escape, навигацию и конкурирующие изменения. Связанный с любым
CatalogItem товар или SKU с партиями удалить нельзя: окончательное решение принимает backend,
409 показывается в диалоге с сохранением черновика. Предварительного is_in_use
в GET нет. 403 закрывает диалог и скрывает недоступные кешированные данные.

Успешный DELETE возвращает пустой 204, API имеет Promise<void>. Отменяются чтения
точной карточки, её упаковок и списков; карточка и кеш упаковок удаляются,
позиция исключается из страниц кеша. Total уменьшается только там, где найден ID.
Списки инвалидируются и перечитываются. Ошибка чтения не отменяет успех DELETE.
После свежего успешного чтения, включая повтор после ошибки, недопустимая последняя
страница корректируется с сохранением поиска, limit, посторонних query и hash.
Редактор очищает черновик и возвращается в список Inventory; исходный список
сохраняет URL. Одноразовая отметка history state передаёт необходимость проверки
пагинации без служебных query-параметров. Возврат из обычного редактирования
по-прежнему поддерживает Catalog.

Сетевой сбой, timeout/5xx либо 404 DELETE требуют «Проверить наличие»: свежий GET
того же ID без кеша/повторов подтверждает отсутствие либо предлагает новое явное
подтверждение. Автоматического повтора DELETE нет. Новых миграций и version нет;
полная замена штрихкодов сохраняет семантику последней успешной записи.
Проверки редактора, mapper, ошибок, кеша и публичной интеграции находятся в
`test/inventory-item-editor.test.ts`; PostgreSQL-контракт полной карточки — в
`test/test_inventory_item_card_postgres.py`.

## Упаковки SKU

ItemPackaging находится в модуле Inventory. Действие «Упаковки» доступно в таблице
номенклатуры и редакторе настроек SKU. Lazy-маршруты:
`/inventory/items/:inventoryItemId/packagings` и
`/inventory/items/:inventoryItemId/packagings/:packagingId`.
Контекст показывает сохранённые SKU, базовую единицу и шаг. Несохранённые настройки
SKU требуют подтверждения при переходе. Безопасный returnTo ограничен исходным
списком или редактором этого SKU; возврат из упаковки сохраняет поиск/страницу списка
и вложенный путь возврата редактора SKU в Catalog.

Таблица показывает код, название, точное количество содержимого, единицу и действия
редактирования и удаления. Search/page/limit хранятся в URL; поиск по коду/названию
применяется через 300 мс или Enter, пагинация серверная, размеры 20/50/100
(50 по умолчанию).
Поиск и смена размера сбрасывают страницу; посторонние query-параметры и hash
сохраняются. Активности у ItemPackaging нет.

«Создать упаковку» открывает диалог пяти обязательных полей: тип тары, код, название,
количество и единица содержимого. Первоначальная единица равна сохранённой базовой
единице SKU. Код, название и количество вводятся самостоятельно. POST передаёт
только эти пять полей; UUID выдаёт сервер, после успеха открывается редактор.
Редактор отправляет только изменённые поля PATCH, пустой запрос пропускается.
Количество хранится и передаётся строкой без Number/parseFloat/округления,
включая экспоненциальную запись. Код сохраняет регистр: BOX и box различаются
внутри SKU. Единицы выбираются из системного UOM-справочника по размерности SKU;
сервер проверяет точный пересчёт и кратность шагу. Смена только единицы сохраняет
числовое количество; выбор типа тары сохраняет ручные код и название.

Поиск типа тары серверный, с задержкой, фильтром активности и догрузкой страниц.
Infinite query имеет отдельный candidates key. Выбранный тип загружается по ID,
включая значения вне первой страницы и неактивные текущие ссылки. Поиск сохраняет
выбранный ID. Неактивный тип отображается с предупреждением: для любого сохранения
нужен активный итоговый тип. Можно выбрать другой тип или обновить сведения о текущем
после его реактивации. Обновление контекста SKU сохраняет черновик; несовместимая
текущая единица остаётся видимой для исправления.

API/DTO/mapper, queries/mutations, page state, черновик и UI разделены. Страницы
связывают сценарии, UI работает через типизированные props/emits. Серверные данные
принадлежат Vue Query. Ключи содержат tenant/user/sessionRevision, SKU/Packaging ID
и параметры запроса. Успех отменяет устаревшее чтение карточки, обновляет её кеш
и инвалидирует списки упаковок этого SKU. DTO упаковки не заменяет карточку товара.
Успех сохранения настроек SKU инвалидирует зависимые запросы упаковок.
Создание и изменение PackagingType инвалидируют отдельный кеш подсказок выбора.

Refetch сохраняет правки; подтверждение PATCH очищает только отправленный снимок,
оставляя более новый ввод. Ошибка поля относится к текущему значению только при
его совпадении с отправленным. Смена tenant/user/session/SKU/упаковки очищает
локальное состояние, отменяет запросы и игнорирует поздние ответы. Таймеры,
watchers и beforeunload освобождаются.

409 остаётся ошибкой операции: возможны занятый код и неактивный тип. При 409/422
обновляются сведения о типе и контекст SKU с сохранением ввода. 422 с loc поля
выделяет поле; текст Domain показывается ошибкой операции. 403/404 скрывают
недоступные данные. Временная ошибка фонового чтения сохраняет полезные строки
и черновик. Есть loading/empty/no-matches/out-of-range и повтор чтения.
POST блокирует повтор, поля, закрытие и уход; PATCH оставляет поля доступными,
блокируя повтор, сброс и уход. Несохранённые изменения требуют подтверждения ухода.
Неоднозначный POST не повторяется: списки помечаются устаревшими, «Проверить список»
ищет введённый код внутри того же SKU; пользователь проверяет точное совпадение.

Проверки моделей находятся в `test/inventory-item-packagings.test.ts` и
`test/inventory-item-packaging-delete.test.ts`. Backend-контракты и миграции
в этом UI-срезе не изменяются.

Удаление доступно из строки таблицы и заголовка редактора. Общий AlertDialog
показывает снимок сохранённых кода, названия, количества и единицы, а также SKU;
первоначальный фокус — на отмене. В редакторе есть предупреждение о потере черновика.
Отмена и ошибка сохраняют ввод. Удаление не зависит от активности типа тары
и доступности справочников. DELETE передаёт только ID владельца/упаковки в URL,
возвращает Promise<void>, не читает JSON из 204 и использует общий CSRF client.

На время DELETE или проверки результата блокируются повтор, закрытие диалога,
Escape, уход со страницы и конкурирующие изменения. Поиск/пагинация приостановлены,
ожидающий поиск отменяется. После подтверждения отменяются старые detail/list reads
этого SKU; удаляется точная карточка, ID убирается из кешированных страниц,
total уменьшается только в страницах, содержащих ID. Списки владельца инвалидируются;
активный список перечитывается. Ошибка этого чтения не отменяет успех удаления.
После свежего успешного чтения опустевшая последняя страница заменяется последней
допустимой с сохранением поиска, limit, returnTo, посторонних query и hash.
Редактор очищает черновик и возвращается в собственный список через безопасный returnTo.

403 скрывает недоступные данные и очищает кеш упаковок владельца. 422 и другие
ожидаемые отклонения показываются ошибкой операции без подсветки полей формы.
Сетевой сбой, timeout, 5xx и неоднозначный 404 не запускают повтор DELETE;
«Проверить наличие» последовательно читает свежие SKU и упаковку без кеша/повторов.
Только существующий SKU и 404 упаковки подтверждают отсутствие: показывается
«Упаковка уже удалена». Существующая упаковка требует нового явного подтверждения;
недоступный/отсутствующий SKU не считается успешным удалением. Ошибку проверки
можно проверить повторно. Смена tenant/user/session/владельца/упаковки отменяет
операцию, сбрасывает подтверждение и исключает позднее обновление чужого кеша.

## Партии SKU

Карточка SKU содержит переход «Партии» в `/inventory/items/:inventoryItemId/lots`.
Список показывает номер, дату производства и срок годности; номер открывает
`/inventory/items/:inventoryItemId/lots/:lotId`. Карточка партии предназначена
для просмотра. Назад возвращает только в собственный список с его фильтрами;
из списка можно вернуться в карточку SKU.

Поиск по номеру и серверная пагинация хранят `search`, `page`, `limit` в URL.
Поиск применяется через 300 мс или Enter, сбрасывает страницу; размеры 20/50/100,
по умолчанию 50. Reload восстанавливает параметры, посторонние query/hash сохраняются.
Номер остаётся строкой с исходным регистром и ведущими нулями. Календарные даты
хранятся строками YYYY-MM-DD или null; Date, UTC и timezone-преобразования не используются.

Создание доступно при LOT и LOT_AND_SERIAL. При NONE/SERIAL показывается причина
недоступности; сохранённые партии можно читать. Диалог принимает номер и две
необязательные даты. При ExpirationMode.NONE срок отключён; REQUIRED объясняет,
что срок понадобится перед поступлением, без обязательности при создании карточки.
После POST открывается созданная партия, её detail-кеш обновляется, списки SKU
инвалидируются. Пустая дата передаётся null. Неизвестные даты и timestamp не отправляются.

HTTP DTO/mapper остаются в api, модели/keys/queries/mutation/page state — в model.
Страницы связывают участников; UI получает типизированные props/emits. Серверные
данные принадлежат Vue Query, ключи включают tenant/user/sessionRevision, SKU,
партию и параметры списка. Изменение SKU инвалидирует зависимые запросы партий;
утрата доступа или удаление SKU очищает относящийся к нему кеш партий.

409/422 и refetch сохраняют ввод. При отказе обновляется актуальный контекст SKU,
не перезаписывая черновик. POST блокирует повтор, закрытие, Escape и уход;
несохранённые данные требуют подтверждения ухода. Неоднозначный POST не повторяется:
«Проверить список» ищет введённый номер для ручной проверки точного совпадения.
Смена tenant/user/session/SKU очищает форму, отменяет запросы и игнорирует поздний
результат старой операции. 403/404 скрывают недоступные данные; временная ошибка
фонового чтения сохраняет полезные строки, доступен повтор.

Предусмотрены loading, empty, no-matches, out-of-range, повтор чтения и мобильный
вид таблицы/диалога. Проверки моделей: `test/inventory-stock-lots.test.ts`.
Редактирование и удаление партий относятся к следующим срезам.

## Склады

Тот же модуль `src/modules/inventory/` предоставляет список `/inventory/warehouses`
и редактор `/inventory/warehouses/:warehouseId`. Пункт меню: **Склад → Склады**.
API, DTO, mapper, queries, mutations, page state, черновик и UI складов отделены
от номенклатуры; общий контекст Inventory включает tenant/user/sessionRevision.

Таблица показывает код, название и активность. Код и действие «Редактировать»
открывают карточку; `returnTo` сохраняет параметры исходного списка. Поиск по коду
или названию применяется через 300 мс либо по Enter. Фильтр «Все / Активные /
Неактивные» передаёт `is_active`, включая явное `false`. URL хранит `search`,
`is_active`, `page`, `limit`; reload и история браузера восстанавливают состояние.
Размер страницы — 20, 50 или 100, по умолчанию 50. Поиск, фильтр и размер страницы
сбрасывают номер страницы. Посторонние параметры и hash сохраняются.

«Создать склад» открывает диалог кода и названия. Только подтверждение отправляет
POST с `{code, name}`. Активность, основную STORAGE-локацию и её назначение
определяет сервер. После успеха открывается редактор созданного склада.
409/422 сохраняют ввод; неоднозначный ответ не повторяет POST автоматически
и предлагает проверить список по введённому коду с фильтром «Все».
На время POST повторная отправка, закрытие диалога и уход блокируются.

Редактор загружает карточку по ID и изменяет код, название и активность.
«Сохранить» отправляет PATCH только изменённых полей; явное `false` сохраняется,
пустой PATCH не отправляется. ID и основная локация в payload не входят.
Нормализацию кода и названия выполняет Domain; клиент проверяет обязательность
полей без подмены серверного casefold. Автосохранения нет.
Черновик отделён от query: refetch сохраняет правки, ответ записи подтверждает
отправленный снимок и сохраняет более новый ввод. Повторный submit, сброс и уход
блокируются при сохранении; уход с несохранёнными правками требует подтверждения.

Query keys содержат scope, тип запроса, ID либо все параметры списка. Чтение
передаёт AbortSignal; успешная запись обновляет detail cache и инвалидирует списки
складов. При смене контекста запросы отменяются, кеш/черновики/ошибки очищаются,
поздние ответы игнорируются. Retry чтения ограничен одной временной ошибкой;
4xx и изменения автоматически не повторяются.
Загрузка, отсутствие совпадений, пустой справочник, страница вне диапазона,
403/404 и повтор ошибки имеют отдельные состояния. Фоновое обновление сохраняет
таблицу и ввод; таблица прокручивается внутри доступной ширины на мобильном экране.
Удаление и управление остатками в этот срез не входят.

В редактор Warehouse добавлен отдельный блок «Основная локация хранения».
Текущий адрес читается по `defaultStorageLocationId`, включая локации вне первой
страницы списка. Отсутствие назначения, загрузка и ошибка с повтором различаются.
«Изменить основную локацию» или «Назначить основную локацию» открывает диалог.
Серверный поиск с debounce 300 мс и infinite query выбирает только активные
STORAGE этого склада, включая дочерние адреса с неактивным родителем. Можно
догрузить следующие страницы. Неактивность Warehouse не запрещает настройку.

Подтверждение отправляет отдельный PUT
`/api/console/inventory/warehouses/{warehouse_id}/default-storage-location`
с единственным `location_id`. Очистка назначения не предоставляется.
Назначение и PATCH настроек склада не выполняются одновременно. Выбор не меняет
сервер до подтверждения; отмена не отправляет запрос. На время записи закрытие
диалога, повторный submit и уход блокируются. Несохранённые код, название и
активность Warehouse сохраняются: ответ назначения не подтверждает их черновик.
Фоновое обновление также сохраняет выбранную пользователем локацию.

Успех обновляет detail cache Warehouse и инвалидирует списки складов. Признак
основной локации и защита её активности в StockLocation используют тот же кеш
Warehouse; собственные поля локаций при назначении не изменяются. Query keys
изолированы по tenant/user/sessionRevision/warehouseId и параметрам поиска.
При смене контекста запросы отменяются, выбор/ошибки очищаются, поздние ответы
игнорируются. Таймер поиска освобождается при закрытии и размонтировании.

422 с указанием `location_id` выделяет поле выбора; Domain-отказ показывается
ошибкой операции. 404 обновляет сведения о складе и выбранной локации, сохраняя
выбор для исправления. Ошибка назначения не выделяет код Warehouse.
Автоповтор PUT отключён. При неоднозначном результате «Проверить назначение»
перечитывает склад, чтобы увидеть фактическую ссылку перед ручной повторной попыткой.

## Локации склада

Локации находятся в том же модуле Inventory. Действие «Локации» доступно в
списке и редакторе Warehouse. Маршруты:
`/inventory/warehouses/:warehouseId/locations` и
`/inventory/warehouses/:warehouseId/locations/:locationId`.
Безопасный `returnTo` сохраняет исходный список или карточку этого же склада.

Плоская таблица показывает код, название, тип, локальную активность и признак
основной STORAGE. Поиск по коду/названию, активность, тип, родитель, номер и размер
страницы хранятся в URL. Пагинация серверная; поиск применяется через 300 мс или
Enter. Действие «Дочерние» выбирает непосредственных детей и сбрасывает остальные
фильтры. Все уровни доступны при отсутствии фильтра родителя.

«Создать локацию» открывает диалог обязательных кода, названия, типа и
необязательного родителя. Родитель ищется на сервере с догрузкой следующих
страниц; доступны все типы и неактивные адреса этого склада. Выбранный родитель
загружается отдельно по ID, включая значения вне первой страницы подсказок.
POST отправляет только `code`, `name`, `location_type`, `parent_location_id`;
начальную активность задаёт сервер. Неактивный склад запрещает создание,
но допускает изменение локальных настроек существующих локаций.

Редактор изменяет только код, название и активность; склад, тип и родитель
показываются как сведения. PATCH содержит только изменённые поля, включая явное
`false`; нормализация остаётся в Domain. Назначенная основная STORAGE определяется
по Warehouse, её деактивация блокируется в UI и проверяется сервером. Если сведения
о складе не загружены, основная локация считается неизвестной: переключение
активности и сохранение недоступны, повтор загрузки сохраняет черновик.

Серверные данные принадлежат Vue Query. Ключи содержат tenant/user/sessionRevision,
ID склада и локации либо все фильтры и параметры страницы. Поиск родителей использует
infinite query. Запись обновляет карточку и инвалидирует списки и поиск родителей.
Фоновое чтение сохраняет правки; подтверждение PATCH учитывает отправленный снимок
и оставляет более новый ввод. Смена контекста отменяет запросы, очищает черновики
и старые кеши, поздние ответы игнорируются. Таймеры и обработчики освобождаются.

Ошибки 422 связываются с полями, если сервер указал поле; 409 остаётся ошибкой
операции, поскольку может означать занятый код или запрет деактивации основной
локации. Ввод сохраняется. Повторный submit и уход заблокированы при записи;
несохранённые правки требуют подтверждения ухода. Неоднозначный POST не повторяется
автоматически: «Проверить список» ищет введённый код без остальных фильтров.
Загрузка, пустой справочник, отсутствие совпадений, страница вне диапазона,
403/404, временная ошибка и повтор запроса имеют отдельные состояния.

Дерево, удаление и смена родителя/типа в этот срез не входят. Основная STORAGE
назначается в редакторе Warehouse, описанном выше. API и миграции в UI-срезе не изменяются.

## Типы тары

Справочник PackagingType находится в модуле Inventory: меню «Склад → Типы тары»,
маршруты `/inventory/packaging-types` и `/inventory/packaging-types/:packagingTypeId`.
Таблица показывает код, название и активность; код и действие «Редактировать»
открывают карточку. Поиск по коду/названию, активность, страница и размер
20/50/100 (по умолчанию 50) хранятся в URL. Поиск применяется через 300 мс или Enter;
смена фильтра или размера возвращает первую страницу. Посторонние параметры и hash
сохраняются; безопасный `returnTo` допускает только список типов тары.

Диалог создания запрашивает только `code` и `name`. UUID и начальную активность
задаёт сервер. Код сохраняет регистр: `BOX` и `box` — разные коды; поиск при этом
не учитывает регистр. Клиент не выполняет casefold или Unicode-нормализацию.
Редактор меняет код, название и активность, включая неактивные записи. PATCH
отправляет только изменённые поля, сохраняет явный `false`; пустой запрос не отправляется.
Деактивация запрещает новые назначения, существующие варианты упаковки сохраняются.

API/DTO/mapper, query keys, чтение, мутации, page state и черновик разделены.
Страницы связывают участников, UI получает типизированные props/emits.
Серверные данные принадлежат Vue Query; ключи содержат tenant/user/sessionRevision,
ID либо все фильтры/пагинацию. Успех отменяет устаревшее чтение карточки,
обновляет её кеш и инвалидирует списки. Черновик независим: refetch сохраняет
правки, подтверждение отправленного снимка оставляет новый ввод во время PATCH.
Смена контекста очищает черновики, диалог и старый кеш, отменяет запросы;
поздние ответы игнорируются. Таймеры и обработчики освобождаются.

409 выделяет код; 422 связывается с полем только при его указании сервером.
При PATCH ошибка поля относится к текущему вводу, только если он совпадает
с отправленным. Ошибки операции сохраняют ввод. Повтор записи отключён.
Во время POST блокируются поля, закрытие, повторный submit и уход; во время PATCH
поля доступны для нового ввода, а повтор, сброс и уход заблокированы.
Несохранённые изменения требуют подтверждения ухода. При неоднозначном POST
«Проверить список» ищет введённый код без фильтра активности, сохраняя регистр;
пользователь проверяет точное совпадение перед новой попыткой.

Предусмотрены загрузка, пустой справочник, отсутствие совпадений, страница вне
диапазона и повтор чтения. Временная ошибка фонового чтения сохраняет таблицу;
403/404 скрывают недоступные данные и редактор. Формы и таблица доступны с клавиатуры
и на мобильном экране. Проверки моделей — `test/inventory-packaging-types.test.ts`.
Удаление, назначение ItemPackaging, API и миграции в этот UI-срез не входят.

## Выбор SKU в Catalog

InventorySkuPicker, тип InventorySkuOption и useInventorySkuSearch экспортируются
через публичный index.ts Inventory. UI получает props/emits; поиск и debounce
300 мс находятся в model, используют общий Axios client, Vue Query и AbortSignal.
Ключи включают tenant/user/sessionRevision/search/offset/limit. Подсказки не
ограничивают точный выбор на сервере первыми 50 строками: новый код повторно
проверяется серверным сценарием по точному совпадению.

Создание товара состоит из выбора типа и необязательного выбора SKU. Выбор
existing/create остаётся черновиком до единственного POST Catalog; отмена не
создаёт складскую позицию. VARIABLE получает SKU через свои продаваемые варианты.
В редакторе отдельная mutation отправляет PUT /items/{id}/sku или вложенный
маршрут варианта. Ввод только ищет; выбор, создание и очистка — явные действия.
На время сохранения повторные действия блокируются; ошибка сохраняет ввод и
предыдущую связь. После успеха обновляются кеши Catalog и Inventory. Смена
контекста, включая sessionRevision, отменяет чтение, очищает черновики/кеши и
не позволяет позднему ответу заменить состояние новой сессии.

## Проверки

Из каталога `frontends/`:

```sh
npm run lint:console
npm run typecheck:console
npm run build:console
npm --workspace @dnk/console run test:inventory
npm --workspace @dnk/console run test:catalog
```

Тесты inventory проверяют DTO mapping, точность Decimal, retry policy, URL,
debounce/disposal, валидацию настроек, подтверждение снимка черновика, сброс
состояния и изоляцию кеша при смене tenant/session. Тесты складов дополнительно
проверяют nullable-ссылку основной локации, фильтр неактивных, частичный PATCH,
подтверждение черновика с новым вводом и безопасный возврат в список.
Тесты StockLocation дополнительно проверяют конкретные payload создания/изменения,
фильтры типа/родителя, атомарный переход к детям, URL, ключи выбранного склада,
изоляцию черновика и обработку конфликтов без ошибочного выделения поля кода.
Тесты назначения основной STORAGE проверяют payload, фильтры кандидатов,
ключи контекста, сохранность выбора при refetch и независимость черновика Warehouse.
При UI-изменениях дополнительно проверяются основные состояния, поиск,
пагинация, повтор запроса, клавиатура и мобильный viewport в браузере.
