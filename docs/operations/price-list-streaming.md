# Потоковая синхронизация прайс-листов

## Исполнение и атомарность

`presentation/jobs/handler.py` преобразует scheduled-job payload в immutable command и вызывает `SynchronizePriceListUseCase` или `CleanupPriceListUseCase`. HTTP и CRON используют общий composition root `presentation/depends`. Application получает порты и immutable `ImportOptions`; SQLAlchemy session остаётся внутри shared UoW adapter.

Поддомены: `price_list` — настройки и lifecycle; `offer` — предложение, текущее состояние и история; `sync_run` — попытка импорта. Staging является технической инфраструктурой. Идентификаторы tenant и агрегатов передаются как VO. Domain не зависит от HTTP, ORM, Pydantic и глобальной конфигурации.

Worker выполняет четыре разных прайса одновременно. PostgreSQL advisory lock сериализует один `(tenant, price_list)` между процессами. Конфликт блокировки откладывает задачу без расходования попытки. Worker продолжает heartbeat lease во время скачивания, разбора и публикации; timeout не заменяет lease.

Источник скачивается с checksum во временный дисковый файл. Проверенный DNS-адрес закрепляется при соединении, исходное имя используется для Host/TLS; каждый redirect проверяется отдельно. XML разбирается SAX по записи, YAML — по событиям с ограничением вложенности/aliases, XLSX — через ZIP/XML и дисковый индекс shared strings с ограниченным LRU-кешем. Незавершённые XML-токены ограничиваются до накопления большого буфера Expat; центральный ZIP-каталог XLSX проверяется до создания ZipFile и ограничен 8 МиБ. Блокирующее чтение выполняется вне event loop, очередь пакетов ограничена. Preview использует эти же адаптеры и кооперативную отмену.

Staging записывается короткими транзакциями; уникальный индекс `(sync_run_id, external_id)` обнаруживает дубликаты между пакетами. До полного чтения и валидации источника предложения не меняются. После проверки одна транзакция читает staging по ключу, применяет предложения и историю пакетами и обрабатывает отсутствующие позиции через `NOT EXISTS` внутри заранее ограниченного диапазона ID. Пустой пакет отсутствующих позиций продолжает обход, если дальше есть кандидаты. Перед commit повторно проверяются status/revision прайса, token/status/tenant и фактический срок lease scheduled job. Цена блокируется `FOR NO KEY UPDATE`, чтобы pause/archive не ждали FK-блокировок новых предложений.

Читатели видят предыдущую опубликованную версию до commit. Публикация остаётся длительной транзакцией: это требует места для WAL, старых версий строк и индексов. Память процесса ограничена пакетами и кешами; объём диска и транзакции растёт с числом строк. Не обещается фиксированное время импорта.

## Результаты и повторы

- От 0 до `MAX_ERROR_RATIO` ошибочных строк включительно: публикуются валидные строки. При наличии ошибок статус `partial`, обработка отсутствующих товаров полностью пропускается.
- Пустой источник, отсутствие валидных строк, превышение порога, повтор идентификатора или повреждённый документ: публикация откатывается целиком.
- Цены нормализуются к `NUMERIC(19,4)` до сравнения/хеширования; NaN, Infinity, переполнение, отрицательные значения и дробные остатки запрещены. Старый hash не считается доказательством изменения: сравниваются нормализованные значения.
- История добавляется только при изменении состояния. Повтор после успешного commit с тем же job ID не публикует данные второй раз.
- После сбоя попытка начинается заново: предыдущий staging очищается пакетами. Статусы run меняются под проверкой актуального владения задачей.
- Успешный staging удаляется пакетами после commit. Quarantine сохраняется. Failed/skipped staging хранится семь дней; cleanup также завершает осиротевшие runs, если их scheduled job окончательно завершилась или удалена. Ожидающие retry и активные задачи не затрагиваются.
- Pause/archive отзывает revision и задачи; выполняющийся импорт теряет право публикации. При штатном SIGTERM worker ограниченно ждёт задачи, затем отменяет их и освобождает lease для повтора.

## Конфигурация

Настройки одинаковы в `temaplate.dev.env`, Docker Compose, Helm values/schema и environment mapping.

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `PRICE_LISTS__BATCH_SIZE` | 1000 | Максимум записей в пакете |
| `PRICE_LISTS__MAX_ERROR_RATIO` | 0.5 | Допустимая доля ошибочных строк, включительно |
| `PRICE_LISTS__MAX_ROWS` | 2000000 | Максимум записей источника |
| `PRICE_LISTS__MAX_DOWNLOAD_BYTES` | 1073741824 | Максимум скачанного файла, 1 ГиБ |
| `PRICE_LISTS__MAX_UNCOMPRESSED_BYTES` | 4294967296 | Максимум распакованных ZIP entries, 4 ГиБ |
| `PRICE_LISTS__BATCH_MAX_BYTES` | 4194304 | Бюджет нормализованного пакета, 4 МиБ |
| `PRICE_LISTS__PARSER_QUEUE_BATCHES` | 1 | Число ожидающих пакетов |
| `PRICE_LISTS__MAX_RECORD_BYTES` | 1048576 | Ограничение одной исходной записи, 1 МиБ |
| `PRICE_LISTS__STRING_CACHE_BYTES` | 8388608 | Бюджет RAM-кеша XLSX shared strings, 8 МиБ |
| `PRICE_LISTS__MAX_TEMP_BYTES` | 4294967296 | Файл + дисковый индекс на импорт, 4 ГиБ |
| `PRICE_LISTS__FAILED_STAGING_RETENTION_DAYS` | 7 | Хранение staging неуспешных запусков |
| `SCHEDULED_JOBS__CONCURRENCY` | 4 | Число задач worker |
| `SCHEDULED_JOBS__JOB_TIMEOUT_SECONDS` | 3600 | Максимальная длительность задачи |

Одна запись может образовать отдельный пакет, если её размер больше `BATCH_MAX_BYTES`. SQL-чтение дополнительно ограничено байтовым бюджетом; fallback INSERT/UPDATE учитывает лимит bind-параметров. PostgreSQL/asyncpg использует COPY и типизированный `UPDATE FROM jsonb_to_recordset`. Пакетный поиск выполняет индексированные LATERAL lookup, чтобы новый прайс без статистики не перечитывался целиком для каждого пакета. Для пакетных UPDATE в текущей транзакции используется `plan_cache_mode=force_custom_plan`: ранний план маленькой таблицы не должен сохраняться после её роста.

XLSX имеет собственный предел 1 048 576 строк на лист: при одном заголовке доступно 1 048 575 записей независимо от `MAX_ROWS`. Прайс на 1 000 001 запись укладывается в этот предел. Колонки ограничены 256; заголовок/начало данных и выбранный лист сохраняют прежние настройки.

`MAX_DOWNLOAD_BYTES` не должен превышать `MAX_TEMP_BYTES`. `/tmp` должен находиться на диске, а не в tmpfs. Helm выделяет дисковый `emptyDir` с бюджетом `concurrency × maxTempBytes`. При четырёх задачах с полными бюджетами необходимо до 16 ГиБ временного диска плюс место PostgreSQL. После аварийного завершения процесса файлы живут до удаления временного volume; обычная ошибка/отмена удаляет их сразу. Для Compose обеспечьте соответствующий запас диска Docker.

Настройки heartbeat/lease сохраняются: по умолчанию heartbeat 60 секунд, lease 300 секунд. PostgreSQL pool должен вмещать admission/advisory соединения, четыре транзакции и служебные heartbeat; стандартный pool 30 + overflow 10 это предусматривает.

## HTTP-пагинация

Существующие URL `/price-lists`, `/price-lists/{id}/offers`, `/price-list-offers`, `/price-list-offers/{id}/history` и offset-ответы сохраняются. Offset-режим возвращает `items`, `offset`, `limit`, `total`.

Для предложений и истории доступны `pagination=cursor`, необязательный `cursor` и `include_total=true`. Ответ содержит `items`, `limit`, `next_cursor`, `has_more`; `total` присутствует только при явном запросе. Сортировка использует NULLS LAST и UUID как дополнительный ключ. Cursor привязан к tenant, фильтрам, направлению, сортировке и области истории; несовместимые параметры возвращают 422. `offset` нельзя совмещать с cursor-режимом.

Каждый запрос читает актуальное состояние. Долговременного snapshot между страницами нет: изменение сортируемого значения может переместить запись между запросами. `change_count` агрегируется только для предложений текущей страницы; count выполняется отдельно.

## Обновление и эксплуатация

1. Остановите приём задач старым worker и дождитесь завершения активных импортов.
2. Примените tenant Alembic-миграции до `0006_price_list_streaming` существующим механизмом проекта. Старые ревизии не изменяются. Таблицы, идентификаторы, история и накопленный quarantine сохраняются.
3. Разверните новую версию API и worker с согласованными настройками и ключом шифрования источников.
4. Проверьте worker readiness, продление lease, статусы runs, свободный временный диск и WAL. Смешанное исполнение старого и нового импортера не поддерживается.

Метрики: `price_list_sync_phase_duration_seconds{phase,format}`, `price_list_sync_batch_rows{phase,format}`, `price_list_sync_runs_total{status,format,trigger}`, `price_list_sync_rows_total{result}`, `price_list_sync_download_bytes_total{format}`, `price_list_sync_duration_seconds{format}`. Labels не включают tenant/job/list IDs или URL.

## Воспроизводимая проверка

`make check` запускает форматирование, backend (включая реальные PostgreSQL migrations), Helm и frontend в тестовом окружении. `test/test_price_list_bulk_postgres.py` проверяет атомарность, retry после commit, потерю lease, pause во время публикации, отмену, cleanup, cursor и HTTP. `test/test_partner_price_lists.py` покрывает нормализацию и безопасность потоковых парсеров/скачивания.

Нагрузочный сценарий: `python -m scripts.benchmarks.price_lists --rows 1000001 --output /results/million.json`, `TEST_POSTGRES_URL` указывает **только на отдельную тестовую PostgreSQL**. Запускайте в runtime-контейнере с `--memory=1g --memory-swap=1g`, дисковым `/tmp` и volume `/results`. Программа генерирует XML/YAML/XLSX, запускает четыре CRON-задачи (XML, YAML, XLSX, XML), затем неизменённый повтор, изменение 1% цен и массовое отсутствие. Проверяется число предложений/состояний, сохранность истории и завершение scheduled jobs. Временные tenant-схемы и задания удаляются после прогона.

Источники синтетические и локальные: тестирует worker, parser, staging и PostgreSQL, не скорость сети поставщика. Отчёт сохраняет RSS/cgroup peak, временный диск, длительности фаз, SQLAlchemy statements, WAL и `EXPLAIN ANALYZE BUFFERS`. Native COPY RPC не входят в счётчик SQLAlchemy statement events; сетевое время следует измерять на реальных источниках. Отдельный контроль первой загрузки и массового отсутствия запускается флагом `--missing-only`. Результаты конкретного стенда см. в `docs/benchmarks/price-lists-million.md`.
