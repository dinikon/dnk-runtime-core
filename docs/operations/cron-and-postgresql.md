# Cron worker и PostgreSQL: параллельные синхронизации

## Что изменено

Worker обрабатывает до четырёх задач одновременно. Он забирает из очереди только
задачи для свободных слотов; завершение быстрой задачи сразу освобождает слот,
даже если другая синхронизация ещё выполняется. `processLimit` ограничивает одну
выборку, `concurrency` — число активных задач. Это относится к `jobs worker`;
разовая административная команда `jobs process-due` сохраняет прежнее поведение.

У каждой задачи отдельное продление lease. После 900 секунд обработчик отменяется,
его незавершённая транзакция откатывается, задача возвращается на повтор с обычным
лимитом попыток. Потеря lease также отменяет обработчик. При SIGTERM worker
перестаёт брать задачи, ждёт до 60 секунд и возвращает незавершённые задачи в
очередь без расходования попытки. Kubernetes даёт ещё 20 секунд на очистку.

Разные прайсы могут синхронизироваться параллельно. Advisory lock одного прайса
закреплён за физическим соединением до освобождения. Конфликтующая задача
откладывается на 30 секунд без расходования попытки. Сессия блокировки не держит
открытую транзакцию во время загрузки файла.

Запись офферов, истории состояний и обновление текущих указателей выполняются
пакетами до 1000 строк в одной транзакции. Неизменившиеся цены не создают лишнюю
историю. Выборка текущих состояний использует JOIN вместо большого списка UUID.
При ошибке откатывается весь импорт, включая staging. Разбор файла выполняется
в отдельном потоке; сетевое ожидание и SQL используют async I/O.

## Пробы и Helm

`dnk-manage jobs healthcheck --liveness` проверяет только свежесть heartbeat
процесса. Без флага дополнительно проверяется файл `.ready`, который worker
обновляет после успешного обращения к БД. Обе команды используют только стандартную
библиотеку Python и не загружают приложение или драйвер БД. Допустимый возраст
файлов — 30 секунд; worker обновляет heartbeat не реже чем раз в 5 секунд.
Недоступность БД снимает readiness, а работающий цикл сохраняет liveness.

Значения для `Apps/dnk.runtime-core.yaml` (внутри `spec.source.helm.values`):

```yaml
application:
  scheduledJobs:
    processLimit: 4
  database:
    pool:
      size: 20
      maxOverflow: 0
      prePing: true
workers:
  cron:
    concurrency: 4
    jobTimeoutSeconds: 900
    shutdownGraceSeconds: 60
    probes:
      startup:
        exec:
          command: [dnk-manage, jobs, healthcheck, --liveness]
        periodSeconds: 5
        timeoutSeconds: 3
        failureThreshold: 24
      readiness:
        exec:
          command: [dnk-manage, jobs, healthcheck]
        periodSeconds: 10
        timeoutSeconds: 3
        failureThreshold: 3
      liveness:
        exec:
          command: [dnk-manage, jobs, healthcheck, --liveness]
        periodSeconds: 20
        timeoutSeconds: 3
        failureThreshold: 3
```

Значения нужно объединить с существующими секциями, сохранив остальные параметры.
Chart и runtime image должны содержать эти изменения. Старые переопределения
`readiness: null` / `liveness: null` отключают соответствующие пробы, даже если
они включены в defaults chart.

Пул cron должен вмещать как минимум `4 × concurrency + 2` соединения: tenant gate,
блокировка прайса, транзакция импорта, heartbeat lease и служебные операции.
Для четырёх задач минимум — 18; профиль выше даёт 20. Этот пул создаётся в каждом
процессе, не один на весь кластер. До увеличения числа задач проверьте память pod:
четыре разобранных файла одновременно потребляют больше RAM, чем один.

## PostgreSQL: 12 ГБ RAM, 6 CPU

При проверке 20 сентября 2026 сервер отвечал как PostgreSQL 16.1.
Наблюдались `shared_buffers=512MB`, `effective_cache_size=4GB`, `work_mem=4MB`,
`maintenance_work_mem=64MB`, `max_wal_size=1GB`, `max_connections=1000` и
26 текущих соединений. Число соединений — моментальный снимок, не пик нагрузки.

[Готовый пример postgresql.conf](postgresql-12gb-6cpu.conf) рассчитан на выделенный
сервер БД с указанными ресурсами. Если 12 ГБ делятся с другими сервисами, бюджет
нужно уменьшить: например, начать с `shared_buffers=2GB` и
`effective_cache_size=6GB`, оставив запас для остальных процессов.

| Параметр | Стартовое значение | Назначение |
| --- | --- | --- |
| `shared_buffers` | `3GB` | 25% RAM для страниц PostgreSQL |
| `effective_cache_size` | `8GB` | Оценка доступного кэша для планировщика; память не выделяет |
| `work_mem` | `8MB` | Бюджет сортировки/хеширования на операцию |
| `maintenance_work_mem` | `512MB` | VACUUM и построение индексов |
| `autovacuum_work_mem` | `128MB` | Бюджет одного autovacuum worker |
| `max_connections` | ориентир `200` | Только после расчёта суммарных пулов всех приложений |

`work_mem` умножается на операции, параллельные процессы и активные запросы;
хеширование может использовать дополнительный множитель `hash_mem_multiplier`.
Поэтому увеличение до сотен мегабайт при большом числе соединений опасно для
12 ГБ. `3GB` — исходная оценка, а не универсальный оптимум.
Основание: [PostgreSQL 16 — память](https://www.postgresql.org/docs/16/runtime-config-resource.html)
и [оценки планировщика](https://www.postgresql.org/docs/16/runtime-config-query.html).

Бюджет соединений: сумма `replicas × processes × (pool.size + maxOverflow)`
для всех клиентов плюс миграции, мониторинг, администрирование и одновременно
живущие старые pod при rollout. Четыре процесса DNK с пулом 20 дают до 80
соединений; полное удвоение при rollout — до 160. Лимит 200 оставляет 40 для
остальных нужд **только если нет других значительных клиентов**. Текущие defaults
30+10 дают до 160 уже без rollout. Значение 1000 само по себе не ускоряет БД;
снижать его до 200 можно после согласования пулов. Поэтому в примере эта строка
закомментирована.

Для серии массовых импортов пример увеличивает WAL до 4 ГБ и интервал checkpoint
до 10 минут, оставляет распределение записи `checkpoint_completion_target=0.9`
и включает сжатие WAL. Нужен запас диска: `max_wal_size` — мягкая граница, а не
максимальный размер каталога `pg_wal`. Надёжность записи остаётся включённой.
См. [PostgreSQL 16 — WAL](https://www.postgresql.org/docs/16/runtime-config-wal.html).

Autovacuum запускается чаще: vacuum scale factor 0.05, analyze scale factor 0.02,
три worker, проверка каждые 30 секунд. Это отправная точка для активно обновляемых
офферов и staging; на общем сервере предпочтительнее задать scale factors только
нужным таблицам через `ALTER TABLE ... SET (...)`.
См. [PostgreSQL 16 — autovacuum](https://www.postgresql.org/docs/16/runtime-config-autovacuum.html).

Для шести CPU предлагаются четыре параллельных SQL worker и до двух на запрос.
Это отдельный механизм от четырёх задач cron. Тип диска неизвестен, поэтому
`random_page_cost=1.1` и `effective_io_concurrency=200` оставлены как необязательный
вариант для подтверждённого SSD/NVMe. Их следует выбирать по задержкам диска и
планам запросов, а не только по количеству ядер.

## Применение и контроль

1. Сохранить текущую конфигурацию, проверить бюджет соединений, RAM и свободный
   диск. Включить файл через существующий `include`/`include_dir` PostgreSQL.
2. Проверить ошибки: `SELECT sourcefile, sourceline, error FROM pg_file_settings
   WHERE error IS NOT NULL;`.
3. Выполнить reload для параметров с контекстом `sighup`; изменения
   `shared_buffers`, `max_connections`, `max_worker_processes`,
   `autovacuum_max_workers` и `shared_preload_libraries` требуют рестарта.
   Проверка: `SELECT name, setting, unit, context, pending_restart FROM pg_settings
   WHERE pending_restart;` после reload. Рестарт БД согласовать отдельно.
4. Для анализа SQL добавить `pg_stat_statements` к существующему
   `shared_preload_libraries`, перезапустить БД и выполнить
   `CREATE EXTENSION IF NOT EXISTS pg_stat_statements;` в нужной базе.
   [Настройка расширения](https://www.postgresql.org/docs/16/pgstatstatements.html).
5. Сравнить время импорта, SQL calls, CPU, RSS worker, pool waits, dead tuples,
   частоту checkpoint и число рестартов на нескольких реальных синхронизациях.

Если нужны ограничения SQL, задавать их роли приложения, а не глобально для
миграций: отправная точка `statement_timeout='60s'`, `lock_timeout='5s'`,
`idle_in_transaction_session_timeout='60s'`. Сначала проверить, что штатные
импорты укладываются в этот предел. `idle_session_timeout` оставить 0:
соединения с advisory lock намеренно могут ждать загрузку файла без транзакции.
См. [PostgreSQL 16 — таймауты](https://www.postgresql.org/docs/16/runtime-config-client.html).

## Проверка изменения

Одноразовая локальная PostgreSQL 16, синтетические 11 074 валидные строки:

| Сценарий | SQL-запросы применения | Время с commit |
| --- | ---: | ---: |
| Первый импорт | 50 | 4.325 с |
| Повтор без изменений | 27 | 2.373 с |

Загрузка файла и создание записи запуска не входят в эти цифры. Это результат
одного локального замера; он не прогнозирует время production. Интеграционные
проверки покрывают историю изменений, исчезновение/возвращение позиций,
quarantine, откат целой транзакции и блокировку одного прайса. Проверки worker
покрывают заполнение свободных слотов, deadline, потерю lease, временный отказ БД
и завершение по SIGTERM. Рабочая PostgreSQL этим файлом не перенастраивалась.
