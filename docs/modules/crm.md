# CRM

CRM содержит самостоятельные Contact, Company, Lead, Deal и Basket. Deal является
единым объектом продажи; внутреннего Order нет. Первый срез создаёт Deal только в
состоянии `draft`. Оплаты, счета, выполнение, склад и доставка относятся к следующим
срезам [плана CRM](../plan/crm-lead-deal-funnel.md).

## Ответственность и хранение

Lead хранит собственные неполные сведения обращения, ссылки на Contact/Company,
позицию воронки и результат конвертации. Копирование Contact создаёт независимые
сведения и bindings; дальнейшее редактирование обращения не меняет контакт.
Пропущенные при создании наборы points копируются из Contact; явно переданные
пустые массивы остаются пустыми. Явные поля запроса имеют приоритет над копией.

Deal допускает прямое создание и несколько существующих контактов/компаний.
При конвертации сохраняет происхождение из Lead. У Lead/Deal ровно одна позиция
Funnel. Версия позиции меняется только при реальном переносе.

Basket владеет строками и единственным коммерческим итогом владельца. Цены и
количества — Decimal, до 6 знаков; HTTP представляет их строками. Стоимость строки
округляется до 2 знаков `ROUND_HALF_UP`, итог складывает округлённые строки.
USD/EUR/UAH ограничивают только CRM. Catalog используется через публичный read
сценарий; его тип/SKU копируются, строка допускает собственное коммерческое имя
и явную цену. Повторные товары имеют независимые ID строк. Полная замена корзины
требует `expected_revision` и сохраняет ID оставленных строк.

Таблицы нового среза: `crm_leads`, `crm_deals`, `crm_deal_contacts`,
`crm_deal_companies`, `crm_baskets`, `crm_basket_items`. Funnel хранится в
[собственном модуле](funnel.md). Миграция `0002_crm_sales_mvp` продолжает tenant
baseline; её SQL фиксирован и не импортирует изменяемые модели приложения.

## Контракты Console

Префикс `/api/console`. Коллекции `/crm/leads` и `/crm/deals` поддерживают POST и
GET; карточки `/{id}` — GET/PATCH. Списки возвращают `items`, `total`, `offset`,
`limit`; принимают `search`, `funnel_id`, `stage_id`, `sort=updated|title`,
`converted` для Lead. `limit` — 1–100, по умолчанию 20.

PUT `/{id}/stage` принимает `stage_id`, `expected_position_revision`.
PUT `/{id}/funnel` принимает `funnel_id`, `expected_position_revision` и назначает
первую стадию целевой воронки. Все изменяющие сценарии используют общий внешний
UoW, аутентифицированный tenant-контекст и CSRF. Basket собственного router не имеет.
GET `/crm/deal-currencies` возвращает валюты CRM, не меняя reference_data.

GET `/crm/leads/{id}/conversion-context` возвращает read snapshot, fingerprint,
points, доступные компании исходного контакта и семь режимов. POST
`/crm/leads/{id}/convert` требует `Idempotency-Key`, `expected_source_token`,
`expected_basket_revision`, явных наборов points каждого создаваемого результата.
Режимы: `contact`, `company`, `contact_company`, `contact_deal`, `company_deal`,
`contact_company_deal`, `deal`.

Конвертация блокирует источник, создаёт результаты, связи, bindings и независимую
копию Basket, затем замораживает Lead/Basket в одной транзакции. Ошибка откатывает
всё. Совпадающий повтор возвращает исходные ID и `replay=true`; другой запрос к
конвертированному источнику даёт 409. GET не создаёт отсутствующие корзины.

## Console

Маршруты `/crm/leads`, `/crm/deals` открывают канбан с независимыми серверными
страницами колонок или серверный список. Поиск, фильтры, вид, сортировка и страница
списка хранятся в URL. Глубина догрузки и доступная прокрутка запоминаются в памяти
по tenant/user/URL. Персональные черновики в localStorage не записываются.

Карточки `/:id` имеют общий локальный черновик сведений и Basket, явное сохранение
и защиту при уходе. Новые строки сопоставляются с серверными ID по клиентскому
ключу; ввод после отправки остаётся несохранённым. Выбор Contact показывает
копируемые сведения и требует подтверждения замены уже введённых данных.

Конвертация показывает шесть секций проверки и итоговую сводку. Первоначально
у Contact/Deal выбраны все points, у Company — ни одной. Pending блокирует
повтор и закрытие. При неизвестном результате доступны проверка и повтор того
же payload с прежним ключом. Конвертированный Lead доступен для чтения.

Переносы подтверждаются сервером. При конфликте либо неизвестном ответе карточка
перечитывается; если проверка не удалась, следующий перенос блокируется до повтора
проверки. Поиск отменяет устаревшие чтения. Запросы и кеши включают tenant и user;
смена контекста сбрасывает черновики и игнорирует поздние результаты.

UI использует существующие компоненты Console. Серверные данные находятся в
TanStack Vue Query; UI получает props/emits. Funnel и Catalog используются через
публичные frontend-контракты. Пустых вкладок будущих операций и автоматизаций нет.

## Проверки

Новые тесты: `test_crm_sales_domain.py`, `test_crm_sales_postgres.py`,
`frontends/apps/console/test/crm-sales.test.ts`. PostgreSQL-тесты требуют отдельной
`TEST_POSTGRES_URL`. Они покрывают семь конвертаций, rollback/replay/конкурентность,
точки связи, независимый Catalog snapshot, точную корзину, версии, CRUD,
tenant-изоляцию, аутентификацию и CSRF. Архитектурные тесты проверяют регистрацию,
цепочку миграций и границы модулей.

Браузерная приёмка выполняется против изолированной PostgreSQL-сборки с тестовым
пользователем: создание, прямой Deal, участники, Catalog, корзина, конвертация,
воронки, канбан/список, догрузка, URL/reload, потеря ответа, конфликты, сохранность
ввода, мобильный экран и клавиатура. Реальный вход через почту/SSO и внешние
операционные интеграции не являются частью этой CRM-проверки.
