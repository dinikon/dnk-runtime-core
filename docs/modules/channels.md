# Channels: подключения, публикации и представления

Срез от 28.10.2026: Backend → Shared Worker → Console для подключений Prom,
Rozetka и WooCommerce, проверки доступа и постраничного импорта публикаций.
Console работает с локальными снимками, сопоставлениями с Catalog и редактором
представлений публикаций. Реализована ручная доставка контента в WooCommerce.
Заказы, автоматическая доставка и XML остаются следующими срезами. Цены и остатки
описаны отдельно ниже.

## Границы

Независимые Aggregate Root: `Channel` (владеет Entity `Connection`), `SyncRun`,
`ExternalPublication`, `CatalogBindingGroup`, `StockSync`, `ProductRepresentation`
`ContentMedia` и `ContentDelivery`.
Каждый имеет собственный Domain Repository. Каталоги слоёв разделены по агрегатам.
Общие адаптеры остаются в `infrastructure/platforms/{prom,rozetka,woocommerce}`.

Domain использует dataclass, Enum и существующий `EntityIdVO`. В нём нет Pydantic,
SQLAlchemy и моделей платформ. Фабрики `create/restore` проверяют ревизии,
сочетания статусов и времени, роли и идентичность. JSON копируются на входе и
выходе. Чистая `PublicationStructurePolicy` проверяет затронутое дерево: один
уровень, то же подключение, допустимый родитель, отсутствие самоссылки. Mapper
не исправляет противоречивое состояние.

Каждый пакет явно связывает конкретные config, credentials, manifest, verifier
и reader. Общий порт не использует `Generic`/`TypeVar` и модели платформ.
Manifest декларирует `verify_connection` и `publications`. Последнее означает
обязательную реализацию чтения источника, не право записи. Публичная доступность
`publications` требует проверенного подключения текущей ревизии. Таблицы
capabilities нет.

## Подключение, валюта и языки

| Платформа | Endpoint | Credentials | Settings |
|---|---|---|---|
| Prom | `https://my.prom.ua` | `token` | `currency: UAH`, `locales: [uk, ru]`, фиксированы |
| Rozetka | `https://api-seller.rozetka.com.ua` | `token` | `currency: UAH`, `locales: [uk, ru]`, фиксированы |
| WooCommerce | HTTPS base URL, включая подпуть WordPress | `consumer_key`, `consumer_secret` | `currency: UAH/USD/EUR`, `locale: uk/ru/en`; defaults `UAH`, `uk` |

Наборы Prom/Rozetka обязательны: другой код, неполный набор, дубли и дополнительные
языки отклоняются. Порядок нормализуется в `uk, ru`. Woo принимает одну валюту и
одну локаль. Коды дополнительно проверяются через публичные Application-контракты
справочников без доступа к их SQL-моделям.

Настройки остаются в JSON `ConnectionConfig`. Пустые прежние настройки читаются
с defaults без записи в БД. Сравнение выполняется после нормализации:
переименование и сохранение тех же настроек не меняют `config_revision`.
Операция `Channel.change_settings` повышает ревизию Channel один раз, даже при
одновременной замене названия и подключения.

Замена настроек или credentials повышает `config_revision`, отменяет активный
SyncRun и прежние задания, запускает проверку. Пропущенные credentials сохраняют
секрет; переданные заменяют комплект целиком. Секреты шифруются через
[Shared Cipher](shared-encryption.md), сериализуются явно с `get_secret_value()`
и не возвращаются в HTTP. После первой успешной проверки identity закреплена.
Другой магазин требует нового Channel; один магазин принадлежит одному Channel
в tenant. Удаление освобождает identity. Названия каналов могут повторяться.

- Prom: identity — единственная корневая группа `groups/list` с положительным ID
  и `parent_group_id=null`; страницы по 100, максимум 50. Стабильность кандидата
  identity на живых магазинах ещё требует проверки.
- Rozetka: Bearer API token, `GET /sites/get-auth-data` → `content.market.id`.
  Логина, пароля и парольного fallback нет. `success=false` при HTTP 200 — отказ.
  `content.id` не является идентификатором магазина.
- WooCommerce: защищённый `system_status` → canonical `environment.site_url`.
  Публичный индекс WordPress не подтверждает доступ.

## Снимки публикаций

| Платформа | Импорт и структура |
|---|---|
| Prom | Основной товар — продаваемый `simple`; разновидности — `variant` с `parent_id` на него |
| WooCommerce | `simple`, `variable` и дочерние `variant`; контейнер не является продаваемой позицией |
| Rozetka | Все позиции как самостоятельные `simple`; группировки остаются в `platform_data` |

WooCommerce `grouped`, `external` и неизвестные типы пропускаются со счётчиком.
Флаги `virtual`/`downloadable` поддерживаемые типы не исключают.

Публикация хранит стабильный UUID, ключ источника, роль, родителя и ревизию;
полный `raw_data`, `normalized_schema=publication.v1`, `normalized_data`,
`platform_schema`, `platform_data`; первое/последнее наблюдение и наблюдавший
SyncRun. Изменившийся снимок повышает ревизию; тот же обновляет только наблюдение.
JSONB-порядок ключей переводов не считается изменением.

Нормализуются названия по локалям, артикул, доступные ссылка/изображение, цены,
количество, режим остатка, наличие и состояние. Деньги — `Decimal`, JSON и HTTP
передают их строками. Неизвестное — `null`, ноль остаётся нулём. Цена не
пересчитывается: нормализованная валюта берётся из канала. Несовпадение с
источником не блокирует импорт и не создаёт предупреждения. Исходные значения
остаются в `raw_data`, валюта контекста — в `platform_data.source_currency`.

Prom/Rozetka сохраняют обе полученные языковые версии; нативный `ua` становится
`uk`. Отсутствующий перевод не копируется из `name` или другой локали. Woo
сохраняет текст под настроенной локалью, без перевода и поддержки WPML.
После изменения настроек снимок сохраняет прежние валюту и переводы до нового
получения. Console обозначает его `stale_configuration`.

Prom использует `variation_base_id`; отсутствующий родитель дозагружается перед
сохранением. При смене основного товара известные затронутые участники
перечитываются, итоговое дерево проверяется и сохраняется атомарно. Характеристики
не угадываются по названию/SKU.

Woo обходит товары, затем вариации каждого полученного `variable`. Следующий
родитель выбирается из БД: растущего списка в checkpoint нет.
`manage_stock=parent` разрешается в representation с явным источником общего
остатка. Название контейнера наследуется только при отдельном нормализованном
признаке, без смешивания локалей.

Rozetka постранично обходит `/goods/all` и `/goods/archive`, передавая только
`page` и `pageSize`. Параметр фильтрации наличия в запросы не добавляется.
Ключ — `source_offer` + `sync_source_id:price_offer_id`; `item_id` и `rz_item_id`
хранятся отдельно, последний может отсутствовать. Повтор в архиве обновляет тот же
UUID. Пропущенные и неполученные позиции автоматически не удаляются.

## Хранение и выполнение

Tenant-миграция `0007_channels_publications` следует за
`0006_channels_verification`. Новые таблицы: `channel_sync_runs` и
`channel_external_publications`. PK/FK/NOT NULL, уникальность
`(connection_id, resource_type, external_id)` и индексы подключения/родителя/запуска
защищают хранение. Новых бизнес-CHECK, SQL Enum и `parent_kind` нет.
Удаление Channel каскадно удаляет локальные подключения, запуски и публикации.
Отдельное удаление истории SyncRun не удаляет публикации.

`SyncRun`: `queued → running → completed/failed/cancelled`, собственная и
конфигурационная ревизии, current job, версионированный checkpoint, счётчики,
безопасная ошибка, время и признак автоматического запуска. Checkpoint содержит
фазу и курсор, без credentials и ответов товаров.

Успешная проверка создаёт автоматический запуск один раз для ревизии подключения.
Ручной старт под блокировкой Channel возвращает действующий запуск либо создаёт
новый полный обход после завершения. Автоматические повторы продолжают текущий
checkpoint через существующий Shared Jobs.

Шаг задания `channels.sync_publications`:

1. Короткий UoW блокирует Channel, проверяет run/config/job/lease, возвращает
   неизменный снимок доступа и курсора.
2. Расшифровка и запрос страницы/родителей выполняются вне SQL-транзакции.
3. Новый UoW повторно проверяет ревизии, владельца задания и lease.
4. Снимки, checkpoint, прогресс и следующее задание сохраняются атомарно.

Потерянная lease, повторная доставка и изменённое подключение не применяют
устаревшую страницу. Полученные страницы остаются после ошибки. Потерянное или
терминальное задание активного запуска даёт `recovery_required`; ручной старт
завершает прерванный запуск и начинает новый. При удалении Channel задания
отменяются, внешний API не вызывается.

Transport сохраняет HTTPS, запрет redirects, проверку публичного IP с закреплением
адреса и ограничение тела 2 MiB. Credentials не передаются в URL. Общая очередь,
TenantGate, lease и повторы принадлежат Shared Jobs.

## HTTP и Console

База: `/api/console/channels`. Аутентификация, `channels.read`/`channels.manage`
и CSRF сохранены. Прежние CRUD, manifests и `POST /{id}/connection/verify`
сохраняют контракты.

| Метод | Новый путь | Результат |
|---|---|---|
| POST | `/{id}/sync-runs` | 202, новый либо действующий запуск |
| GET | `/{id}/sync-runs/latest` | `{sync_run: …}` или `{sync_run: null}` |
| GET | `/{id}/sync-runs/{run_id}` | Состояние и `recovery_required` |
| GET | `/{id}/publications` | Карточки, `search`, `offset`, `limit`, `locale` |
| GET | `/{id}/publications/{publication_id}` | Карточка с выбранной позицией |

HTTP DTO явно перечисляют публичные поля, без raw/platform документов, checkpoint
и секретов. Чтение не восстанавливает агрегаты. Пагинация — по корням, дети
загружаются пакетно; поиск по ребёнку возвращает его карточку. Prom показывает
основной товар среди вариантов; Woo — вариации; Rozetka — одну позицию.
Диапазон цен считается только в одной сохранённой валюте.

Карточка передаёт `root_external_id`, `root_sku` и `root_main_image_url` из
корневой публикации. В списке WooCommerce название, артикул и фото относятся
к родительскому товару; состав `items` по-прежнему содержит только вариации.
Отсутствующее фото родителя отображается заглушкой, отсутствие артикула — его
внешним ID; данные вариаций их не подменяют.

Console: `/channels` показывает подключения общей DataTable с поиском, фильтрами
и пагинацией по 50 записей. `/channels/:id` открывает настройки в левой панели
шириной 340 px и вкладку «Публикации» с общей DataTable справа. Настройки
сохраняются кнопкой; уход с несохранённым черновиком требует подтверждения,
поиск и пагинация публикаций сохраняют черновик. Возврат через `returnTo`
разрешён только во внутренний список `/channels` и восстанавливает его фильтры.
Старый `/channels/:id/publications` перенаправляет на страницу подключения,
сохраняя query и hash; `/channels/:id/publications/:publicationId` остаётся
страницей публикации. Сохранены запуск, счётчики/ошибки/повтор, создание товара
из публикации и просмотр разновидностей. Форма поддерживает enum,
const и фиксированный массив языков без преобразования массивов в строки.
Поиск, язык, позиция и пагинация сохраняются в URL и tenant/session query keys.
Смена контекста отменяет запросы и очищает кеш. Polling выполняется только для
активного запуска; обновление не стирает черновик настроек. Без достоверного
общего числа процент выполнения не выводится.

## Привязки к Catalog

Локальный агрегат `CatalogBindingGroup` владеет явными парами продаваемых позиций.
У группы неизменны подключение, корень Catalog, режим и корень внешней карточки.
Перенос на другую карточку выполняется через снятие группы и создание новой.
Несколько независимых групп одного Catalog в одном подключении разрешены;
одна позиция Catalog может участвовать в разных группах. Внутри группы позиция
Catalog и публикация используются по одному разу. Публикация закрепляется только
за одной группой; у вариативной карточки резервируется всё семейство, включая
пока не сопоставленные позиции.

| Режим | Catalog | Публикации |
|---|---|---|
| `SIMPLE_TO_SIMPLE` | Простой товар | Самостоятельный `simple` без детей |
| `VARIABLE_TO_VARIABLE` | Варианты одной карточки | Prom: основной `simple` и `variant`; WooCommerce: только дети `variant` |
| `VARIABLE_TO_SIMPLE` | Варианты одной карточки | Независимые `simple` без детей, на всех трёх платформах |

Rozetka не поддерживает `VARIABLE_TO_VARIABLE`. Простой товар Catalog нельзя
сопоставить внешнему семейству или отдельной разновидности. Контейнер `variable`
Catalog и контейнер WooCommerce никогда не являются продаваемыми парами.
Частичное сопоставление разрешено, пустая группа — нет. Архивирование сохраняет
связь, физическое удаление использованной карточки или варианта запрещено.
Удаление Channel удаляет только собственные связи и локальные снимки.

Состояние вычисляется при чтении: `linked` — все известные позиции обеих сторон
сопоставлены; `partial` — остались свободные позиции; `conflict` — состав, роли
или закрепления стали несовместимыми. Добавление варианта даёт `partial`, изменение
родителя или типа может дать `conflict`. Пропуск позиции при импорте не означает
её удаления. Изменение контента, валюты, цены, статуса или остатка не разрывает связь.
`linked` обозначает полноту сопоставления, а не готовность публикации к продаже.

Новая tenant-миграция `0009_channels_catalog_bindings` добавляет только
`channel_catalog_binding_groups` и `channel_catalog_binding_items`. Ссылки на
Catalog — UUID через публичный Application-контракт владельца, без чужих SQL FK.
Переходы, режимы, роли и семейства проверяет Domain. SQL обеспечивает PK/FK,
уникальность и индексы. Хранение не добавляет capability, отправку, XML или Jobs.

Блокировки команд: семья Catalog → Channel → повторное чтение группы.
Создание и обновление сравнивают структурные SHA-256 токены (ID, kind, parent),
поэтому изменение текста или цены не инвалидирует форму. Обновление и снятие
требуют `expected_revision`; сохранение прежних пар не повышает ревизию.
Чтение выполняется на согласованном SQL-снимке, Catalog и семьи площадки
загружаются пакетно. DTO не содержат raw/platform JSON и credentials.

| Метод | Путь от `/api/console/channels` | Назначение |
|---|---|---|
| GET | `/catalog-bindings?catalog_item_id=…` | Группы карточки Catalog; также `channel_id`, `publication_id`, `mode`, `locale`, `offset`, `limit` |
| GET | `/{id}/catalog-bindings` | Группы подключения, те же фильтры |
| GET | `/{id}/catalog-binding-candidates` | Поиск корней Catalog с фильтрацией режима до пагинации |
| GET | `/{id}/publication-binding-candidates` | Локальные корни площадки и `occupied_ids` |
| POST | `/{id}/catalog-bindings/preview` | Проверка структуры без записи, токены и точные SKU-подсказки |
| POST | `/{id}/catalog-bindings` | Создание независимой группы, 201 |
| GET / PUT / DELETE | `/{id}/catalog-bindings/{group_id}` | Чтение, атомарная замена пар и явное снятие |

Существующий список публикаций принимает `binding=linked|unlinked` до пагинации.
Карточки списка и деталей содержат `bindings` с ID группы, корнем и названием
Catalog, режимом и вычисленным состоянием. Доступ использует `channels.read` и
`channels.manage`; изменения и POST preview защищены CSRF.

Console добавляет вкладку «Публикации» в просмотр и редактор Catalog, блок связей
в деталях публикации, отметки и фильтр в списке. Выбор канала, режим, поиск
кандидатов и явные пары доступны в общем редакторе. Точные уникальные SKU
применяются только отдельным действием. Для самостоятельной публикации можно
явно выбрать новую группу или добавить позицию в существующую `VARIABLE_TO_SIMPLE`. Цена, валюта, наличие, источник остатка,
архивный статус и устаревший снимок показываются для сравнения, не блокируя связь.
При конфликте редактор сохраняет ввод; перечитывание группы и выход с изменениями
требуют явного действия. Неоднозначный результат создания не повторяется:
пользователь сначала проверяет обновлённый список групп.

Проверки среза: `test.test_catalog_bindings`, `test.test_catalog_bindings_postgres`,
`channels-bindings.test.ts`, существующие Catalog/Channels/Files и архитектурные
наборы. Миграции проверяются только на disposable PostgreSQL-базах.

### Представление публикаций и preview

Первые два среза [плана контента](../plan/channels-content-representation.md)
реализуют вычисление представления существующей группы, сохранение overrides
и отдельное разрешение экспорта. Preview:

```http
POST /api/console/channels/{channel_id}/catalog-bindings/{group_id}/representation/preview
Content-Type: application/json

{}
```

По умолчанию читаются все локали типизированных настроек платформы. Тело
`{"locales":["uk"]}` выбирает их подмножество. `null` эквивалентен отсутствию
параметра; пустой список, дубли и ненастроенные локали отклоняются с 422.
Нужны аутентификация, `channels.read` и CSRF. Группа проверяется в границах
канала и tenant; чужой ID не раскрывается. Preview доступен и до проверки
подключения, поскольку не обращается к API площадки.

Результат `{representation, state, export_blockers, draft}` содержит:

- `binding_group_id`, `connection_id`, ревизии связи и конфигурации, `platform`,
  `mode`, локали и общий `as_of`;
- `binding_state` и структурные `issues` группы;
- `targets`: внешние и внутренние ID цели, стабильный `binding_item_id`, роль,
  `content` по локалям, исходный `catalog_content`, `ready` и причины блокировки;
- сохранённое состояние overrides, разрешение и его блокировки. `draft` отличает
  проверку переданного черновика от проверки сохранённого документа.

Контент ограничен `title`, `body` и упорядоченной `gallery` с `file_id`, `alt`,
`caption`; первое изображение главное. Отсутствие поля (`null`), явная очистка
описания (`""`) и пустая галерея (`[]`) сохраняют свой смысл. `origins` указывает
владельца каждого эффективного поля: `catalog`, `catalog_parent`, `group_override`,
`item_override` или `missing`.
Межъязыкового fallback и подстановки контента площадки нет. Неизменяемые типы
контента не содержат цен, остатков, SKU, Console URL или документов raw/platform.

`RepresentationBuilder` в Application использует публичный многоязычный
batch-контракт Catalog и локальные проекции Channels. Все чтения выполняются
на общей сессии UoW с `REPEATABLE READ`, установленным до первого SQL-запроса.
Чистая `RepresentationPolicy` в Domain переиспользует проверку структуры связей
и определяет готовность целей. Агрегаты ради чтения не восстанавливаются.

`SIMPLE_TO_SIMPLE` даёт одну цель; `VARIABLE_TO_SIMPLE` — сопоставленные
независимые позиции, включая частичную группу. Для Prom `VARIABLE_TO_VARIABLE`
сохраняет продаваемую основную позицию и её разновидности. Для WooCommerce
дополнительно формируется `container` из корня Catalog: при частичном
сопоставлении он блокируется с `representation_family_incomplete`, а контент
сопоставленных вариаций остаётся доступен. Конфликт структуры, отсутствующие
источники и устаревшие наблюдения возвращаются диагностикой. Отсутствующее
название блокирует цель с указанием поля и локали.

`ready` означает готовность локального контента. Для разрешения экспорта
дополнительно нужны текущее верифицированное подключение с identity, актуальная
структура и наблюдения, контент всех настроенных локалей и доступные изображения
overrides. Частичный `VARIABLE_TO_SIMPLE` допустим, `VARIABLE_TO_VARIABLE`
требует полной семьи. Preview не меняет сохранённое разрешение.

### ProductRepresentation и overrides

`ProductRepresentation` — отдельный Aggregate Root одной группы сопоставлений
с собственным Domain Repository. Неизменяемые `RepresentationOverridesVO`,
`ItemOverridesVO` и `LocalizedOverridesVO` содержат конкретные типы полей.
Domain определяет композицию, ревизии, переходы разрешения и очистку удалённых пар.
Application координирует Catalog, проверку Files и очистку HTML общим sanitizer.

Порядок композиции: эффективный Catalog → общие overrides группы → overrides пары.
Пара идентифицируется стабильным `CatalogBindingItem.id`. Общие значения применяются
и к контейнеру WooCommerce; отдельного ключа overrides контейнера нет. Языки и группы
одного товара независимы. `null` или отсутствие поля означает наследование;
`body: ""` и `gallery: []` явно очищают значение. Непустая галерея заменяет весь список.
Пустое название отклоняется. Сброс — сохранение полного документа без нужного поля.
Значения отключённой локали можно сохранить неизменными или удалить, но нельзя менять.

Сценарии на `/api/console/channels/{channel_id}/catalog-bindings/{group_id}/representation`:

| Метод | Путь относительно representation | Назначение |
| --- | --- | --- |
| GET | — | Сохранённые overrides, аудит, версии контекста и стабильные ID пар |
| PUT | — | Сохранение полного документа overrides |
| POST | `/preview` | Сохранённый результат либо переданный черновик без записи |
| POST | `/enable` | Повторная проверка и разрешение экспорта |
| POST | `/disable` | Выключение разрешения без проверки готовности |

GET требует `channels.read`; PUT, enable и disable — `channels.manage` и CSRF.
Команды принимают `expected_revision`, `expected_binding_revision`,
`expected_config_revision`. PUT также принимает `overrides: {common, items}`;
preview с overrides требует те же три версии. Устаревший контекст возвращает 409
и не перезаписывает документ. Невалидные поля/файлы возвращают безопасную ошибку 422.

GET и preview не создают строки. До первого PUT возвращается read-state
`id: null, revision: 0, export_enabled: false` и пустой документ. Первая сохранённая
ревизия — 1, экспорт выключен. Два одновременных первых сохранения дают один успех
и один конфликт. Enable до сохранения — 409; disable до сохранения ничего не создаёт.
Сохранение без изменений не меняет ревизию и аудит. Изменённый документ увеличивает
ревизию один раз; если он перестал быть готовым, тем же переходом выключается экспорт.
Разрешение — локальное согласие пользователя, доставки и заданий оно не запускает.

Миграция `0011_channels_representations` добавляет одну tenant-таблицу:

| Поля | Назначение |
| --- | --- |
| `id`, `binding_group_id` | UUID; одна запись на группу, FK с ON DELETE CASCADE |
| `revision`, `export_enabled` | Положительная сохранённая ревизия и разрешение |
| `overrides_schema`, `overrides_data` | Версия `representation_overrides.v1` и конкретный JSONB-документ |
| `created_at`, `updated_at`, `created_by`, `updated_by` | Аудит |

Таблица не хранит копию итогового контента и не заполняется миграцией. Изменение
состава группы в одной транзакции сохраняет строки и UUID неизменных пар, удаляет
overrides исчезнувших пар, сохраняет общие overrides и выключает экспорт с увеличением
ревизии представления. Неизменённый состав не сбрасывает разрешение. Удаление группы
каскадно удаляет представление, сохраняя Catalog и локальные наблюдения площадки.
Удаление канала удаляет представление вместе с прочими данными подключения;
Catalog сохраняется.

Команды используют общий UoW и порядок блокировок: Catalog → Channel → группа →
представление → Files по отсортированным ID. После блокировок версии перечитываются.
Files проверяется через публичные контракты владельца: свой tenant, ready, MIME
изображения. Чтения объектов storage и HTTP внутри транзакции нет. Публичные URL,
загрузка новых изображений, удержание media и проверка внешней доступности — будущий срез.

В Console у группы связей доступно действие «Представление публикации».
Редактор показывает Catalog и итог, источники полей и диагностику; позволяет выбрать
группу/пару и язык, очистить описание/галерею, вернуть наследование, выбрать изображения
из Files, менять порядок, alt и caption. Проверка черновика не сохраняет изменения.
Разрешение включается отдельным действием после сохранения и свежей проверки.
Черновик отделён от query cache: refetch, ошибка и конфликт не стирают ввод; текст,
введённый во время сохранения, остаётся несохранённым. Закрытие грязной формы требует
подтверждения. Смена tenant/session закрывает редактор, очищает кеши и игнорирует поздние
ответы старого контекста.

Проверки: `test.test_channels_representation`,
`test.test_channels_representation_postgres`, `test.test_channels_representation_overrides`,
`test.test_channels_representation_overrides_postgres` и `channels-representation.test.ts`.
PostgreSQL покрывает HTTP, права/CSRF, Files, tenant-изоляцию, все режимы связей,
согласованный preview, ревизии/no-op, гонки первого сохранения и изменения состава,
миграцию upgrade/downgrade и каскады. Browser QA покрывает ввод во время сохранения,
конфликт, галерею, разрешение, ошибки/повтор, смену сессии и мобильный экран.

### Галереи и ContentMedia

Media-срез добавляет подготовку итоговых галерей для API/XML и внешний доступ к
изображениям. Автоматическая доставка всего контента остаётся
следующим срезом. Preview ничего не публикует и не создаёт media-записей.

Явная подготовка:

```http
POST /api/console/channels/{channel_id}/catalog-bindings/{group_id}/representation/gallery/prepare
Content-Type: application/json

{"expected_revision":2,"expected_binding_revision":1,"expected_config_revision":1}
```

Нужны authenticated tenant, CSRF, `channels.manage` и `files.read` для каждого
фактически выбранного файла. Подключение должно быть проверено с текущей ревизией
и закреплённой identity, представление сохранено и экспорт явно разрешён.
Отсутствие media-записи не блокирует само включение разрешения.

Возвращаются `galleries`: цель, внешний ID, родитель, вид публикации, локаль и
упорядоченные `images` с `media_id`, ревизией, `file_id`, `alt`, `caption`, URL,
состоянием передачи и подтверждённым `remote_media_id`. Первое изображение главное.
Неопределённая галерея не превращается в очистку; явная пустая возвращается как `[]`.

Проверяются все итоговые изображения, включая наследуемые из Catalog. Files
проверяется через публичные контракты: свой tenant, ready-файл/диск, ownership
физического бакета и объекта, размер до 10 MiB, допустимый raster и фактический
MIME заголовка. Конвертация изображений не выполняется. Пакет WooCommerce
дополнительно ограничивает MIME своим поддержанным набором.

Первая SQL-фаза собирает согласованный снимок и права; затем транзакция завершается,
проверки storage выполняются вне SQL. Вторая фаза блокирует Catalog → Channel →
группу/представление, перечитывает версии и сравнивает контент Catalog. Файлы
блокируются по отсортированным ID, после чего создаются или переиспользуются media.
Изменение источника во время проверки не публикует устаревшие ссылки. Повтор и
конкурентная подготовка используют те же записи и токены.

Публичное чтение:

```text
GET|HEAD https://<tenant-api-host>/api/channels/content-media/{media_id}/image.{extension}?token=...
```

Tenant и канонический API host получаются из Tenancy; cookies, Console principal и
CSRF не требуются. URL содержит 256-битный случайный секрет и разрешает только этот
ресурс. Проверяются hash токена, отсутствие отзыва, актуальное разрешённое использование
в итоговой галерее, fingerprint и Files. Старый кеш сам по себе доступ не разрешает.
Чужой tenant, неверный токен, неправильное расширение и исчезнувший файл дают 404.
Ресурс отдаётся без redirect и публичной bucket policy, с `no-store`, `nosniff` и
`Referrer-Policy: no-referrer`; storage stream открывается после завершения SQL,
закрывается при EOF, отмене, disconnect и ошибке ответа. TenantGate удерживается
до завершения потока. Отзыв запрещает новые чтения; начатая выдача может завершиться.

`POST /api/console/channels/{channel_id}/content-media/{media_id}/revoke` принимает
`expected_revision` и идемпотентно отзывает ссылку. `…/renew` с тем же контрактом
явно меняет секрет после повторной проверки Files ACL и живого использования.
Старый URL перестаёт приниматься. Подготовка не восстанавливает отозванный доступ
автоматически. Отключение экспорта или исчезновение последнего использования
тоже прекращает новые чтения. Уже скачанные площадкой копии не удаляются.

`0012_channels_content_media` создаёт одну tenant-таблицу `channel_content_media`:
ID подключения и Files, source/metadata fingerprints, ревизия, hash/ciphertext токена,
дата отзыва, внешний ID, состояние/ID операции, безопасная ошибка и даты аудита.
Уникальность — `(connection_id, file_id, source_fingerprint, metadata_fingerprint)`;
индекс `file_id` обслуживает проверки использования. FK на подключение имеет CASCADE,
FK на Files нет. Галерея, позиции и alt не дублируются в этой таблице.

Files запрещает перезапись объекта: source fingerprint основан на стабильном UUID.
Пакет определяет metadata fingerprint: XML использует только файл, WooCommerce
разделяет attachment по alt, поскольку alt является общим свойством attachment.
Обычный повтор одного варианта использует ID; перестановка галереи не создаёт media.
Разные alt одного файла могут потребовать разные внешние attachment для сохранения
независимости групп. Подробнее: [код WooCommerce](https://woocommerce.github.io/code-reference/files/woocommerce-includes-rest-api-controllers-version3-class-wc-rest-products-controller.html).

Состояния: `not_required` для XML и `pending → in_flight → ready|unknown|failed`
для API. `BeginMediaTransferHandler` резервирует выбранные варианты под тем же
барьером подключения и проверяет три версии контекста. API вызывается снаружи
после commit. `RecordMediaTransferResultHandler` проверяет операцию, ревизию media,
конфигурацию и identity; запоздавшие результаты не перезаписывают состояние.
Unknown запрещает слепой повтор; подтверждённая сверка может зафиксировать ID
текущей операции. `InvalidateMediaReferenceHandler` сбрасывает только подтверждённо
исчезнувший attachment. Долговечная оркестрация полной доставки относится к следующему
срезу; эти сценарии и внешняя сборка уже доступны исполнителю.

`WooGalleryAdapter` формирует images-only запрос: первый раз `src`, далее `id`
без повторного скачивания. Порядок и alt проверяются также в ответе. В базовом
контракте вариации поддерживается одно изображение: лишние изображения и неподдержанный
caption дают явную ошибку, а не обрезаются. URL имеет расширение, поскольку WooCommerce
берёт имя для загрузки из URL: [реализация загрузчика](https://raw.githubusercontent.com/woocommerce/woocommerce/trunk/plugins/woocommerce/includes/wc-rest-functions.php).

Открытые токены не сохраняются в Domain/SQL и не включаются в repr. Используется
общий Shared Cipher. Uvicorn скрывает query в access logs; Console nginx отключает
логи media-location, штатный nginx ingress chart уже отключает access log. Внешний
операторский proxy также должен исключать секретные query из access/error logs.

Проверки: `test.test_channels_content_media`, `test.test_channels_content_media_postgres`
и `test.test_files_usage`. Покрываются anonymous GET/HEAD, настоящий MinIO, Files ACL,
отзыв/ротация, смена контекста во время storage I/O, наследование Catalog, конкуренция,
первый src/повтор id, независимость alt, unknown/revision fencing и миграция.
Рабочие tenant-схемы в рамках реализации не мигрируются.

### Ручная доставка контента WooCommerce

Пользователь сохраняет overrides, проверяет preview, отдельно разрешает экспорт
и запускает «Обновить на площадке». API capability `write_content` объявлена только
в manifest WooCommerce. Другие платформы сохраняют прежние capabilities; включение
экспорта не создаёт задания само по себе. Автоматические события Catalog и XML
в этот срез не входят.

Preview дополнен `content_fingerprint` и `delivery_issues`. Fingerprint включает
итоговые локализованные поля и адреса целей, не включает время или секретные URL.
Изменение наследуемого Catalog обнаруживается даже при прежней ревизии representation.
Preview черновика не разрешает отправку несохранённых изменений. Console требует
явно подтвердить просмотр сохранённого preview; изменение контента снимает отметку.

HTTP под `/api/console`:

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/channels/{channel}/catalog-bindings/{group}/content-deliveries` | 202, принятые поколения каждой цели |
| GET | `/channels/{channel}/catalog-bindings/{group}/content-deliveries` | Состояния целей и необходимость восстановления |
| POST | `/channels/{channel}/catalog-bindings/{group}/content-deliveries/{publication}/reconcile` | 202, запланированная сверка |

Первый POST принимает `expected_revision`, `expected_binding_revision`,
`expected_config_revision`, `content_fingerprint`. Нужны текущие версии, проверенное
подключение, identity, разрешение группы, `channels.manage` и `files.read` всех
фактически выбранных файлов. Устаревший preview даёт `content_preview_changed`/409.
Сверка принимает `expected_revision` состояния доставки. GET требует `channels.read`;
мутации также требуют CSRF и совпадения authenticated tenant с доменом.

Товар и variable-контейнер обновляются через `/products/{id}` только полями
`name`, `description`, `images`; вариация — через
`/products/{parent}/variations/{id}` полями `description`, `image`.
Отсутствующее значение не включается в запрос. Пустое описание и пустая галерея
явно очищают соответствующие поля. `short_description`, цены, остатки, SKU,
атрибуты, тип и состав вариантов не передаются.
Перед PUT вариации подтверждаются её фактические `parent_id` и тип из ответа API;
неполный или чужой адресат отклоняется до записи. Описание учитывает абзац wpautop
для простого текста и внешние переводы строк, не отбрасывая теги и внутренние пробелы.
Источник: [нативный контроллер](https://raw.githubusercontent.com/woocommerce/woocommerce/trunk/plugins/woocommerce/includes/rest-api/Controllers/Version3/class-wc-rest-product-variations-controller.php).
У вариации нет отдельного редактируемого имени: индивидуальный title override
блокирует доставку. Сохраняется режим одного изображения вариации текущего
адаптера; несколько изображений и caption отклоняются до постановки Jobs.
Многоизображение вариаций в отдельных версиях WooCommerce не заявляется автоматически.
Контракты: [товары](https://developer.woocommerce.com/docs/apis/rest-api/v3/products/),
[вариации](https://developer.woocommerce.com/docs/apis/rest-api/v3/product-variations/).

`ContentDelivery` — самостоятельный root одной пары representation/publication.
`0013_channels_content_deliveries` создаёт одну tenant-таблицу
`channel_content_deliveries` с составным PK `(representation_id, publication_id)`:

- revision, requested/sending/applied generations, status и current_job_id;
- requested_context с инициатором, версиями, identity, целью и fingerprint;
- prepared_schema, prepared_request_encrypted, prepared_context, prepared_hash;
- last_applied_hash, versioned result, безопасный error_code и даты аудита.

В prepared_context сохраняются неизменяемое намерение и версии/ID операций новых
media. Точное тело запроса шифруется Shared Cipher: оно может содержать media tokens.
Credentials и Authorization header не дублируются. Native body декодируется только
конкретными `WooProductContentUpdate` / `WooVariationContentUpdate`; общие слои
работают с типизированным envelope. Read DTO не содержат запрос или ciphertext.

FK на representation и publication используют CASCADE. Есть индекс publication_id
и частичный индекс status для queued/unknown. История попыток и lease остаются
в Shared Jobs, отдельной таблицы запусков нет. Миграция не запускает существующие
представления и в рамках реализации не применяется к рабочим tenant-схемам.

`channels.deliver_content` содержит только channel/group/representation/publication ID.
Рабочий API host Worker получает через публичный фасад Tenancy из активного
подтверждённого API домена; без отдельного API домена используется подтверждённый
основной Console host с API proxy. Права сохранённого инициатора проверяются тем же
AuthorizationServiceProtocol; Console-сессия и искусственный principal не нужны.
При отдельной политике авторизации Worker получает её через внешнюю сборку.

Порядок исполнения:

1. HTTP сохраняет поколения и Shared Jobs одним UoW. Одинаковый активный запуск
   объединяется; терминальный повтор создаёт новое пользовательское поколение.
2. Worker проверяет lease и контекст, подготавливает representation и media.
   Storage I/O выполняется между SQL-фазами. Затем точный запрос и резервации
   media фиксируются как `in_flight` одним commit.
3. Общий барьер подключения сериализует сетевой шаг с изменением конфигурации,
   удалением и другими исходящими операциями. Под ним выполняется короткая
   повторная проверка, затем UoW завершается перед API.
4. WooCommerce GET проверяет существующую цель и уже совпадающий контент. При
   необходимости выполняется PUT только разрешённых полей. Успех требует
   подтверждённого адреса, отправленных полей и порядка/alt/media ID в ответе.
5. Другой короткий UoW проверяет lease, задание, sending generation, запрос,
   config revision и identity. Результат цели и media применяются атомарно.

Подготовка использует порядок Catalog → Channel → representation → Files/media.
Под сетевым барьером повторного Catalog FOR UPDATE нет: иначе редактор, удерживающий
Catalog и ожидающий Channel, мог бы заблокировать завершение Worker.
Ключ старого stock-барьера сохранён; общая реализация находится в
`infrastructure/channel/gate.py`.

Статусы: `queued → in_flight → succeeded|failed|unknown`, а до отправки возможны
`blocked` и `cancelled`. Потеря lease запрещает применение старого ответа.
Повторное получение `in_flight` выполняет только сверку, даже если процесс упал
между commit и фактическим PUT. Доставка старого поколения не отмечает новое
намерение выполненным. Следующее явно запрошенное поколение планируется после
известного исхода; неизвестный исход блокирует следующую запись в ту же цель.
Изменение Catalog без нового запуска не вызывает автоматическую отправку.

Контейнер обрабатывается перед вариациями. Пока его исход неизвестен, дочерняя
работа откладывается. Известная независимая ошибка одной цели не отменяет успех
остальных. Отключение разрешения или изменение состава группы отменяет ожидающие
доставки. Удаление канала отменяет его jobs; начатый внешний запрос нельзя
откатить SQL-транзакцией.

Неизменившийся last_applied_hash сам по себе не пропускает отправку: Worker читает
текущий контент, поэтому повтор может восстановить ручное изменение на площадке.
Повтор изображения использует известный attachment ID, не src.

Таймаут, потеря ответа или потенциально частичное применение PUT переводят состояние
в `unknown`; `retryable` HTTP-ошибки не означает безопасный повтор записи. Сверка
выполняет только GET. Известные media IDs и отправленные поля могут подтвердить
успех. Совпадение alt/порядка не доказывает соответствие новой загрузки Files → ID:
если оно не подтверждается, unknown сохраняется, принудительной повторной загрузки
в первом срезе нет. Также несовпадение текущих значений не доказывает завершение
предыдущего запроса. Уже загруженные площадкой копии автоматически не удаляются.

Console показывает каждую цель, requested/applied generations, время результата,
причину отказа и действие сверки. Частичный итог вычисляется из целей. Поллинг
останавливается при терминальном результате или необходимости ручного восстановления.
Reload перечитывает серверное состояние; смена tenant/session закрывает редактор
и исключает применение поздних ответов. Черновик не заменяется результатами доставки.

Входящий raw/normalized snapshot публикации этим путём не перезаписывается.
Его актуализирует обычное чтение площадки; частичный ответ доставки не является
полным снимком публикации.

Проверки: `test.test_channels_content_delivery`,
`test.test_channels_content_delivery_postgres`,
`test.test_channels_content_delivery_architecture`, frontend
`channels-content-delivery.test.ts`. Проверены HTTP/Worker, native payload,
сохранение шифрованного запроса, повтор media ID, частичные результаты семьи,
таймаут, lease во время PUT, смена Catalog и конкурирующий редактор.
Live smoke действующего магазина требует рабочих credentials и в этот срез
не выполнялся.

### Создание Catalog из публикации

В списках публикаций показаны стоимость и остаток, а также три иконки:
открыть публикацию, открыть товар, отменить связь. При нескольких связях
иконки предлагают выбор товара или группы. Без связи средняя иконка предлагает
«Создать связь» и «Создать товар и связать», отмена остаётся недоступной.
В колонке связи также доступно явное действие «Создать связь».
Отмена требует подтверждения и актуальной ревизии группы. Остатки суммируются
без повторного учёта общего родительского источника; неизвестное количество
отличается от нуля.
Из списка и из карточки можно создать товар с автоматической связью. Для выбора
существующего товара открывается редактор сопоставлений с текущей публикацией
и подключением. Он использует прежние кандидаты, preview tokens и ревизии.
На время создания повторное действие блокируется, после создания
показывается «Открыть товар». Ошибки и предупреждения видны в карточке;
для уже связанной публикации открывается существующий товар.

Карточка публикации использует ту же оболочку с левой панелью 340 px и верхними
хлебными крошками, что подключение. Слева расположены сведения, цена и остаток,
действия связи, подключение и изображение. Справа — вкладки «Позиции» на общей
DataTable и «Связи с каталогом» с существующим редактором. Вкладка сохраняется
в `publication_tab`; ссылка с `binding` открывает вкладку связей и редактор.
Прямой адрес варианта подсвечивает его строку. У WooCommerce контейнер не
подставляется вместо варианта, у Prom сохраняется основная продаваемая позиция.
На телефоне сведения расположены над вкладками, прокрутка ограничена таблицей.
Возврат к подключению сохраняет поиск, язык, фильтр связи и пагинацию списка,
убирая только параметры карточки и редактора. Backend и DTO не меняются.

`POST /api/console/channels/{channel_id}/publications/{publication_id}/catalog-item`
получает актуальные детали через платформенный `get_details`, сохраняет изображения
в Files и атомарно создаёт Draft Catalog с привязкой. Ответ содержит
`catalog_item_id`, `binding_group_id`, `created` и `warnings`; новый товар возвращает
201, повторный запрос к уже связанной карточке — 200 и существующие ID.

Самостоятельная Simple создаёт Simple. WooCommerce Variable создаёт контейнер
и варианты. Семейство Prom создаёт Variable, в котором основной продаваемый товар
Prom также представлен вариантом. Тип и состав полученного семейства должны
совпадать с локальными публикациями; при изменении требуется синхронизация.

API и загрузка изображений выполняются вне транзакции Catalog. Перед сохранением
повторно проверяются ревизия подключения, локальное семейство и отсутствие связи.
Вставка товара и привязки фиксируется одним коммитом. Новых таблиц, операций,
миграций и фоновых заданий нет. Потеря ответа и конкурентные нажатия не создают
повторный товар, пока существует привязка.

Переносятся доступные переводы, описания, галерея, SKU, остатки и поддержанные
измерения с известными единицами, обычная и акционная цены с периодом акции.
Валюта берётся из конфигурации канала без пересчёта суммы. Цена контейнера
Variable отсутствует; цены сохраняются у продаваемых вариантов. WooCommerce
передаёт UTC-поля `date_on_sale_*_gmt`. Prom передаёт сумму или процент скидки:
адаптер вычисляет акционную цену; календарный период включает весь последний
день по `Europe/Kyiv` и сохраняется как полуоткрытый UTC-интервал. Rozetka
использует `price` как текущую цену. Значение `price_old` становится обычной ценой,
если оно выше текущей; тогда текущая цена сохраняется как акционная. Более низкая
`price_promo` может дополнительно уменьшить цену акции. Старая цена ниже текущей
и промо-цена выше текущей не применяются и возвращаются как предупреждения;
равные текущей значения не создают фиктивную скидку. Нативные значения остаются
в исходном снимке публикации.
Конфликтующие SKU
очищаются с предупреждением, включая все повторы внутри новой семьи.
Недоступные изображения пропускаются с предупреждением. Исходные публикации
не изменяются; последующая синхронизация не перезаписывает Catalog.

Prom читает `/api/v1/products/{id}`; для семейства дополнительно обходит список,
чтобы проверить полный актуальный состав разновидностей. Для переноса галереи
в Catalog ссылки CDN `images.prom.ua` на копии `_w200_h200_` и других размеров
преобразуются в ссылки без ограничения размера. Это применяется и к запасному
`main_image`; внешние URL и исходные снимки публикаций не изменяются. Уже
сохранённые файлы Catalog автоматически не заменяются. WooCommerce читает
продукт и страницы вариаций; при наличии веса или размеров единицы получает
из `/wp-json/wc/v3/settings/products` (`woocommerce_weight_unit` и
`woocommerce_dimension_unit`). Rozetka использует
`/goods/details?item_id=...&sync_source_id=...` либо `rz_item_id`; авторизация
остаётся по API-токену. При отсутствии обоих идентификаторов деталей возвращается
явная ошибка. В ответе деталей `photo_preview` допускается как массивом, так и
одной строкой URL; пустая строка означает отсутствие превью. При переносе
изображений полная галерея `photo` имеет приоритет над превью.
Контракт Rozetka: [официальная документация](https://api-seller.rozetka.com.ua/apidoc/#api-ApiItems-GetGoodsItemDetails).

## Синхронизация остатков

Количеством для отправки управляет Catalog. Ручное получение остатка с площадки
обновляет только публикацию; Catalog и остальные подключения не изменяются.
Полная синхронизация публикаций также не перезаписывает Catalog.

Пакеты Prom, WooCommerce и Rozetka объявляют `read_stock` и `write_stock` и
реализуют явные `get_stock` / `set_stock`. Проверенное подключение разрешает чтение.
Отправка дополнительно требует `config.settings.stock_sync.allow_export=true` у
подключения и количественного учёта соответствующей позиции Catalog. По умолчанию
отправка запрещена. Разрешением и его поколением владеет Entity Connection;
платформенная конфигурация доступа остаётся отдельным ConnectionConfigVO.
Изменение разрешения повышает ревизию агрегата один раз, не повышает config_revision
и не запускает верификацию или синхронизацию публикаций. Включение само по себе
ничего не отправляет. Старые задания и события отсекаются поколением и временем
изменения разрешения, в том числе после выключения и повторного включения.

Все настройки хранятся в существующем `channel_connections.settings`. Например:

```json
{
  "currency": "UAH",
  "locales": ["uk", "ru"],
  "stock_sync": {
    "allow_export": false,
    "revision": 1,
    "changed_at": "2026-10-30T10:00:00Z"
  }
}
```

В Domain используется immutable StockSyncSettingsVO, SQL-форма проверяется
StockSyncSettingsDocument, публичные настройки — конкретной строгой Pydantic-моделью.
Mapper разделяет и собирает платформенные настройки и локальную политику без
обращения к API. Публичный `config.settings.stock_sync` содержит только allow_export;
revision и changed_at управляются сервером и отклоняются при передаче клиентом.
Верхнеуровневого allow_stock_export в запросах и ответах Channel нет. В ответе
панели остатков это поле остаётся вычисляемым разрешением действия.

| Метод | URL относительно `/api/console/channels/{channel_id}/catalog-bindings/{group_id}` | Результат |
| --- | --- | --- |
| GET | `/stock` | Локальные количества, владельцы, состояние операции и причины блокировки |
| POST | `/stock-import` | 202; получить актуальное количество только в публикацию |
| POST | `/stock-export` | 202; согласовать связанную семью с Catalog; 200, если все позиции пропущены |

Получение принимает `publication_ids`: непустой список выбирает явные позиции,
пустой — все позиции группы. Отправка принимает пустой документ и всегда согласует
всю связанную семью. Ответ отправки содержит `operation_ids` и безопасные `warnings`;
неподдержанные состояния пропускаются, остальные позиции продолжают выполнение.
Одно задание семьи хранит отдельные результаты её участников. Повторный активный
запрос возвращает существующее задание; одновременное получение и отправка одной
семьи отклоняются до завершения текущей операции. Console сохраняет выбор строк
только для получения, показывает режим и источник Catalog, общий итог, ошибки
участников и предупреждения. Polling работает только для активной операции и
изолирован по tenant/session/channel/group.

`StockSync` хранится в `channel_stock_sync_states` по UUID участника
синхронизации. Новая tenant-миграция `0010_channels_stock_sync` добавляет эту
таблицу и раздел stock_sync существующего JSON настроек подключения. Таблица
channels не изменяется. SQL содержит структурные FK/PK и индекс;
состояния, поколения и топология проверяются Domain. Желаемое состояние хранится в типизированном JSONB `desired_state` вместо одиночного
количества; наблюдение сохраняет фактический результат API. Это текущее состояние,
а не журнал всех операций и не полный SyncRun публикаций.

Наблюдение изменяет только нормализованные поля остатка ExternalPublication и
версионированный `platform_data.stock_observation`. Полный `raw_data` остаётся
ответом последнего полного получения; нативные поля отдельного stock-запроса
сохраняются в stock_observation. Контент, цена, SKU, фотографии и last_sync_run_id
не изменяются. Более ранний полный API-запрос не затирает новое stock-наблюдение
той же ревизии подключения при позднем применении страницы.

Domain Catalog накапливает `CatalogStockChanged` только при изменении количества,
количественного учёта, ручного наличия, backorders или эффективного владельца. Событие содержит
UUID затронутых позиций без сохранённого количества. Изменение Catalog, Outbox и
внутренняя доставка Shared Jobs сохраняются в одной транзакции. Внутренняя доставка
не требует работающего брокера; внешний Outbox publisher независимо публикует тот
же envelope. Channels использует Shared Inbox для дедубликации и ставит задания
только для существовавших на момент события связей и действовавшего разрешения.
Создание карточки из публикации и создание связи не запускают отправку.

Worker выполняет короткую подготовку, сетевые запросы вне SQL-транзакции и короткое
применение с проверкой lease, config_revision, binding_revision и поколения операции.
Session advisory barrier сериализует сетевые операции Channel с изменением доступа,
разрешения, связей и удалением. Количество перечитывается перед записью; изменение
во время записи создаёт исправляющее задание. Повтор устанавливает абсолютное
актуальное значение. Уже переданный площадке запрос гарантированно отозвать нельзя.

Единственная политика Catalog разрешает собственный количественный учёт варианта,
затем наследование количественного учёта родителя, иначе ручное наличие варианта.
Ноль — заданное значение. Ручной статус родителя детям не наследуется.
Общая политика Channels не содержит названий платформ: она проверяет адресатов,
разрешения и объявленные адаптерами возможности (`StockFeaturesVO`). Один источник
может проецироваться в несколько независимых получателей. Конфликт разных источников
одной цели и дубли нативного адресата по-прежнему блокируют конкретные позиции.
Отрицательные количества не отправляются, ручное наличие не превращается в 0 или 1.

Адаптер WooCommerce воспроизводит режимы Catalog у родителя и вариантов, включая
включение и выключение manage_stock. Родитель выполняется первым; ошибка родителя
останавливает зависимые записи. Prom получает эффективное значение каждой продаваемой
позиции, включая основной товар семьи. При ручном наличии Prom меняются только
presence/in_stock без записи quantity_in_stock. Для Rozetka неподдержанный ручной
статус возвращает предупреждение stock_status_unsupported; количественный режим
сохраняет прежние проверки источника. Неподдержанные backorders также не подменяются.
Частичная связь разрешена: несопоставленные варианты не записываются, но Console
предупреждает о влиянии общего родителя на их наследуемые значения.

Повтор задания пропускает подтверждённые шаги. Изменение желаемого состояния уже
выполненного шага создаёт новое поколение согласования семьи. Цены, контент,
статус размещения и Catalog при чтении площадки не изменяются. Распределение общего
физического запаса и резервирование не входят в этот сценарий.

Prom использует GET `/api/v1/products/{id}` и POST `/api/v1/products/edit` с массивом,
отклоняет явные errors и проверяет наличие, а в количественном режиме — также количество и собственный режим остатка
контрольным GET. Пустой processed_ids при отсутствии errors допустим: Prom возвращает
такой ответ в том числе при повторной отправке уже установленного значения. Наличие
ID в processed_ids само по себе тоже не заменяет контрольное чтение. Warnings
не превращают подтверждённый остаток в отказ. Несовпадение фактического состояния
возвращает stock_write_unconfirmed и повторяется по правилам Shared Jobs.
Диагностика содержит ID публикации и товара, количество обработанных ID, ошибок и
предупреждений и безопасный технический код провайдера, если он доступен. Полные
ответы и credentials не логируются; Worker связывает результат с publication_id и
job_id. Неопределённое наследование количества
разновидности блокирует количественную запись. WooCommerce использует GET/PUT products/variations
и отдельно разрешает родительский manage_stock. Rozetka использует токен Bearer,
GET `/goods/details` и PUT `/items/mass-update`: отправляются только подтверждённый
item_rz_id и stock_quantity. Источник Rozetka уже должен иметь availability=4;
режим источника автоматически не переключается. Несколько локальных публикаций
с одним marketplace ID блокируют отправку до устранения неоднозначности.
Отсутствующий marketplace ID,
неподдержанный backorders и ошибки отдельных позиций возвращают безопасный отказ.
После записи адаптеры читают и проверяют фактическое количество; неподтверждённый
результат повторяется по правилам Shared Jobs.

## Постоянный XML-фид Prom

Реализован backend-срез `ContentFeed`: управление источником, проверка полного
документа и публичная выдача XML по управляемому токену. Первая версия поддерживает
Prom YML (`source_schema="prom.yml.v1"`), один полный каталог подключения
(`scope_key="catalog"`). Новая tenant-миграция `0014_channels_content_feeds`
создаёт `channel_content_feeds`. Передача ссылки в API Prom и отслеживание импорта
в этот срез не входят; получение XML не означает применение контента на Prom.
UI настройки фида в Console пока не добавлен.

Prom объявляет `content_feed` в manifest; capability API-доставки `write_content`
остаётся отдельной. Синхронизация Prom сохраняет строковый API `external_id` как
`platform_data.import_key`, не заменяя нативный ID публикации. Существующие
публикации требуют повторной синхронизации. Нельзя подставлять внутренний ID Prom,
SKU или вычисленный номер при отсутствии ключа.

### Управление

Все пути управления относительны к `/api/console/channels/{channel_id}/content-feeds`.
Требуются авторизация `channels.manage` и совпадение tenant с доменом запроса;
изменения и POST preview требуют CSRF.

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/` | 201; выключенный фид с новым токеном |
| GET | `/` | `items` — список публичных карточек |
| GET | `/{feed_id}` | `feed` — карточка |
| PUT | `/{feed_id}` | Замена источника/настроек с `expected_revision` |
| POST | `/{feed_id}/preview` | `ready`, `statistics`, `issues` полной сборки |
| POST | `/{feed_id}/enable` | Полная проверка и CAS-включение |
| POST | `/{feed_id}/disable` | Выключение endpoint |
| POST | `/{feed_id}/access/rotate` | Новый токен; прежняя ссылка перестаёт работать |
| POST | `/{feed_id}/access/revoke` | Отзыв токена и выключение |
| DELETE | `/{feed_id}?expected_revision=…` | 204; удаление фида |

POST создания принимает:

```json
{
  "source_url": "https://supplier.example/catalog.xml?token=…",
  "source_schema": "prom.yml.v1",
  "source_settings": {"base_locale": "ru"}
}
```

PUT принимает те же настройки и обязательную `expected_revision`; отсутствующий
`source_url` сохраняет прежний адрес. Остальные изменяющие POST принимают только
`expected_revision`. Сохранение неизменных настроек не повышает ревизию; изменение
источника или параметров выключает фид до повторной проверки. Выключение сохраняет
токен. Ротация отозванного токена не включает фид автоматически.

`feed` содержит ID, ревизию, enabled, scope_key, source_schema/source_settings,
public_url и created_at/updated_at. Исходный URL не возвращается. Если публичный
HTTPS origin ещё не настроен, public_url равен null; включение отклоняется с
`feed_public_origin_unavailable`. Запись токена хранит hash и ciphertext через
существующий проектный Shared Cipher. Записи фида удаляются каскадно с подключением.

### Публичная выдача

`GET /api/channels/content-feeds/{feed_id}/feed.xml?token=…` работает без Console-сессии.
Tenant определяется через существующий Tenancy host/admission. Выключенный,
отозванный, чужой фид и неправильный токен дают 404. Токен не имеет автоматического
срока истечения. Ответы имеют `Cache-Control: no-store`; query не сохраняется
в Uvicorn access log. Origin берётся из Tenancy, а не из произвольного Host.
Для внешнего Prom нужен действительный доступный публичный HTTPS origin.

Каждый GET заново загружает полный исходный документ. Источник — публичный HTTPS
URL без redirect, credentials в authority, внутренних адресов и рекурсии feed URL.
Query источника может содержать секрет, поэтому URL шифруется. Существующий
`PublicHttpsTransport` закрепляет проверенный DNS/IP и ограничивает ответ;
обращение выполняется без HTTPX INFO-логирования секретного URL. Лимит источника
и готового документа — 10 MiB, общий timeout загрузки — 30 секунд.
XML не раскрывает entities и не загружает внешние DTD; глубина ограничена 128,
число узлов — 200000. Стандартное объявление DOCTYPE допускается без загрузки DTD.

В исходном дереве меняются только название, описание и picture разрешённых
представлений. Несопоставленные позиции и группы с выключенным экспортом остаются
исходными. Цены, остатки, SKU, offer/category ID, group_id, параметры и неизвестные
расширения сохраняются. Сохранность относится к структуре и значениям, а не
к исходному форматированию XML. Пустой документ, дубли ключей, отсутствующая
разрешённая цель или ошибка любой разрешённой группы блокируют весь ответ.

Профиль `base_locale="ru"` использует name/description для ru и name_ua/description_ua
для uk. Другой языковой профиль отклоняется. Обновление названия vendor.model
отклоняется: Prom игнорирует name при этом типе. Для украинской версии требуются
непустые название и описание. Галерея одна на offer: разные наборы файлов по
локалям запрещены; порядок сохраняется, первое изображение главное. Разрешено
до десяти изображений. Явная очистка описания или всей галереи отклоняется как неподдерживаемая;
отсутствующая галерея сохраняет исходную. Alt остаётся в представлении, вымышленные
поля XML не создаются.

Изображения получают существующие ограниченные ContentMedia URL; повторный GET
переиспользует записи. Загрузка изображений на Prom и внешние media ID не нужны.
Права владельца разрешения на канал и используемые Files проверяются повторно;
выдача не расширяет доступ за пределы сохранённых разрешённых представлений.

Получение source/storage и сериализация выполняются вне SQL-транзакции. Чтение
представлений использует согласованные снимки; после сетевых операций и перед
ответом проверяются ревизия фида, настройки/проверка подключения, состав групп,
представления, ключи публикаций и текущие права. При изменении контекста допускается
одна повторная сборка. Настройка, выключение или ротация во время загрузки
аннулируют старый результат.

Только полностью сериализованный и повторно проверенный XML передаётся HTTP-слою.
Проверяется сохранение полного набора offer и категорий. Ошибка возвращает JSON
с безопасным кодом и неуспешным статусом; пустой ассортимент, частичный XML или
молчаливый возврат исходника вместо неудавшегося наложения не выдаются. Контроль
состава сравнивает результат с полученным исходником: внешнюю неполную, но
корректную выгрузку нельзя достоверно распознать без отдельного эталона.
