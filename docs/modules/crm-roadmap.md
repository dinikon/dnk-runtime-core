# CRM Roadmap

Документ описывает поэтапный план развития CRM-модуля проекта с учётом целевых функций:

- базовые сущности `Lead`, `Deal`, `Contact`, `Company`;
- справочник связей (телефон, email, Telegram, Viber), привязываемый к любой сущности;
- воронки, стадии и роботы на стадиях;
- кастомные объекты, поля и связи;
- отдельная фича CRM Sales (сегменты, кампании, рассылки на базе `Contact`);
- отдельная фича коротких ссылок.

## Принципы планирования

- **Итеративная поставка**: каждая фаза завершает функциональный вертикальный срез.
- **Tenant-aware by design**: все данные, настройки и автоматизации изолированы по tenant.
- **Schema-first подход**: новые объекты и поля проектируются через runtime schema, чтобы снизить хардкод.
- **Событийная интеграция**: ключевые операции публикуют доменные события для роботов, продаж и рассылок.
- **Наблюдаемость и аудит**: изменения сущностей и автодействий фиксируются для трассировки.

## Этап 0 — Foundation (2–3 недели)

### Цели

Подготовить архитектурный и инфраструктурный фундамент для масштабирования CRM.

### Работы

- Выделить единый `crm kernel` для общих контрактов:
  - идентификаторы CRM-объектов;
  - базовые поля (timestamps, owner, tenant, status);
  - общие политики доступа.
- Спроектировать таблицы и репозитории для:
  - `crm_entity_registry` (тип + метаданные сущности);
  - `crm_relation_directory` (универсальные контакты/каналы);
  - `crm_pipeline`, `crm_stage`, `crm_robot_binding`.
- Ввести шину доменных событий CRM:
  - `entity.created`, `entity.updated`, `entity.stage_changed`, `campaign.launched`.
- Зафиксировать API-конвенции:
  - фильтры, сортировка, пагинация;
  - идемпотентность для массовых операций;
  - совместимость с текущим API для `Contact`.

### Результат этапа

- Архитектура данных и контрактов готова для подключения новых сущностей без переписывания ядра.

## Этап 1 — Core CRM Entities (4–6 недель)

### Цели

Реализовать 4 основные сущности: `Lead`, `Deal`, `Contact`, `Company`.

### Работы

- Добавить доменные модели и CRUD use-cases для `Lead`, `Deal`, `Company`.
- Актуализировать `Contact` как полноценный участник связей:
  - связка contact ↔ company;
  - связка lead/deal ↔ contact/company.
- Реализовать универсальные механизмы:
  - soft-delete + восстановление;
  - optimistic locking;
  - аудит изменений (кто/когда/что изменил).
- Расширить HTTP API:
  - единообразные endpoints для всех 4 сущностей;
  - базовая фильтрация по owner, stage, updated_at.

### Критерии готовности

- Каждая сущность поддерживает CRUD, список, фильтрацию и связи с другими core-сущностями.

## Этап 2 — Справочник связей (2–4 недели)

### Цели

Сделать единый функционал контактных каналов (телефон, почта, Telegram, Viber), привязываемый к любой сущности.

### Работы

- Ввести `RelationPoint`/`CommunicationChannel` модель:
  - `type`: phone | email | telegram | viber;
  - `value` + нормализованное представление;
  - `is_primary`, `is_verified`, `label`.
- Поддержать привязку к любому объекту через полиморфную связь:
  - `entity_type`, `entity_id`.
- Реализовать валидацию и дедупликацию:
  - формат E.164 для телефонов;
  - RFC-подобная валидация email;
  - нормализация username/handle для мессенджеров.
- Добавить поиск по каналам (например, найти контакт/сделку по номеру телефона).

### Критерии готовности

- Любая core-сущность может хранить и использовать набор каналов связи с единым API.

## Этап 3 — Воронки, стадии, роботы (5–8 недель)

### Цели

Реализовать конструктор воронок для сущностей и роботизацию стадий (по аналогии с Bitrix24).

### Работы

- Реализовать `Pipeline` и `Stage`:
  - несколько воронок на tenant;
  - привязка воронки к типу сущности (`Lead`, `Deal`, далее кастомные).
- Реализовать переходы по стадиям:
  - ручные и автоматические;
  - валидация допустимых переходов;
  - SLA/таймеры на стадии.
- Реализовать `Robot`-движок (MVP):
  - триггеры: вход в стадию, выход из стадии, таймер, изменение поля;
  - действия: задача, webhook, изменение поля, отправка уведомления.
- Добавить sandbox-конфигурацию роботов и журнал исполнения.

### Критерии готовности

- Пользователь может собрать воронку, назначить стадии и привязать роботов с наблюдаемым исполнением.

## Этап 4 — Кастомные объекты и поля (6–10 недель)

### Цели

Дать пользователю возможность создавать пользовательские объекты, поля и связи между стандартными/кастомными сущностями.

### Работы

- Расширить runtime schema:
  - конструктор пользовательского объекта;
  - типы полей (строка, число, дата, enum, reference, json);
  - обязательность, дефолты, индексы, правила валидации.
- Реализовать связи между объектами:
  - one-to-one, one-to-many, many-to-many;
  - ограничения каскадности/целостности.
- Сгенерировать слой доступа:
  - динамические репозитории/запросы;
  - универсальные CRUD-endpoints для кастомных объектов.
- Поддержать кастомные поля в:
  - фильтрации, сортировке, экспорте;
  - роботах и сегментации CRM Sales.

### Критерии готовности

- Без деплоя кода можно создать новый объект и использовать его в связях, воронках и автоматизации.

## Этап 5 — CRM Sales (сегменты, кампании, рассылки) (6–9 недель)

### Цели

Построить отдельную фичу продаж и маркетинга на базе `Contact`.

### Работы

- Добавить модуль сегментации:
  - статические и динамические сегменты;
  - правила по полям контактов, активности, стадиям сделок.
- Реализовать кампании:
  - аудитория, расписание, шаблоны, каналы;
  - статусы кампаний и метрики выполнения.
- Реализовать рассылки (MVP):
  - email + мессенджер-коннекторы (через адаптеры);
  - rate limit, retry, обработка ошибок доставки.
- Внедрить compliance-слой:
  - opt-in/opt-out;
  - blacklist;
  - лог согласий и отписок.

### Критерии готовности

- Можно собрать сегмент, запустить кампанию и получить трекинг результатов по контактам.

## Этап 6 — Короткие ссылки (2–3 недели)

### Цели

Сделать отдельную фичу short links для кампаний, роботов и внешних коммуникаций.

### Работы

- Реализовать сервис сокращения ссылок:
  - генерация короткого кода;
  - TTL/архивация;
  - защита от коллизий.
- Добавить трекинг переходов:
  - счётчики, UTM, источник, timestamp;
  - привязка к кампании/контакту (если возможно).
- Интегрировать в CRM Sales и роботов:
  - автогенерация коротких ссылок в шаблонах.

### Критерии готовности

- Короткие ссылки создаются из CRM и дают метрики переходов для аналитики кампаний.

## Сквозные потоки качества (параллельно всем этапам)

- **Безопасность**: RBAC по объектам/полям/действиям роботов.
- **Производительность**: индексация по связям, стадиям, каналам и часто используемым фильтрам.
- **Миграции**: обратимая стратегия миграций и versioned-schema.
- **Тестирование**:
  - unit для domain/use-cases;
  - integration для репозиториев и API;
  - contract tests для внешних коннекторов рассылок;
  - e2e для воронок/роботов/кампаний.
- **Observability**:
  - structured logs;
  - метрики SLA роботов и рассылок;
  - trace-корреляция через request-id / campaign-id.

## Предлагаемые релизные инкременты

- **Release A**: Этапы 0–1 (core сущности).
- **Release B**: Этап 2 + базовые воронки из Этапа 3.
- **Release C**: полный Этап 3 + MVP кастомных полей из Этапа 4.
- **Release D**: полный Этап 4 + MVP CRM Sales.
- **Release E**: зрелый CRM Sales + короткие ссылки.

## KPI успеха Roadmap

- Time-to-configure новой воронки: < 15 минут.
- Доля операций без ручного вмешательства (через роботов): > 40%.
- Скорость построения сегмента до 100k контактов: < 5 секунд.
- Доля доставленных сообщений кампании (delivery rate): > 95% (канал-зависимо).
- Conversion tracking для short links доступен в разрезе кампании/сегмента.
