# Catalog: SIMPLE и категории

Catalog хранит карточку простого товара в tenant-схеме. `Product` — корень агрегата,
владеющий ровно одним `Variant`. Variant ссылается через `sku_id` на Inventory.SKU;
один SKU можно использовать в нескольких товарах. `Category` — отдельный корень
агрегата с деревом категорий. Цена, остатки, атрибуты, вариативные товары и
Channels пока не реализованы.

`Product.kind` типизирован строковым Enum `ProductKind`: `SIMPLE = "simple"`,
`VARIABLE = "variable"`. API возвращает `kind: "simple"`; прежнее поле `type`
удалено. Сейчас создание и восстановление поддерживают только SIMPLE с одним
Variant. Наличие VARIABLE в Enum не включает создание вариативных товаров.
ProductType как отдельная схема контента и ContentBlockDefinition описаны
в [плане Catalog](../plan/catalog.md) и пока не реализованы.

## Переводы

У Catalog нет выбранного или основного языка. Товар можно создать без контента.
Каждый сохранённый перевод содержит код локали BCP 47, обязательное `name` длиной
1–255 символов и необязательное `description`. Состав и применение, если они нужны,
входят в текст описания, а не в отдельные поля. При записи код проверяется по
активному глобальному справочнику `reference_data` через Application-контракт;
старые переводы остаются читаемыми, если код позднее станет неактивным. Два
перевода одного товара с одинаковым кодом не допускаются.

GET всегда требует явный `locale`. Если перевод отсутствует, `content` равен
`null`; другой язык не подставляется. Frontend сможет взять первоначальный выбор
языка из `interface_language` профиля пользователя, но backend не выбирает его сам.

Категория имеет UUID, необязательный `parent_id` и хотя бы один перевод названия
длиной 1–255 символов после trim. Одинаковые названия допустимы. При записи
локаль проверяется по `reference_data`; ранее сохранённые переводы остаются
читаемыми после деактивации локали. Чтение не подставляет другой язык.

Товар явно связан с нулём или несколькими категориями. У непустого набора ровно
одна основная категория; у пустого её нет. Родители не добавляются к товару
автоматически. Перенос категории под себя или потомка запрещён. Удалить категорию
можно только тогда, когда у неё нет детей и привязанных товаров.

## Console API

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/console/catalog/products` | Создание SIMPLE, `201` |
| GET | `/api/console/catalog/products/{product_id}?locale=uk` | Карточка, `200` |
| PUT | `/api/console/catalog/products/{product_id}/contents/{locale}` | Записать или заменить перевод, `200` |
| PUT | `/api/console/catalog/products/{product_id}/categories` | Заменить назначения и основную категорию, `200` |
| POST | `/api/console/catalog/categories` | Создать категорию, `201` |
| GET | `/api/console/catalog/categories?locale=uk` | Плоский список, `200` |
| GET | `/api/console/catalog/categories/{id}?locale=uk` | Карточка со всеми переводами, `200` |
| PUT | `/api/console/catalog/categories/{id}/contents/{locale}` | Добавить или заменить название, `200` |
| PUT | `/api/console/catalog/categories/{id}/parent` | Перенести или сделать корневой, `200` |
| DELETE | `/api/console/catalog/categories/{id}` | Удалить неиспользуемую категорию, `204` |

POST принимает `sku_id` и необязательный массив `contents`; сервер создаёт Product
ID и Variant ID. Ответ содержит оба ID, `sku_id`, актуальный `sku_code`, коды
сохранённых переводов, `kind` и аудит. GET добавляет `requested_locale`
и `content`, который может быть `null`, `categories: [{id, name}]` и `primary_category_id`.
Название категории относится только к запрошенной локали и может быть `null`.
PUT перевода товара принимает `name` и `description` и заменяет перевод целиком.
POST товара не принимает категории: назначения меняются отдельным PUT.

Все методы требуют authentication и tenant-контекста; изменяющие методы используют
существующую CSRF-проверку. Дополнительных проверок уровней доступа в Catalog нет.
Неизвестные поля и невалидные данные дают `422`, отсутствующая ссылка — `404`,
цикл и попытка удалить используемую категорию — `409`.

## Хранение и развёртывание

Tenant-миграция `0012_catalog_simple` создаёт таблицы товара, его единственного
Variant и переводов. `0013_catalog_categories` добавляет дерево, переводы
категорий и явные связи с товарами. Ссылки на SKU и глобальные локали проверяются через
Application-порты; чужие ORM-модели не становятся контрактом Catalog.
Репозитории используют общую сессию UoW с уже выбранной tenant-схемой и не
управляют транзакцией.
Миграция `0014_catalog_product_kind` переименовывает колонку `type` в `kind`
и преобразует `SIMPLE` в `simple`, сохраняя ID, контент, варианты и категории.
Downgrade восстанавливает колонку и значение. Перед запуском нового backend
нужно обновить tenant-схемы; Console и API переключаются на новый контракт вместе.
Структурные изменения дерева сериализуются transaction-scoped advisory lock по
tenant ID. FK запрещают удалять категорию с детьми или товарными связями; связь
с товаром удаляется каскадно только вместе с самим товаром.

Перед открытием API обновить существующие tenant-схемы:

```sh
dnk-manage tenant-migrations upgrade --all
```
