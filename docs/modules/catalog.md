# Catalog

Catalog хранит простые товары и вариативные карточки с дочерними позициями, локализованный контент,
галереи и коммерческие значения. Атрибуты, категории, метки и metadata удалены
из Domain, Application, HTTP, Console и текущей SQL-схемы. Архитектура описана в
[backend](../architecture/backend.md) и [frontend](../architecture/frontend.md).

## Модель и транзакции

CatalogItem и ProductType — отдельные Aggregate Roots. Блоки контента и их
переводы принадлежат ProductType, отдельного write repository для блока нет.
Фабрики create/restore и доменные методы проверяют состояние. Mapper выполняет
только преобразования; чтение коллекций использует batch-проекции без N+1.

Товар изменяется одним атомарным PATCH под блокировкой конкретного item.
Разные поля применяются к актуальному состоянию; для одного поля побеждает
последняя успешная запись. Репозиторий сохраняет изменённые группы связей.
Reference guards удалены вместе с изменяемыми справочниками.
Внешний UoW владеет транзакцией; ревизий в активных контрактах нет.

## ProductType и создание Tenant

CatalogProvisioningFacade.initialize_defaults(tenant_id, actor_id) — публичный
Application-контракт установки Default. Tenancy обращается к нему через свой порт
и Infrastructure-адаптер после создания схемы и администратора, до commit общего
UoW. CLI и Control Plane используют тот же процесс. Ошибка откатывает onboarding.

Фасад создаёт системный тип code=default, schema_version=1 и два блока:

| Код | Тип | Обязательность |
| --- | --- | --- |
| title | text | Непустой текст до 255 символов при сохранении перевода |
| body | rich_text | Необязательный текст до 1000000 символов |

ProductType и каждый блок получают собственный UUIDv7. UUID разных Tenant
независимы; audit содержит UUID созданного администратора. Подписи en/ru/uk
создаются вместе со схемой, без межъязыкового fallback. Повторная инициализация
полной схемы сохраняет UUID; неполная или изменённая системная схема — ошибка.
Чтение и создание товара не инициализируют отсутствующий Default.

Объект product команды CreateCatalogItemCommand содержит product_type_code="default". Application
разрешает код в существующий UUID текущего tenant и передаёт его фабрике товара.
HTTP принимает все поддержанные разделы создания; Console по-прежнему создаёт
пустой Draft и открывает редактор. Выбора и изменения типа в Console нет.
Схема сохранённого товара читается по его product_type_id. GET /product-type/default
находит схему по коду. Фиксированных UUID и таблиц соответствия UUID в коде нет.

## Поля товара

Сохраняются status draft/active/archived, virtual, nullable SKU, цена, наличие,
измерения, переводы и галереи. SKU уникален в tenant после trim с сохранением
регистра. Товар создаётся черновиком без контента, цены и SKU.

Price specification хранит regular/sale, currency и UTC-интервал [from,to).
Текущая price вычисляется на as_of. Decimal точный, до шести дробных разрядов;
0 допустим, отсутствие цены блокирует продажу. Валюта проверяется Reference Data.

Вес — nullable value/unit g/kg; размеры независимо nullable cm/m. Точность
проверяется в g/mm до шести знаков без округления, хранятся исходные пары.
Virtual не очищает измерения и не меняет наличие. Inventory и резервы отсутствуют.

Новый товар: manage_stock=false, stock_quantity=null, stock_status=in_stock,
backorders=no. При учёте количества требуется целое число, включая отрицательное;
наличие вычисляется по количеству и политике backorders. При выключенном учёте
действует ручной stock_status. Boolean строгий. Продажа требует active, цену
и наличие in_stock/on_backorder; публикация проверяет active.

## Контент и медиа

Контент передаётся по кодам title/body. PATCH content.values заменяет полный
набор выбранной locale; пропуск body удаляет его, пустая строка сохраняется.
content=null удаляет перевод. Состав, обязательность, типы и expected_schema_version
проверяются по снимку схемы товара. Rich text очищается NH3 до доменной проверки
и DOMPurify перед показом. Запись разрешена для активной locale Reference Data,
сохранённый перевод неактивной locale читается. Межъязыкового fallback нет.

Галерея принадлежит item+locale: Files links, порядок, alt/caption и одно главное
изображение в непустом наборе. Полный набор заменяется атомарно; gallery=null
удаляет галерею. До 100 изображений. Upload PNG/JPEG/WebP/GIF/AVIF/BMP до 10 MiB
определяет MIME по сигнатуре файла общей инфраструктурной функцией, а не по расширению
или объявлению клиента. В Files передаются те же байты без конвертации, resize и сжатия.
Files handlers работают на общем UoW без Files ORM/FK в Catalog.
Image stream закрывается после ответа; снятие связи не удаляет Files объект.

## HTTP и Console

Префикс /api/console/catalog: POST/GET /items, GET/PATCH/DELETE /items/{id},
GET /product-type/default, upload и image content. Удалённые справочники отсутствуют
в OpenAPI. PATCH принимает status, sku, virtual, price_specification, stock, weight,
dimensions, content, gallery. Неизвестные поля и пустой PATCH дают 422.
Пропуск поля сохраняет значение; null очищает только nullable-поля. Изменение
content/gallery требует query locale. Ошибки разделов содержат field/message.
List поддерживает locale/search/status и offset/limit до 100; поиск идёт по SKU/title.

Console показывает список, создание товара/услуги, обзор и редактор. Поля title
и body сохраняются общей очередью autosave через 800 мс. Подтверждение запроса
не стирает более новый ввод. Ошибочный раздел остаётся в черновике, сеть/5xx
приостанавливают очередь до явного повтора. Upload не повторяется автоматически.
Уход и смена locale сначала сохраняют ввод; смена tenant/session отменяет очередь.

Публичный GetCatalogItemsPublicationSnapshot сохраняет собственные DTO,
locale/as_of, схему и значения товаров с вычислениями. Удалённых полей в нём нет.

## SQL и выпуск

Baseline 0023_catalog_item создаёт структуру без seed Catalog. Данные Default
создаются только через onboarding. Таблицы справочников, назначений, metadata,
variant selections и default selections удалены. Сохраняются SQL kind,
parent_id и ограничения ролей simple/variable/variant. Корни simple и variable используют эти роли; variant принадлежит одному variable.
Аддитивная tenant-миграция `0008_catalog_variants` только разрешает SKU
контейнера, сохраняя общую уникальность и прежнюю схему остатков. Откат
отказывается продолжать при наличии variable с непустым SKU; данные не очищаются.

Ревизия 0026_catalog_attribute_ids удалена; 0027_remove_channels следует за
0025_user_display_currency. Глобальные миграции и другие модули сохраняются.
Исторические имена таблиц остаются в ownership registry для autogenerate.
Переход требует пересозданных tenant-схем и повторного onboarding; переноса данных
нет. Backend и Console выпускаются согласованно.


## Публичный контракт Draft и внешние связи

`CreateCatalogItem` принимает типизированный объект `CreateCatalogItemValues`:
тип, статус, virtual, SKU, price specification с периодом акции, stock, вес,
габариты, контент нескольких локалей и локализованные галереи. Пустой объект
по-прежнему создаёт Draft типа Default. Старые HTTP-входы `{}` и `{virtual: ...}`
сохраняются; POST `/catalog/items` принимает дополнительные разделы без изменения
ответа `{id}`. Переводы передаются как `translations[locale]` с `values` и
`expected_schema_version`, галереи — как `galleries[locale]` по прежнему контракту Files.

`CatalogItemCreationService` проверяет справочники, SKU, схемы, доступность файлов,
очищает rich text и применяет Domain create/update до единственного сохранения.
`ValidateCatalogDraft` использует ту же подготовку без записи. Отдельный сценарий
CreateDraftCatalogItem удалён. `LockCatalogItemForBinding` предоставляет потребителю
собственную item-блокировку и безопасную проекцию. Consumer query/lock не требуют
дополнительных HTTP endpoints. Channels задаёт Draft/Default/virtual=false явно.

Channels вызывает контракт через свой adapter. В Catalog не передаются platform
kind, publication ID или native JSON. Ограничение двух языков интерфейса Channels
не ограничивает количество переводов самого Catalog. Цены и количество не
округляются, SKU проверяется также SQL uniqueness. Сервис не вызывает HTTP или
соседние create/update handlers друг из друга и не выполняет commit.

Delete подключён к CatalogItemUsagePort через публичный GetCatalogUsage Channels
на той же сессии. Проверка под item-lock запрещает удаление при активных ссылках,
включая архивные каналы. Явное снятие ссылки сохраняет товар. Последующая загрузка
публикаций не меняет canonical значения Catalog.

## Импорт CSV и XML

На странице товаров доступны «Импортировать позиции» и журнал импортов.
Мастер принимает файл либо публичную HTTP/HTTPS-ссылку, показывает до 20 записей,
позволяет исправить параметры разбора и сопоставление, затем запускает фоновые
задания. Адрес `/catalog/imports/{id}` восстанавливает состояние после reload;
закрытие окна не останавливает процесс. Остановка сохраняет уже обработанные
товары и применяется на границе позиции. Журнал доступен в `/catalog/imports`.

CSV поддерживает UTF-8/BOM, Windows-1251, запятую, точку с запятой и табуляцию.
Повторяющиеся заголовки различаются по позиции. Отсутствующие последние ячейки
дополняются пустыми значениями, лишние столбцы и повреждённые кавычки отклоняются.
XML разбирается потоково: Prom/YML распознаётся автоматически, для другой структуры
доступен выбор найденного узла записи. Поля сохраняют пути, namespace, атрибуты
и повторяющиеся значения. Пользовательские XPath и выражения не выполняются.
Стандартная декларация `DOCTYPE yml_catalog SYSTEM "shops.dtd"` распознаётся
без загрузки DTD; внутренние подмножества, другие DTD и сущности запрещены.

Автоматическое сопоставление поддерживает системные имена и поля Prom:
`Код_товару`/`vendorCode` → SKU, название/описание → ru, `_укр`/`_ua` → uk,
цены, скидки, количество, наличие, фотографии и измерения. Правила можно изменить;
язык, валюту и единицы можно задать константой. Цена преобразуется через Decimal,
без округления; даты без timezone используют выбранную в мастере IANA-зону.
Дата окончания без времени включает указанный день и переводится в исключительную
UTC-границу следующего дня. Категории, характеристики и внешние ID не создают
новых полей Catalog и остаются несопоставленными.

Режимы: создание (начальный), обновление и создание с обновлением. Существующий
товар определяется только по SKU после trim с сохранением регистра. При создании
найденный SKU пропускается; при обновлении отсутствующий SKU пропускается.
Без SKU можно только создавать. Повтор SKU внутри источника пропускается после
первой записи, включая случай ошибки первой записи. Новые товары используют
Draft/Default, если статус не сопоставлен явно. Изменение SKU существующего товара
импортом не выполняется.

Несопоставленные поля сохраняются. Пустые значения по умолчанию сохраняются;
отдельная настройка включает очищение сопоставленных полей. Обязательное значение
очистить нельзя. Частичные изменения цены, контента и измерений объединяются
с актуальным товаром под item-lock. Количество включает количественный учёт;
при ручном наличии используются канонические значения и алиасы Prom.

Изображения скачиваются с проверкой размера и raster-сигнатуры вне SQL UoW.
Общие URL используются для всех импортируемых языков, а Files-объекты разделяются
между их галереями. Пустой язык фотографий означает общие фото; при импорте только
фото используется выбранная локаль. Порядок сохраняется, первое фото главное,
если явно не сопоставлен номер главного изображения (от 1).
Успешный список заменяет галерею. Ошибка части фото у существующего товара
сохраняет всю прежнюю галерею, остальные поля обновляются. У нового товара
сохраняются доступные фото. Ошибки скачивания становятся предупреждениями.

### API и выполнение

Префикс `/api/console/catalog/imports`:

| Метод | Результат |
| --- | --- |
| POST, JSON URL либо multipart file | 202, ID запуска; обязательный Idempotency-Key |
| GET | Журнал с offset/limit |
| GET /{id} | Состояние, конфигурация и предпросмотр |
| PUT /{id}/configuration | 202, новая версия черновика и подготовка предпросмотра |
| POST /{id}/start | 202; тело с подтверждённой version |
| POST /{id}/resume | 202; тело с generation из состояния остановленного запуска |
| POST /{id}/cancel | 202, запрос остановки без тела запроса |
| GET /{id}/rows | Результаты с outcome/offset/limit; outcome=warnings выделяет предупреждения |
| GET /{id}/report.csv | Поток CSV с номером, SKU, результатом, ID товара, ошибками и предупреждениями |

Доступ соответствует обычным операциям Catalog, изменения требуют CSRF. Запуски,
файлы и строки изолируются tenant-схемой. Ошибки контракта дают 422, неизвестный
запуск — 404, устаревшая версия/второй активный импорт — 409, превышение размера —
413. Повтор создания с прежним ключом и тем же источником возвращает прежний ID;
тот же ключ с другим источником даёт 409. Повтор старта той же версии не создаёт
новую работу. Конфигурация после запуска заморожена.

CatalogImport — отдельный агрегат жизненного цикла. Исходный файл сохраняется
через двухфазный публичный контракт Files; предпросмотр и импорт читают один
неизменяемый снимок. SQL-таблицы `catalog_imports`, `catalog_import_rows` и
`catalog_import_media` содержат технический JSONB конфигурации, payload и
предпросмотра; канонические поля товаров остаются обычными SQL-колонками.
Domain и Application не используют ORM, Files ORM/FK отсутствуют в Catalog.

Работу выполняет штатный `dnk-manage jobs worker`: зарегистрированы
`catalog.import.prepare`, `catalog.import.run` и `catalog.import.maintain`.
Пачка ограничивается 100 записями и 60 секундами между позициями. Для каждой
позиции отдельный внешний UoW атомарно сохраняет товар, результат и счётчики;
продолжение планируется в общей транзакции с точкой восстановления. Проверка
worker lease перед commit отсекает устаревшие выполнения. Файлы подготовленных
изображений переиспользуются при повторе задания; SQL-фаза проверяет готовность
и metadata через публичные Files-контракты без открытия сетевых потоков.

`processed = created + updated + skipped + errors`; предупреждения считаются
отдельно и могут сопровождать успешные строки. Ошибка данных отклоняет одну
позицию. Ошибка БД/хранилища запускает штатный retry. Сверка через пять минут
обнаруживает исчерпанные задания, а обслуживание завершённых импортов выполняется
ежедневно. Число активных импортов на tenant задаётся конфигом (по умолчанию один);
подготовка других источников разрешена независимо от этого лимита. Повторы и результаты доступны через метрики
`catalog_import_jobs_total`, `catalog_import_rows_total`, `catalog_import_job_seconds`.
Содержимое товаров и полные URL в метрики/логи не передаются.

### Ограничения и выпуск

Настройки `CATALOG_IMPORT__*` и Helm `application.catalogImport` задают размер
источника (100 MiB), число записей (100000), изображения (100 на товар, до 10 MiB),
параллельные скачивания (4), размер/время пачки и сроки хранения. URL допускают
только HTTP/HTTPS и стандартные порты, без credentials. DNS проверяется до
соединения с привязкой к проверенному публичному IP; каждый redirect проверяется
отдельно. Полученные байты ограничиваются независимо от Content-Length.

Черновики истекают через 24 часа. Через семь дней после завершения исходные
payload и предпросмотр очищаются, source-файл отправляется в Files trash по его
обычным правилам. Результаты хранятся 30 дней. Фотографии товаров не удаляются
обслуживанием импорта. CSV-отчёт экранирует значения, похожие на формулы.

Миграция `0003_catalog_imports` добавляется после `0002_crm_sales_mvp`, существующая
baseline не изменяется. Выпуск: миграции tenant, затем согласованное обновление
API, worker и Console. Для файлового источника и фото требуется подготовленный
системный bucket Files. Настройки доступны одинаково в API и worker.

### Продолжение остановленного импорта

В мастере основные действия закреплены в нижней панели; мобильная версия использует
полноэкранный диалог, вертикальное сопоставление и список результатов без горизонтальной
прокрутки. Дополнительные параметры и предпросмотр свёрнуты отдельно от действий.

`POST /{id}/resume` принимает `{ "generation": 0 }`, требует CSRF и возвращает ID,
статус и текущее поколение выполнения. `generation` и `can_resume` возвращаются в
журнале и деталях импорта. Продолжение разрешено для `cancelled`, если есть остаток,
полностью подготовленный снимок и не истёк семидневный срок хранения источника.
Конфигурация, версия, строки и счётчики сохраняются; уже завершённые строки, включая
ошибочные и пропущенные, повторно не применяются. Подготовка и скачивание источника
повторно не выполняются, готовые фотографии переиспользуются.

Продолжение увеличивает поколение выполнения и атомарно ставит новое задание с
сохранённого курсора. Оно не конфликтует с ID прежней завершённой пачки. Повтор
запроса прежнего поколения возвращает актуальное состояние без нового запуска,
даже если импорт успели снова остановить. Старые задания отсекаются поколением,
версией, ID задания и lease. Продолжение использует тот же настраиваемый лимит
активных импортов на tenant; конфликт возвращает 409 без изменения счётчиков. После продолжения возобновляется
пятиминутная сверка, срок хранения завершённого результата отсчитывается от следующего
завершения/остановки. Истёкший или неподготовленный источник продолжить нельзя.

Tenant-миграция `0004_catalog_import_resume` добавляет `generation` со значением 0
для существующих импортов. Обновлять миграцию, API, worker и Console нужно согласованно.

### Настройка одновременных импортов

`CATALOG_IMPORT__MAX_ACTIVE_PER_TENANT` задаёт максимально допустимое число активных
импортов одного рабочего пространства. Значение — целое число от 1, начальное — 1.
Для допуска двух импортов одновременно:

```dotenv
CATALOG_IMPORT__MAX_ACTIVE_PER_TENANT=2
```

Эквивалент для Helm:

```yaml
application:
  catalogImport:
    maxActivePerTenant: 2
```

Лимит одинаково применяется к первому запуску и продолжению. Он учитывает `queued`,
`running` и `cancelling`: запрос остановки освобождает место после подтверждения
worker. Подготовка и сопоставление не занимают места. Каждый tenant получает
собственный лимит. Снижение настройки не прерывает уже активные импорты; новые
запуски отклоняются до освобождения места. Повтор принятого запроса остаётся
идемпотентным даже после снижения лимита. Ответ 409 сообщает установленный предел.

Проверка количества и постановка задания выполняются в одной транзакции под общей
tenant-блокировкой, включая несколько экземпляров API. Параллельные импорты одного
SKU сериализуют его поиск и создание; SQL-уникальность SKU и item-lock сохраняются.
Фактическое число исполняемых заданий дополнительно ограничивается общими слотами
`SCHEDULED_JOBS__CONCURRENCY` / Helm `workers.cron.concurrency`. Все экземпляры API
должны получать одинаковое значение лимита; после изменения конфигурации их нужно
перезапустить. Остальные ограничения импорта уже доступны в `CATALOG_IMPORT__*` и
Helm `application.catalogImport`: размер источника, число записей/изображений,
параллельность скачивания, бюджет пачки и сроки хранения.

Миграция `0005_catalog_import_limits` заменяет фиксированный уникальный индекс
обычным частичным индексом активных импортов. Она нужна даже при начальном лимите 1;
применять её следует до согласованного обновления API и worker. Downgrade требует
не более одного активного импорта в tenant и отказывается от отката без изменения
данных, пока лишние импорты не остановлены или не завершены.


## Варианты без структурных атрибутов

`CatalogItem` — корень семьи; `CatalogVariant` — принадлежащая ему Entity без
отдельного repository. SQL сохраняет все роли в `catalog_item`. Simple продаётся
сам; variable — контейнер без цены и virtual; variant имеет собственные SKU,
цену, virtual и статус. SKU уникальны среди всех ролей tenant, включая необязательный
SKU контейнера. Преобразование kind, перенос между родителями, атрибуты и
комбинации не поддерживаются.

Draft/Archived variable может быть пустым. Active требует хотя бы один
неархивный вариант. Архивирование/удаление последней такой позиции отклоняется
атомарно. Неактивный родитель блокирует эффективную продажу/публикацию детей,
не переписывая их статусы. Удаление корня удаляет дочерние данные Catalog;
файлы остаются под управлением Files.

В каждой locale title/body/gallery наследуются независимо при отсутствии
собственного значения. Пустое собственное название запрещено; body="" очищает
описание; собственная пустая галерея означает отсутствие изображений. Удаление
переопределения возвращает наследование. Межъязыкового fallback нет. Вес и
габариты наследуются; габариты заменяются всей группой. Цена не наследуется.
Каждый вариант хранит полную собственную спецификацию stock: по умолчанию
manage_stock=false, stock_status=in_stock, без количества. Если собственный учёт
включён, действуют количество и backorders варианта. Иначе при включённом учёте
родителя действуют его количество и backorders; при выключенном — ручной статус
варианта. Родительские переключения не меняют настройки детей. Ручные статусы
сохраняются и возвращаются после выключения общего учёта. Количество общего
источника не суммируется по детям. У variable без учёта ручное наличие задают дети.
Отдельного сохраняемого stock_source и выбора источника в командах/HTTP нет.
В read DTO stock содержит собственные настройки, effective_stock — вычисленные;
stock_source own/parent и sources.stock вычисляются доменной политикой.
Console всегда позволяет включить собственный учёт варианта; при наследовании
показывает общее количество без редактирования и скрывает ручной статус.

HTTP дополняется вложенными маршрутами `/items/{id}/variants`: GET/POST,
GET/PATCH/DELETE `/{variant_id}`, upload и image content. GET передаёт собственные
поля и `effective_*`, а `sources` содержит владельцев эффективных разделов.
Локализованные PATCH используют прежнюю версию схемы. Создание variable с
начальными variants атомарно через прежний POST `/items`. Корневой список
считает семьи и ищет также по SKU/title детей; отображает количество вариантов
и диапазон текущих цен без конвертации, смешанные валюты помечаются отдельно.

Console создаёт variable через выбор типа, показывает вкладку вариантов с
пагинацией и редактирует позицию в Sheet. Наследование настраивается отдельно;
autosave сохраняет только собственные значения. Root/variant/locale и контекст
пользователя входят в cache keys; выбранный вариант и пагинация — в URL.
В общем списке variable раскрывается в строки вариантов той же DataTable.
Дети читаются только после раскрытия, по 25 на страницу; пагинация семей
и фильтры списка не меняются. Смена фильтра, locale или пользователя сворачивает семьи.
Оба списка передают `manage_stock`, эффективное `stock_quantity` и вычисленный
`stock_source` (`own`/`parent`) без дополнительных запросов на каждую строку.
Общий остаток отмечен явно; отсутствие учёта не заменяется нулём.

В таблицах товаров и вариантов ячейки цены и остатка открывают быстрое
редактирование с кнопкой сохранения. Перед вводом читается полная спецификация;
PATCH содержит только выбранный раздел, сохраняя акцию и политику предзаказа.
У контейнера цена остаётся диапазоном, а изменяется у варианта. Для наследуемого
остатка форма явно редактирует общий источник родителя; собственный учёт
варианта настраивается в полном редакторе. Несохранённый ввод защищён при
навигации, ошибка не закрывает форму, фоновые ответы не заменяют черновик.
Мутация обновляет список, раскрытые варианты и детали текущего контекста.
CSV/XML импорт остаётся simple-only: SKU variable/variant даёт ошибку строки,
без обновления семьи.

Публичный `GetCatalogProductSnapshot` возвращает типизированный корень, дочерние
позиции, собственные и эффективные значения, источники, locale/as_of. Consumer
передаёт свой внешний UoW, handler берёт ту же family lock, что mutations, затем
читает batch-проекцию без восстановления агрегата. Контракт не содержит ORM или
идентификаторов площадок. Каналы и экспорт этим срезом не меняются.

Будущая привязка WooCommerce использует контейнер и дочерние позиции. Для Prom
два варианта Catalog означают две продаваемые позиции Prom: основной выбирается
в Channels, Catalog-контейнер третьего товара не создаёт. В режиме
`VARIABLE_TO_SIMPLE` каждый вариант станет отдельным простым товаром Prom.
Режим и выбранный основной ID принадлежат Channels, а не Catalog.

## Связи с публикациями Channels

Вкладка «Публикации» доступна у простого и вариативного товара в просмотре и
редакторе. Ею владеет публичный UI-контракт Channels: Catalog не управляет чужими
таблицами или query keys. Сопоставление не изменяет контент, цену, остаток или
состояние товара. Draft, Active и Archived доступны для новых связей; архивирование
сохраняет существующие группы.

Catalog предоставляет публичный `CatalogBindingsFacade`: блокировку семьи,
пакетный снимок семей с эффективными полями и поиск корней заданного типа до
пагинации. Наличие связей проверяется через собственный `CatalogPublicationUsagePort`,
адаптер которого обращается к Application-контракту Channels на общем UoW.
Domain блокирует физическое удаление использованного корня и использованного
варианта; несвязанный вариант подчиняется прежним правилам Catalog.

Режимы, ограничения, HTTP и жизненный цикл описаны в
[Channels: привязки к Catalog](channels.md#привязки-к-catalog).

Изменение количественного учёта, количества или backorders накапливает доменный
`CatalogStockChanged` со списком затронутых позиций. Изменение родителя учитывает
наследников, а изменение собственного остатка варианта не отправляет соседние
варианты. Application записывает интеграционное событие, Outbox и внутреннее
задание доставки до commit общего UoW. HTTP и импорт используют одну реализацию.
Ручное получение остатка Channels не изменяет Catalog. Правила отправки и
разрешения описаны в [синхронизации остатков Channels](channels.md#синхронизация-остатков).
