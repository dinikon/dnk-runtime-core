# Inventory: первый Domain-срез

Модуль `inventory` объединяет складские агрегаты. В текущем срезе реализована
только Domain-модель номенклатуры `InventoryItem`; она располагается непосредственно
в `src/modules/inventory/domain/`, поскольку других корней в модуле пока нет.

Нормативные требования: [архитектура backend](../architecture/backend.md).
Целевой состав складской системы описан в [плане](../plan/inventory.md).

## Граница агрегата

| Поле | Тип и смысл |
| --- | --- |
| `id` | Постоянный `InventoryItemIdVO` |
| `sku` | Обязательный ручной `SkuVO` |
| `base_uom` | Базовая единица `UomCodeVO` |
| `tracking_mode` | `NONE`, `LOT`, `SERIAL`, `LOT_AND_SERIAL` |
| `expiration_mode` | `NONE`, `OPTIONAL` или `REQUIRED` |
| `barcodes` | Неизменяемый tuple дочерних `ItemBarcode` |
| `uom_conversions` | Неизменяемый tuple дочерних `ItemUomConversion` |

Партии, серийные экземпляры, остатки, движения и резервы не принадлежат этому
агрегату. Фактические даты годности здесь не хранятся.

## Значения и настройки

`SkuVO`, `UomCodeVO` и `BarcodeVO` принимают строки, убирают пробелы по краям
и запрещают пустые значения, управляющие и форматирующие символы Unicode.
`SkuVO` сохраняет каноническое значение после `trim + casefold`: `ABC` и `abc`
равны, имеют одинаковый hash и сохраняются как `abc`. Длина канонического SKU
составляет от 1 до 25 символов. Ограничение проверяется после нормализации,
поскольку Unicode casefold может увеличить длину строки.
Штрихкод сохраняет ведущие нули и регистр; `UomCodeVO` также сохраняет регистр.
Контракт Catalog SKU не импортируется в Inventory.

`ConversionFactorVO` принимает только конечный положительный `Decimal`.
Например, `base_uom=PCS`, дополнительная единица `BOX`, коэффициент `12`
означают `1 BOX = 12 PCS`. Все конвертации прямые, относительно базовой единицы.

SKU обязателен в `create/restore`, не генерируется и заменяется вручную через
`change_sku`. SKU уникален среди InventoryItem одной tenant-схемы. Один штрихкод
в этой схеме принадлежит только одному InventoryItem, независимо от единицы
упаковки или склада. В другом tenant те же SKU и штрихкод допустимы.

По согласованной границе этого среза SQL-хранение пока не реализуется.
В следующем срезе обязательны атомарные ограничения БД: уникальность
канонического SKU у позиций и уникальность значения штрихкода во всей таблице
штрихкодов tenant-схемы. Ограничения только на пару `(inventory_item_id, barcode)`
недостаточно. Предварительный поиск дубликата не заменяет уникальный индекс;
защита должна работать при конкурентных создании и изменении.
Сейчас Domain обеспечивает каноническое сравнение SKU и отсутствие повторов
штрихкодов внутри одной позиции, а межагрегатная уникальность остаётся требованием
к будущему хранению, а не гарантией отдельного агрегата.

По умолчанию `create` задаёт `tracking_mode=NONE`, `expiration_mode=NONE`
и пустые коллекции. `NONE` и `OPTIONAL` совместимы с любым TrackingMode.
`REQUIRED` совместим с `LOT`, `SERIAL`, `LOT_AND_SERIAL`; сочетание
`tracking_mode=NONE` / `expiration_mode=REQUIRED` отклоняется.
Учёт партии сам по себе не включает контроль срока годности.

| Режим | Дата | Учётное поведение |
| --- | --- | --- |
| `NONE` | Срок годности не учитывается | Контроль дат выключен |
| `OPTIONAL` | Можно указать дату только как заметку | Как у NONE: без обязательности, проверки просрочки и влияния на доступность, резервирование, отгрузку, FEFO или автоматические действия |
| `REQUIRED` | Дата обязательна до проведения поступления | Контроль срока включен |

`OPTIONAL` сохраняется отдельным значением, а не alias режима `NONE`, чтобы
сохранить намерение пользователя записывать необязательные даты-заметки.
Это не Python `None`: поле всегда содержит типизированный `ExpirationMode`.
Свойство `controls_expiration` истинно только у `REQUIRED`.
Будущая `StockExpirationPolicy` должна обходить учётную обработку дат для
обоих режимов `NONE` и `OPTIONAL`, даже если заметка содержит прошедшую дату.
Фактические даты, заметки и проверка пригодности появятся вместе с партиями,
серийными экземплярами и операциями. В этом срезе отдельной исполняемой Policy нет.

## Дочерние Entity и инварианты

`ItemBarcode` содержит собственный `ItemBarcodeIdVO`, `BarcodeVO` и `UomCodeVO`.
`ItemUomConversion` содержит собственный `ItemUomConversionIdVO`, `UomCodeVO`
и `ConversionFactorVO`. Обе Entity имеют фабрики `create/restore`.

Инварианты состава проверяет `InventoryItem`:

- ID внутри каждой коллекции уникальны.
- Значения штрихкодов не повторяются внутри позиции.
- Для каждой дополнительной единицы существует не более одной конвертации.
- Базовая единица не получает конвертацию в саму себя.
- Штрихкод ссылается на базовую или объявленную дополнительную единицу.
- Используемая штрихкодом конвертация не удаляется.
- Изменение единицы конвертации не оставляет штрихкоды с неизвестной единицей.

У дочерних Entity нет самостоятельных write repositories. Внешний код меняет
их состав и значения через методы агрегата.

## Изменения и восстановление

`InventoryItem.create/restore` проверяют полный состав, включая собственные
значения Entity. `restore` принимает все поля явно и сохраняет переданные ID.

Публичные методы `change_sku`, `add_barcode`, `change_barcode`, `remove_barcode`,
`add_uom_conversion`, `change_uom_conversion`, `remove_uom_conversion` возвращают
новый проверенный `InventoryItem`. Результат необходимо использовать вместо
исходного экземпляра. При успехе и при отказе исходный объект остаётся неизменным.
Изменение дочерней Entity сохраняет её ID; операции с отсутствующим дочерним ID
отклоняются доменной ошибкой.

Базовая единица, режим прослеживаемости и режим годности задаются при создании.
Методов их изменения пока нет: будущие сценарии должны учитывать историю.
Сохранённые движения должны фиксировать использованный коэффициент конвертации,
чтобы его последующее изменение не пересчитывало историю.

## Проверки и границы среза

`test/test_inventory_domain.py` проверяет фабрики, матрицу режимов, ручной SKU,
строковые значения, точные коэффициенты, уникальность и ссылки дочерних объектов,
их жизненный цикл и сохранение исходного состояния при отказах.

Application-сценарии, хранение, миграции, API и интеграционные события относятся
к следующим срезам.
