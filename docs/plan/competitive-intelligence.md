## 1. Цель и ценность

Предоставить пользователю сведения о конкурирующих товарных предложениях:
кто продаёт сопоставимый товар, где он опубликован, каковы обычная и акционная
цены, наличие и история изменений.

На уровне Instance формируется общий индекс публичных публикаций. Внутренняя
ЛЛМ в фоне находит соответствия с каталогом каждого тенанта. Пользователь
подтверждает связь для отслеживания либо пропускает предложение. Связи,
рекомендации и решения пользователя принадлежат конкретному тенанту.

Основной пользовательский сценарий:

1. Система обнаруживает публикации на Prom и Rozetka.
2. Извлекает площадку, продавца и сведения о товарном предложении.
3. Сопоставляет публикации с позициями каталога тенанта.
4. Показывает рекомендацию с объяснением сходства и обнаруженными различиями.
5. Пользователь выбирает «Отслеживать» или «Пропустить».
6. Подтверждённая связь появляется в мониторинге цен и наличия.

## 2. Объём MVP

### Входит в первый срез

- Источники Prom и Rozetka с отдельными JSON-конфигурациями.
- Обнаружение публикаций в настроенных областях обхода: категории,
  страницы продавцов, sitemap и их допустимая пагинация.
- Регулярное обновление ранее найденных предложений.
- Общий индекс источников, продавцов, публикаций и их наблюдений в Instance.
- История цен и наличия с явным временем наблюдения.
- Фоновый поиск кандидатов и оценка внутренней ЛЛМ.
- Подтверждение, пропуск, приостановка и прекращение отслеживания связи.
- Ручное добавление публичного URL для постановки в обработку.
- Списки рекомендаций и отслеживаемых предложений, история и базовое сравнение.
- Эксплуатационные сведения о покрытии, свежести, ошибках и очередях.

Область обхода задаётся явно и ограничивается бюджетом запросов. MVP не обещает
полное покрытие всего ассортимента Prom, Rozetka или интернета. Нулевой результат
поиска означает отсутствие кандидатов в текущем индексе, а не отсутствие
конкурентов на рынке.

### Следующие срезы

- Другие маркетплейсы, самостоятельные магазины и согласованные товарные feeds.
- Подписка на весь ассортимент продавца и обнаружение новых товаров магазина.
- Проверенное объединение аккаунтов одного продавца на разных площадках.
- Уведомления по правилам пользователя.
- Автоматическая конвертация валют и расширенная аналитика.
- Автоматическое изменение собственных цен.

Продажи, выручка и доля рынка конкурента не выводятся из цены и наличия.

## 3. Термины и модель предметной области

Базовая цепочка:

~~~text
Источник размещения → Аккаунт продавца → Публикация
Prom               → Продавец А      → Предложение товара
Rozetka            → Продавец Б      → Предложение товара
~~~

| Понятие | Ответственность |
| --- | --- |
| Source | Площадка размещения и жизненный цикл её конфигурации |
| SellerAccount | Публичный аккаунт продавца в определённом источнике |
| MarketPublication | Конкретное предложение продавца для товара или варианта |
| PublicationObservation | Неизменяемый снимок предложения на момент наблюдения |
| CrawlRun | Ограниченный запуск обхода с курсором, состоянием и результатами |
| CatalogPublicationLink | Рекомендация или подтверждённая связь позиции Catalog с публикацией |

Публикация — предложение конкретного продавца, а не обязательно вся страница
товара. Одна страница может объединять несколько продавцов. Для Rozetka это
подтверждается [описанием группировки товаров](https://sellerhelp.rozetka.com.ua/p188-product-grouping.html).
Цена должна извлекаться в контексте того же предложения, что и продавец.
Минимальная цена общей карточки не присваивается всем её продавцам.

Названия продавцов не являются стабильными идентификаторами. Аккаунты на разных
площадках не объединяются автоматически по названию. Возможная будущая сущность
Merchant связывает только проверенные аккаунты одного продавца.

Отдельно различаются источник размещения и способ получения данных.
Например, размещение в Google Shopping и получение через Merchant API — разные
измерения происхождения. Merchant Center API предоставляет товары
авторизованного аккаунта и не рассматривается как публичный каталог всех
конкурентов: [контракт products.list](https://developers.google.com/merchant/api/reference/rest/products_v1/accounts.products/list).
Приватные подключения не включаются в общий публичный индекс без отдельно
определённой модели доступа.

## 4. Владение данными и изоляция

Общий индекс живёт в глобальной схеме public БД текущего Instance. Он общий
для тенантов этого Instance; межинстансовая репликация в MVP не входит.
Предлагаемый префикс таблиц — ci_.

| Область | Предлагаемые данные |
| --- | --- |
| public.ci_sources | Источники, активная ревизия конфигурации и состояние |
| public.ci_source_definitions | Неизменяемые версии конфигураций и их хеши |
| public.ci_seller_accounts | Публичные сведения об аккаунтах продавцов |
| public.ci_publications | Идентичность и последний корректный снимок публикации |
| public.ci_publication_observations | История наблюдений цены, наличия и условий |
| public.ci_publication_embeddings | Поисковые представления публичных публикаций |
| public.ci_crawl_runs | Запуски, курсоры, охват и безопасные результаты обработки |
| Схема тенанта: ci_catalog_publication_links | Рекомендации, решения и отслеживание |
| Схема тенанта: ci_match_evaluations | Оценки сопоставления, объяснения и версии моделей |
| Схема тенанта: ci_catalog_match_documents | Закрытая поисковая проекция позиций Catalog |
| Схема тенанта: ci_ingest_requests | Технические receipts ручного добавления URL |

Таблицы определяют хранение, а не автоматически новые Aggregate Roots.
PublicationObservation, версии конфигурации и оценки — связанные неизменяемые
записи. Технический receipt запроса URL нужен для идемпотентности и чтения
результата своим тенантом; отдельный бизнес-агрегат для него не вводится.

Одна публичная публикация хранится один раз и может использоваться несколькими
тенантами. Решение «Пропустить» или «Отслеживать» одного тенанта не влияет на
решения другого. В глобальный индекс не копируются тексты, embeddings и цены
каталога тенанта, оценки сопоставления или решения пользователей.

Существующий Shared Jobs может хранить tenant ID и технические ID в envelope
задания; это не часть публичного индекса. Его tenant-записи очищаются штатным
механизмом удаления. Глобальный приоритет обхода не раскрывает подписчиков.

Удаление тенанта удаляет его связи, поисковую проекцию, receipts и оценки,
но сохраняет общий индекс. Глобальная публикация, на которую возможны ссылки,
сохраняет стабильный UUID и при исчезновении становится tombstone; физическое
удаление такой публикации не является штатной операцией MVP.

## 5. Данные публикации

Типизированное ядро обеспечивает поиск и аналитику. Версионированные attributes
и platform_data сохраняют расширения источника без изменения общей модели
для каждого нового поля. Исходные данные и происхождение позволяют проверить
нормализацию, но не подменяют типизированный контракт.

| Группа | Поля |
| --- | --- |
| Идентичность | id, source_id, seller_account_id, external_offer_id, external_card_id, variant_key |
| Размещение | canonical_url, seller_url, рынок/страна, локаль наблюдения |
| Контент | Названия по известным локалям, main_image_url |
| Цены | current_price, regular_price, sale_price, currency |
| Условия | price_kind, единица продажи, размер упаковки, условия акции, если известны |
| Наличие | in_stock, out_of_stock, preorder или unknown |
| Идентификаторы | Массив scheme/value: GTIN, EAN, UPC, ISBN, MPN и другие |
| Признаки | Бренд, модель, характеристики варианта, состояние товара |
| Происхождение | URL получения, метод извлечения, версия конфигурации, исходные значения |
| Наблюдение | first_seen_at, last_seen_at, last_success_at, observed_at |
| Качество | Статус извлечения, issues, freshness и статус доступности публикации |
| Версионирование | schema_version, смысловой fingerprint, fingerprint полного снимка |
| Расширения | attributes, platform_data |

Правила нормализации:

1. Деньги хранятся через Decimal и передаются в JSON строками. Ноль сохраняется
   как ноль; неизвестное значение — null. Валюта берётся из наблюдения источника
   и проверяется через Application-контракт Reference Data.
2. current_price — наблюдаемая текущая цена. regular_price и sale_price
   заполняются только при наличии соответствующего смысла в источнике.
   Акция не определяется только сравнением двух случайных чисел.
3. Условная цена по купону, клубной карте или способу оплаты обозначается явно.
   Она не подменяет общедоступную цену в сравнении.
4. price_kind различает exact, from, range, on_request и unknown. Для диапазона
   сохраняются его границы; «от» не превращается в точную цену.
5. Идентификаторы хранятся строками с ведущими нулями. Для GTIN проверяются
   допустимые длина и контрольная цифра; исходное значение сохраняется.
   Некорректное значение не используется как точное доказательство совпадения.
6. GTIN описывает товар и не является PK публикации. Наличие одинакового GTIN
   у разных продавцов не объединяет их предложения.
7. Отсутствующий перевод не выдумывается. Неизвестная локаль не получает
   произвольную метку языка.
8. Неразрешённый продавец или неоднозначная принадлежность цены дают issue
   и исключают сомнительное предложение из ценовой аналитики.

Устойчивый ключ публикации строится из пространства идентификаторов источника,
аккаунта продавца, внешнего предложения и варианта, если он влияет на identity.
Его точный состав подтверждается исследованием каждого источника. Изменение
названия, цены и tracking-параметров URL не создаёт новую публикацию.

Каждое успешно применённое наблюдение получает собственную идентичность,
время получения и использованную конфигурацию. Повторная доставка того же
результата не создаёт вторую запись. История читается отдельно, без загрузки
всех наблюдений внутрь агрегата MarketPublication.

## 6. Рекомендация и отслеживание

В MVP подписка означает отслеживание конкретной публикации для конкретной
позиции Catalog. Подписка на весь магазин — отдельный будущий сценарий.

CatalogPublicationLink содержит id, catalog_item_id, publication_id, status,
relation_type, latest_evaluation_id, needs_review, decided_by, decided_at,
created_at, updated_at и собственную версию для защиты конкурентных решений.

~~~text
suggested → tracking
suggested → skipped
skipped   → tracking     явное решение пользователя
tracking  → paused
paused    → tracking
tracking / paused → skipped     явное прекращение отслеживания
~~~

- relation_type различает same_product и similar_product.
- Для пары catalog_item_id/publication_id существует одна связь.
- Автоматическая обработка создаёт suggested, но никогда tracking.
- Подтверждение требуется и при совпадении по GTIN.
- Пропуск сохраняется; новая оценка ЛЛМ не возвращает предложение автоматически.
- Пользователь может просмотреть пропущенные предложения и изменить решение.
- Для вариативного товара выбирается конкретная продаваемая позиция Catalog.
- Материальное изменение модели, варианта или комплектации публикации ставит
  needs_review. Система не перепривязывает связь к другому предложению.
- Приостановка сохраняет решение, но снимает повышенный приоритет обновления.
- Прекращение отслеживания сохраняет подавление повторной рекомендации.

Удаление позиции Catalog согласуется с его usage-контрактом: tracking и paused
требуют явного прекращения отслеживания перед удалением. Suggested/skipped
не блокируют удаление; связанные оценки и поисковая проекция удаляются вместе
с позицией. Проверка и создание активной связи сериализуются item-lock Catalog.

## 7. JSON-конструктор источников

Каждый источник описывается отдельным версионированным JSON-файлом, проверяемым
общей JSON Schema. Планируемые определения: prom.json и rozetka.json.
Конфигурации управляются на уровне Instance; редактор конструктора в Console
в MVP не требуется.

Конструктор задаёт разрешённые домены, области обнаружения, пагинацию,
бюджет обхода, загрузку, контексты извлечения, identity, нормализацию,
обязательные поля и периодичность.

Ниже иллюстрация DSL. Домен и селекторы условные; это не готовая конфигурация
Prom или Rozetka. Боевые селекторы и доступность полей проверяются на этапе 0.

~~~json
{
  "schema_version": "source.v1",
  "code": "marketplace_example",
  "revision": 1,
  "allowed_hosts": ["marketplace.example"],
  "discovery": {
    "strategies": ["sitemap", "seller_catalog"],
    "seed_urls": ["https://marketplace.example/catalog"],
    "max_pages_per_run": 500
  },
  "fetch": {
    "driver": "http",
    "browser_fallback": false,
    "timeout_seconds": 20,
    "per_host_concurrency": 1
  },
  "extract": {
    "product": {
      "title": {"css": "h1", "read": "text"},
      "main_image_url": {
        "css": ".product-image",
        "read": "attribute",
        "attribute": "src"
      }
    },
    "offers": {
      "each": ".offer",
      "fields": {
        "external_offer_id": {
          "css": ":scope",
          "read": "attribute",
          "attribute": "data-offer-id"
        },
        "seller_external_id": {
          "css": ".seller",
          "read": "attribute",
          "attribute": "data-seller-id"
        },
        "seller_name": {"css": ".seller", "read": "text"},
        "current_price": {
          "css": ".price",
          "read": "text",
          "normalize": "decimal"
        },
        "sale_price": {
          "css": ".sale-price",
          "read": "text",
          "normalize": "decimal",
          "nullable": true
        },
        "currency": {"constant": "UAH"}
      }
    }
  },
  "refresh": {
    "discovery_interval_seconds": 86400,
    "tracked_interval_seconds": 21600,
    "untracked_interval_seconds": 259200
  }
}
~~~

Схема должна также описывать извлечение regular_price, идентификаторов товара,
наличия и остальных нормализованных полей. Пример показывает только часть
сопоставлений, а не полный контракт публикации.

Поддерживается ограниченный набор операций: CSS, XPath, JSONPath, JSON-LD,
чтение атрибутов, разрешённые fallback и зарегистрированные нормализаторы.
Используется единый документированный диалект выражений. Исполнение произвольных
Python/JavaScript, загрузка модулей и shell-команд из JSON запрещены.

Нестандартное получение или преобразование оформляется именованным адаптером
в Infrastructure. Конструктор остаётся общим, а не скрывает всю обработку
каждой площадки за одним непрозрачным адаптером.

Версии DSL, нормализованной публикации и конфигурации источника независимы.
Активация выполняется после проверки схемы и fixtures. Запуск фиксирует
конкретную ревизию; смена активной версии не смешивает правила внутри страницы.

## 8. Скрапер и обновление индекса

Отдельный контейнер competitive-scraper использует код модуля и БД Instance.
Его можно масштабировать независимо от API и фонового сопоставления.

~~~text
Планирование → Обнаружение URL → Загрузка → Извлечение предложений
            → Нормализация → Сохранение наблюдения → Поисковый индекс
~~~

Предлагаемые начальные интервалы:

| Работа | Интервал |
| --- | --- |
| Обнаружение новых публикаций | 24 часа |
| Обновление активно отслеживаемых публикаций | 6 часов |
| Обновление остальных известных публикаций | 72 часа |

Это настройки источника, уточняемые после измерений. Подписки нескольких
тенантов дают одно общее обновление публикации. Повышенный приоритет —
восстанавливаемая производная активных связей; прекращение последней подписки
не должно навсегда оставлять публикацию в ускоренном обходе.

Обязательное поведение:

- Короткий UoW получает контекст задания; сеть и браузер работают вне транзакции.
- Перед записью новый UoW проверяет актуальность контекста, владельца lease,
  её срок и порядок наблюдений. Старый worker не перезаписывает свежий снимок.
- Наблюдение, изменение публикации, checkpoint и необходимые сообщения
  сохраняются атомарно; повторная доставка идемпотентна.
- Ограничения запросов действуют суммарно на домен во всех replicas.
- Обрабатываются Retry-After, backoff, тайм-ауты, лимиты ответа и бюджет обхода.
- Сетевой сбой, CAPTCHA и ошибка извлечения не означают удаление предложения.
- Последний корректный снимок сохраняется с признаком устаревания.
- Исчезновение подтверждается отдельными успешными проверками по правилам
  источника. Неполный обход не удаляет пропущенные публикации.
- Контролируются допустимые домены, публичные IP и переходы. Правила применяются
  также к browser subrequests; внутренние адреса недоступны из браузера.
- robots.txt и актуальные ограничения источника учитываются при настройке
  обхода. Блокировка фиксируется как отдельный исход, без автоматического обхода.

Текущий Channels читает публикации авторизованных магазинов. Он не является
источником произвольного каталога конкурентов. В частности, Prom API описывает
работу с данными собственной компании: [официальный контракт](https://public-api.docs.prom.ua/).
Приватные credentials Channels не используются публичным скрапером.

## 9. Сопоставление внутренней ЛЛМ

Сопоставление выполняется отдельным worker competitive-matcher:

1. Получить снимок позиции Catalog через публичный Application-контракт.
2. Найти кандидатов по валидным идентификаторам, тексту и семантическому поиску.
3. Выбрать ограниченный набор, например 20 кандидатов.
4. Передать внутренней ЛЛМ только необходимые данные позиции и кандидатов.
5. Проверить структурированный ответ и актуальность исходных snapshots.
6. Сохранить оценку и рекомендацию в схеме текущего тенанта.

Результат оценки:

~~~text
classification: same_product | similar_product | incompatible | uncertain
score
matched_evidence[]
conflicts[]
explanation
model_version
prompt_version
catalog_fingerprint
publication_fingerprint
~~~

Размер, цвет, объём, упаковка, комплектация и состояние учитываются явно.
Неизвестный признак не становится доказательством совпадения. Несовместимые
идентификаторы и явно разные варианты не превращаются в same_product только
из-за сходного названия. Score используется для ранжирования и не называется
вероятностью без отдельной калибровки.

Повторная оценка нужна при смысловом изменении позиции или публикации.
Изменение только цены не требует повторного вызова ЛЛМ. Fingerprints содержат
только поля соответствующего назначения; цена не входит в matching fingerprint.
Смена модели не отменяет решение пользователя.

Тексты страниц являются входными данными. Модель не получает инструменты
перехода по ссылкам, исполнения команд или самостоятельного подтверждения связи.
Неизвестный candidate ID и ответ вне схемы отклоняются. Ошибка inference
не создаёт tracking; безопасный повтор ограничен бюджетом.

В текущем Catalog нет структурированных GTIN и характеристик. Базовый поиск
работает по имеющимся названиям и контенту. Добавление идентификаторов и
публичного matching snapshot выделяется отдельной зависимостью Catalog;
модуль не предполагает, что эти поля уже существуют. SKU продавца не считается
глобальным товарным идентификатором.

Готовая внутренняя inference-интеграция при подготовке PRD не обнаружена.
Нужны EmbeddingPort и LlmMatchingPort с локальным адаптером. Конкретные модели,
размер embeddings и аппаратные требования выбираются по контрольной выборке.

## 10. Аналитика и Console

Три основных раздела:

- «Рекомендации»: товар Catalog и публикация рядом, площадка, продавец,
  изображение, цены, объяснение, различия, подтверждение и пропуск.
- «Отслеживаемые»: подтверждённые связи, цены, наличие, свежесть, разница,
  приостановка, продолжение и прекращение отслеживания.
- «История»: изменения цены и наличия выбранной публикации.

В карточке товара Catalog — вкладка «Конкуренты». В MVP не требуется отдельный
пользовательский редактор источников или просмотр технических raw payload.

Для same_product доступны минимальная и медианная цена сопоставимых предложений,
число уникальных продавцов и отклонение собственной цены:

~~~text
отклонение = (наша цена − цена конкурента) / цена конкурента × 100%
~~~

Процент рассчитывается только при цене конкурента больше нуля. Сравнение
использует одинаковую валюту, совместимые вариант и упаковку, точную цену,
допустимое наличие и актуальное наблюдение. Similar_product показывается
отдельно и не участвует в метрике идентичных товаров. Неоднозначные условия
цены дают объяснение недоступности сравнения.

API возвращает as_of, observed_at и причины исключения из сравнения.
История конкурента строится по наблюдениям; пропуски сбора не изображаются
как доказанное постоянство цены. История собственных цен не восстанавливается
из текущего снимка Catalog и не включается в MVP без отдельного источника.

Для загрузки, пустого результата, ошибки, фонового обновления и pending mutation
предусматриваются отдельные доступные состояния. Отсутствие рекомендаций,
пустой индекс и неготовое сопоставление имеют разные сообщения.

## 11. Техническое направление

Модуль реализуется в src/modules/competitive_intelligence по DDD и Clean
Architecture. Самостоятельные Aggregate Roots: Source, SellerAccount,
MarketPublication, CrawlRun, CatalogPublicationLink. Они ссылаются друг на друга
по ID. Domain остаётся чистым Python; HTTP, SQL, parser и inference — адаптеры.

| Назначение | Предлагаемое решение |
| --- | --- |
| API и HTTP-загрузка | Существующие FastAPI и httpx |
| HTML и структурированные данные | lxml, JSON-LD и ограниченный DSL |
| Необходимое browser-rendering | Playwright в scraper-контейнере |
| Данные | Существующие PostgreSQL и SQLAlchemy |
| Поиск | Текстовые индексы и pgvector для embeddings |
| Очереди и периодичность | Существующий Shared Jobs |
| Inference | Внутренний сервис через Application-порты |
| Console | Отдельный модуль Vue с собственными API/model/UI |

Справочные первичные источники: [lxml](https://lxml.de/parsing.html),
[Playwright](https://playwright.dev/python/docs/library),
[pgvector](https://github.com/pgvector/pgvector).

Shared Jobs потребуется дополнить маршрутизацией по роли или типам заданий:
scraper, matcher и общий worker не должны забирать несовместимые задания.
Текущий контракт claim_due_jobs не принимает такой фильтр. Для глобальных
заданий также нужна проверка lease, поддерживающая tenant_id=null.

## 12. Этапы и критерии готовности

| Этап | Результат |
| --- | --- |
| 0. Исследование источников | Проверенные пути обнаружения, identity продавца/предложения, поля, ограничения и размеченные fixtures |
| 1. Общий индекс | Глобальные модели и миграции, JSON Schema, Prom/Rozetka definitions, scraper, история и свежесть |
| 2. Рекомендации | Catalog-контракты, поиск, внутренняя ЛЛМ, tenant-связи и сохранение решений |
| 3. Аналитика | Console, сравнение, история, мониторинг и эксплуатационная проверка |

Критерии приёмки MVP:

- Обе площадки проходят сценарий «обнаружение → сбор → рекомендация →
  подтверждение → обновление».
- Цена относится к определённому предложению продавца. На обязательных fixtures
  нет ошибочной передачи цены от одного продавца другому.
- Повторный обход, доставка и восстановление lease не создают дубликатов.
- Подтверждения и пропуски изолированы по tenant. Пропуск не возвращается
  автоматически, включая смену версии модели.
- Ошибки источника сохраняют последний корректный снимок и видимую свежесть.
- Целевая корректность извлечения присутствующих обязательных полей — не менее
  95% на размеченной доступной выборке каждой площадки. Отсутствующие поля
  и заблокированные страницы учитываются отдельно, а не исчезают из отчёта.
- Целевая точность показываемых рекомендаций — не менее 90% на отдельной
  контрольной выборке с трудными отрицательными примерами и разными вариантами.
  Порог score сам по себе не подтверждает достижение показателя.
- Целевой возраст отслеживаемых данных при штатной доступности источника —
  до 8 часов для 95% публикаций. Отдельно видны общая свежесть всех отслеживаемых
  публикаций, заблокированные источники и превышения бюджета.
- Пользователь видит пределы покрытия; отсутствие кандидатов не представляется
  как отсутствие конкурентов на площадке.

До реализации на этапе 0 фиксируются объём пилота, состав выборки, пороги
показа, правила подтверждения исчезновения, бюджет сети/inference, retention
наблюдений и диагностических материалов. Полная retention-политика и модель
выбираются до выпуска, без неограниченного хранения HTML и истории.

Декомпозиция сценариев, файлов, транзакций, миграций и проверок приведена
в [плане реализации](competitive-intelligence-implementation.md).
