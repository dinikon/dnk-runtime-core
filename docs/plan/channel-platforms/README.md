# Товарные модели платформ Channels

Срез открытой официальной документации на **2026-10-07**. Включены все **21 платформы**
из `PLATFORMS` в [реестре Channels](../../../src/modules/channels/infrastructure/channel/definitions/registry.py).

Основной результат — [platforms.json](platforms.json): способы обмена, внешние
идентификаторы, справочники и способы их получения, **29 схем объектов с JSON-примерами**,
контекст выбора схемы, ограничения и **58 ссылок на первичные источники**
(из них страница API Shop-Express оказалась недоступна).
[platforms.schema.json](platforms.schema.json) проверяет структуру самого исследования.
Это материалы к [плану Catalog](../catalog.md) и [плану Channels](../channels-integrations.md).

Схемы представляют документированное подмножество полей. Для Хорошопа, Shop-Express,
OpenCart и OkayCMS приложены явно помеченные структуры для сопоставления:
полный нативный контракт зависит от магазина, расширения или недоступной документации.
Их нельзя отправлять в API. Примеры остальных платформ также не являются готовыми
публикациями: ID условные, требования выбранной категории ещё должны быть применены.

## Способы передачи и справочники

«Передача» здесь означает обмен карточками, а не доставку заказа покупателю.
Операции чтения, создания, изменения контента и обновления наличия разделены в JSON.
Наличие платформы в таблице не означает готовность её коннектора в приложении.

| Платформа | Подтверждённый путь обмена товарами | Особые справочники и модель |
| --- | --- | --- |
| Etsy | Open API v3; listing, inventory, медиа и файлы отдельными операциями | Seller taxonomy → properties/values/scales; разделы магазина, теги, материалы, профили исполнения |
| Amazon | Listings Items API и JSON_LISTINGS_FEED | Product Type Definitions по marketplace/seller; условные атрибуты, browse nodes, variation themes |
| eBay | REST Inventory API; альтернативное семейство Trading API | Дерево категорий и aspects; InventoryItem, Offer и группа вариантов — разные объекты |
| Prom.ua | API чтения/изменения; XML/YML и API запуска импорта | Группы магазина ≠ категории Prom; характеристики категории ≠ пользовательские характеристики |
| Rozetka | API чтения и цены/наличия; XML/YML для карточек | Категории источника ≠ категории Rozetka; параметры/значения категории, производители, правила группировки |
| Allo | XML/YML, совместимый Hotline-формат, XLSX | Категории и их шаблоны характеристик; бренды/гарантия; полный Product API не подтверждён |
| Kasta | XML, Excel и кабинет поставщика | Категория/тип товара определяет обязательные характеристики; отдельные правила разновидностей |
| Эпицентр | XML/XLSX для контента; API справочников и обновления предложения | Категория → attribute set → attribute → options; коды и переводы независимы |
| Shopify | Admin GraphQL; CSV | Standard Product Taxonomy, custom productType, collections, tags, options, metafields |
| Хорошоп | XML/YML/Excel; API подтверждён на уровне семейства | Категории и шаблоны, характеристики/словари шаблона, бренды, модификации |
| Tilda | CSV и XML/YML, включая URL экспорта | Категории, Editions, Modifications, Characteristics, Tabs, Unit/Portion; API страниц не равен Product API |
| Wix | Stores Catalog V3 API | Categories, brands, ribbons, info sections; options создают варианты, modifiers — настройки покупки |
| Weblium | CSV импорт/экспорт | Категории как пути, повторяемые Option-колонки, digital/physical, availability |
| Shop-Express | CSV/YML импорт | Категории; контракт характеристик/вариантов требует шаблона магазина; API-документация недоступна |
| Webflow | Data API v2 Ecommerce | Product и SKU, sku-properties/sku-values; категории и пользовательские поля коллекций |
| OpenCart | Контракт выбранного расширения или собственного адаптера | Категории, производители, attribute groups, options, единицы, налоги, языки/магазины |
| WooCommerce | REST wc/v3; CSV | 4 вида + virtual/downloadable; categories, tags, brands, global/local attributes, terms, shipping/tax classes |
| Magento CMS | Административный REST; CSV импорт | type_id, EAV attribute sets/groups/options, категории, websites/store views, configurable/bundle relations |
| PrestaShop CMS | Legacy Webservice XML | Categories, features/values, product options/values, combinations, manufacturers/suppliers, languages, stock |
| Okay CMS | CSV; YML через отдельный модуль | Категории, бренды, характеристики из колонок; дополнительные структуры зависят от версии/модулей |
| CS-Cart | REST API | Categories, features, options, variation groups; vendor/storefront, статусы и параметры упаковки |

В каждой записи `delivery[].source_ids` и `taxonomies[].source_ids` ссылаются на
`sources` основного JSON. Там находятся адреса официальных страниц и статус доступа.
`not_verified` означает отсутствие подтверждённого контракта в исследовании,
а не доказанное отсутствие функции у платформы.

## Как устроен JSON

- `platforms[].runtime_capabilities` — текущий срез нашего реестра, отдельно от возможностей площадки.
- `delivery[]` — формат, направление, операции, статус подтверждения и источник.
- `identity[]` — внешние ID товара, предложения, разновидности, источника и артикула.
- `taxonomies[]` — область действия, идентичность, способ получения справочника и источники.
- `product_schemas[]` — JSON Schema 2020-12 выбранного объекта и иллюстративный пример.
- `schema_resolution[]` — что нужно знать для получения применимой схемы.
- `limitations[]` — пробелы документации и ограничения переноса.

Для XML используется наша JSON-проекция: `@id` — атрибут, `#text` — текст узла,
массив — повторяемые элементы. Для CSV значения ячеек остаются строками.
`research_descriptor` означает предложенную структуру исследования, а не нативный
формат. Отсутствие `required` в частичной схеме не означает необязательность полей
на платформе. Разрешённые неизвестные поля сохраняют расширения, но не проходят
проверку правил площадки.

Пример выбора схемы Prom:

```python
import json
from pathlib import Path

research = json.loads(Path("docs/plan/channel-platforms/platforms.json").read_text())
prom = next(p for p in research["platforms"] if p["kind"] == "prom")
product = next(s for s in prom["product_schemas"] if s["key"] == "product")
print(product["json_schema"])
print(prom["taxonomies"])
```

## Что нужно получить при подключении магазина

Полные деревья категорий и все значения характеристик не скачаны. В наборе нет
авторизованных выгрузок магазинов: `values_status: not_fetched` указан явно.
Например, для Prom требуется экспорт характеристик выбранной категории из кабинета,
для Rozetka — `category-options` по `category_id`, для Эпицентра — набор атрибутов
и его options, для Amazon — PTD schema в контексте продавца и marketplace.
Конкретные пути и первичные источники находятся в JSON.

Перед реализацией коннектора необходимо зафиксировать версию API/CMS/модуля,
получить актуальные словари и шаблон магазина, разделить read/create/update/variant/
offer-контракты и проверить операции на тестовом товаре. Для закрытых платформ
понадобится документация кабинета или экспорт его шаблона. Успешная локальная
валидация примера не проверяет права продавца, категорийные правила или модерацию.

## Следствия для плана Catalog

Внешний `productType` не является универсальным типом: у WooCommerce это вид товара,
у Amazon — ключ схемы, у Shopify — пользовательская классификация. Внутренний
`Catalog.ProductType` остаётся типом контента. Связи между ними задаются сопоставлениями.

Идентификатор внешнего SKU сохраняется в проекции даже для виртуальной карточки.
Это не создаёт связь с внутренним Inventory.SKU. Размеры, единицы, порции и упаковка
также сопоставляются отдельно от опций и групп вариантов.

Схема публикации должна фиксировать платформу, канал, версию, категорию/шаблон,
локаль и полученные определения атрибутов. Выбор транспорта делается для операции:
один канал может создавать карточки через XML и обновлять цену через API.
