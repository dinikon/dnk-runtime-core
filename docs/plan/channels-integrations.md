# План модуля интеграций и каналов

Дата обновления: 2026-10-11. Статус: рабочий документ для дополнения.

Документ структурирует требования к интеграциям с внешними платформами.
Это план разработки, а не описание реализованного функционала.
Предложения по технической реализации и открытые вопросы выделены отдельно.

Исходные данные для следующих коннекторов: [исследование всех 21 платформы реестра](channel-platforms/README.md)
с JSON, товарными схемами, способами обмена и внешними справочниками.

Связанный документ: [план Catalog и товарных представлений Channels](catalog.md).
Он уточняет единую модель CatalogItem, представления, overrides и mappings,
а также целевые стратегии публикации Prom и WooCommerce.

Read-коннектор Rozetka расширяет срез Prom/WooCommerce и описан в
[разделе 15](#15-rozetka-следующий-read-коннектор). Контрактная реализация готова;
проверка реального кабинета остаётся отдельным пунктом приёмки.

## Реализованный первый срез: настройки Channels

Реализованы агрегат Channel, tenant-хранение, API каталога конфигураций и раздел
Console «Интеграции → Каналы». Подробности и контракт: [Channels](../modules/channels.md).

- ChannelKind — конечная платформа; ChannelType — cms, marketplace или shop.
- Реестр в коде содержит config.connection (JSON Schema + UI schema)
  и config.capabilities.read_publications для Prom/WooCommerce/Rozetka.
- Создание настроек доступно для Prom (api_key) и WooCommerce
  (url, consumer_key, consumer_secret) и Rozetka (username, password);
  остальные платформы пока недоступны.
- Facebook Leads и TikTok Leads исключены из этого среза; тип форм отложен.
- is_active — пользовательская активность; status — unverified/connected/error.
  Новый канал сохраняется как unverified. Изменение подключения сбрасывает проверку;
  переименование и активность её не меняют.
- Credentials шифруются; UI показывает наличие ключа и позволяет заменить его.
- Структура сценариев закреплена отдельными DTO и HTTP-контрактами; фабрики
  агрегата проверяют создание/восстановление без `__post_init__`.
  Архитектурные ограничения проверяются `test_channels_architecture.py`.
- Реализован Read импорт Prom/WooCommerce/Rozetka: автоматический запуск при создании
  активного канала, ручное обновление, durable страницы и прогресс/ошибки.
- ExternalPublication хранит native JSON и версионированный Read документ.
  PublicationImportRun хранит жизненный цикл обхода. Структура слоёв разделена
  по трём Aggregate Roots: channel/external_publication/publication_import_run.
- Console канала содержит вкладки «Публикации» и «Настройки подключения»;
  публикации открываются как поля карточки, с галереей, описанием и вариациями.
- Проверка подключения отдельным сценарием, YML, периодический импорт,
  сверка удалений, редактирование/выгрузка и Catalog остаются следующими этапами.

Разделы ниже описывают целевой интеграционный MVP, а не уже доступные операции.
Сохранение активного канала ставит импорт в очередь; полный успех фиксируется
только после завершения всех доступных страниц и вариаций. Статус проверки
подключения Channel остаётся независимым от состояния импорта.

## 1. Назначение и термины

Модуль отвечает за подключение внешних источников и синхронизацию состояния
нашей платформы и её данных с маркетплейсами, облачными магазинами, магазинами
на собственной CMS и формами сбора обращений.

**Канал (Channel)** — конкретный подключённый источник с пользовательским названием,
данными подключения и выбранными объектами синхронизации.
Например: «WooCommerce — основной магазин» или «Prom.ua — магазин 1».
**Коннектор** — реализация взаимодействия с определённой платформой.
Несколько каналов одной платформы используют один тип коннектора.
**Публикация** — товарная карточка во внешнем источнике; её идентичность
и внешнее состояние отличаются от внутреннего товара нашей платформы.

## 2. Каталог внешних платформ

Все перечисленные платформы должны присутствовать в каталоге, который возвращает
бэкенд. Доступность реализации указывается отдельно от наличия в каталоге.

| Категория | Платформы | Доступность в первой версии |
| --- | --- | --- |
| Маркетплейсы | Etsy, Amazon, eBay, Prom.ua, Rozetka.com.ua, Allo, Kasta, Эпицентр | Только Prom.ua; остальные — «Недоступно» |
| Облачные интернет-магазины | Shopify, Хорошоп, Tilda, Wix, Weblium, Shop-Express, Webflow | Все — «Недоступно» |
| CMS: собственные интернет-магазины | OpenCart, WordPress, Magento CMS, PrestaShop CMS, Okay CMS, CS-Cart | Только WooCommerce для WordPress; остальные — «Недоступно» |


В мастере подключения WordPress-магазина рабочая интеграция называется
**WooCommerce**. Подключение произвольного WordPress-сайта без WooCommerce
не входит в первую версию.

Facebook Leads и TikTok Leads отложены; категория форм не входит в текущий каталог.

Этот перечень задаёт продуктовый план. Он не утверждает, что API каждой платформы
поддерживает все перечисленные ниже объекты или операции.

## 3. Объекты синхронизации

Целевая модель предусматривает следующие компоненты:

| Компонент | Содержание | Первая версия |
| --- | --- | --- |
| Товары | Товарные данные и публикации в источнике | Доступно для Prom.ua и WooCommerce |
| Заказы | Заказы внешнего источника | Недоступно |
| Клиенты | Данные покупателей | Недоступно |
| Способы доставки | Доступные способы доставки | Недоступно |
| Способы оплаты | Доступные способы оплаты | Недоступно |
| Статусы | Внешние бизнес-статусы и их соответствие внутренним | Недоступно |

Способы доставки и оплаты отображаются отдельными компонентами, чтобы можно было
независимо выбирать и отслеживать их синхронизацию.
Компонент «Статусы» отличается от технического статуса подключения или синхронизации.
Какие именно бизнес-статусы входят в этот компонент, требуется уточнить.

Для каждого канала пользователь выбирает, с какими компонентами он хочет работать.
Компоненты, которые канал не поддерживает или которые ещё не реализованы,
видны в интерфейсе, но их элементы выбора отключены (`disabled`).
Рядом показывается причина недоступности.

Доступность задаёт бэкенд. Он также проверяет выбор при сохранении:
нельзя включить недоступный компонент через прямой запрос к API.
Действие «Выбрать всё», если предусмотрено, выбирает только доступные компоненты.
В первой версии для Prom.ua и WooCommerce это только товары.

## 4. Границы первой версии

В первую версию входят:

1. Каталог всех запланированных платформ с признаком доступности.
2. Рабочие подключения Prom.ua и WooCommerce.
3. Новая вкладка «Каналы» на фронтенде.
4. Мастер добавления канала: название, данные подключения, выбор компонентов.
5. Проверка подключения с отображением результата попытки добавления.
6. Редактирование данных подключения существующего канала.
7. Дашборд для каждого подключения со статусами компонентов.
8. Автоматический запуск синхронизации выбранных компонентов после добавления.
9. Загрузка всех существующих товарных публикаций подключённого источника.

Заказы, клиенты, способы доставки, способы оплаты и бизнес-статусы остаются
в целевой модели и интерфейсе как недоступные компоненты.
Начальный MVP охватывает Prom/WooCommerce. Расширение Read для Rozetka описано
в разделе 15; остальные платформы пока не входят в рабочие интеграции.

Обязательный первый товарный сценарий — загрузка существующих публикаций
из источника в платформу. Состав редактирования товаров, обратной отправки,
синхронизации цен и остатков уточняется отдельно; эти операции нельзя считать
утверждёнными только на основании слов «работа с товарами».
В MVP не реализуются сопоставление внутренних атрибутов Catalog с атрибутами
Prom/WooCommerce и передача атрибутов или их значений во внешние системы.
Если внешний источник возвращает атрибуты при первичной загрузке, они могут
оставаться в наблюдаемом состоянии публикации, но не создают автоматически
атрибуты Catalog. Экспорт VARIABLE по выбранной стратегии с внешними
атрибутами вариаций относится к следующему этапу.

## 5. Вкладка «Каналы»

На вкладке отображаются подключённые каналы и действие «Добавить канал».
При добавлении список платформ, категории, доступность и настройки компонентов
загружаются с бэкенда.
Фронтенд использует эти данные и не определяет доступные платформы самостоятельно.

Для существующего канала доступны переход на дашборд и изменение данных подключения.
Предлагаемый состав карточки в списке: пользовательское название, платформа,
статус подключения и краткий результат последней синхронизации товаров.

## 6. Мастер добавления канала

### Последовательность

1. Пользователь открывает вкладку «Каналы» и выбирает добавление.
2. Бэкенд возвращает каталог платформ. Недоступные платформы видны,
   но продолжить их подключение нельзя.
3. Пользователь выбирает Prom.ua или WooCommerce.
4. Пользователь указывает название источника и данные для подключения.
   Набор полей зависит от платформы и задаётся бэкендом.
5. Пользователь выбирает компоненты синхронизации. Недоступные компоненты отключены.
6. При попытке добавления бэкенд проверяет подключение и необходимые права доступа.
   Интерфейс показывает ход проверки и её результат.
7. При неудачной проверке отображается понятная причина; пользователь может
   исправить данные и повторить попытку.
8. После успешной проверки канал сохраняется вместе с выбранными компонентами.
9. Автоматически запускается первичная синхронизация выбранных компонентов.
10. Открывается дашборд канала с состоянием процесса и результатом загрузки.

### Пример: WooCommerce

Пользователь выбирает WooCommerce, вводит название «Основной магазин» и данные
подключения. В списке компонентов видит товары, заказы, клиентов, способы доставки,
способы оплаты и статусы. В первой версии выбрать можно только товары.

После успешного добавления система загружает все существующие товарные публикации
WooCommerce. Во время загрузки компонент «Товары» показывает «В процессе».
После успешного завершения — «Синхронизировано».
Остальные компоненты показывают «Недоступно» с объяснением ограничения первой версии.

## 7. Изменение данных подключения

Пользователь должен иметь возможность открыть настройки существующего канала
и изменить данные для подключения.

Предлагаемый сценарий: новые данные проверяются до применения; при успешной проверке
сохраняются, при неудачной — отображается причина и остаётся возможность исправления.
История канала и загруженные публикации сохраняются при замене ключа доступа
к тому же источнику.

Замена адреса или аккаунта на другой источник требует отдельного правила:
нельзя автоматически считать его публикации теми же внешними объектами.
Это правило необходимо уточнить перед реализацией редактирования.

## 8. Дашборд подключения

Каждый подключённый канал имеет собственный дашборд. На нём видны название
источника, платформа, статус подключения и краткое состояние каждого компонента:
товаров, заказов, клиентов, способов доставки, способов оплаты и статусов.

Обязательные состояния синхронизации:

| Состояние | Значение |
| --- | --- |
| Недоступно | Компонент не поддерживается каналом или не реализован в текущей версии |
| В процессе | Синхронизация выбранного компонента запущена и ещё не завершена |
| Синхронизировано | Последний запуск успешно завершён для всего объёма выбранного компонента |

Статус подключения отображается отдельно: успешная проверка доступа сама по себе
не означает, что публикации уже загружены. Отказ доступа к работающему каналу
также отличается от отсутствия поддержки компонента.

**Предложение для уточнения:** добавить состояния «Не выбрано», «Ожидает запуска»
и «Ошибка», чтобы корректно показать выключенный компонент, очередь и неудачный запуск.
Частичный результат или ошибка не должны отображаться как «Синхронизировано».

Для товаров предлагается показывать количество загруженных публикаций, прогресс,
время последней успешной синхронизации и причину ошибки при её наличии.
Общее количество показывается, только если источник позволяет достоверно его получить.

## 9. Первичная загрузка публикаций

После добавления канала запускается загрузка всех существующих товарных публикаций
в рамках подключённого магазина или аккаунта, доступных выданным данным подключения.
Точная трактовка «всех» по статусам публикаций вынесена в открытые вопросы.

Предлагаемые правила процесса:

- Загрузка выполняется в фоне с обработкой всех страниц внешнего источника.
- Для публикации сохраняются канал, внешний идентификатор и полученные товарные данные.
- Внешняя публикация и внутренний товар различаются: загрузка не должна автоматически
  перезаписывать существующий товар или создавать складской остаток.
- Сопоставление публикации с каталогом и правила создания новых товаров уточняются отдельно.
- Повтор запроса, страницы или всего запуска не создаёт дубли уже загруженных публикаций.
- Прогресс сохраняется, чтобы сбой можно было восстановить без потери результата.
- Ошибка сохраняется вместе с частичным результатом; канал остаётся доступным в интерфейсе.
- Пустой источник считается успешно обработанным: «Синхронизировано», 0 публикаций.
- Успех фиксируется после обработки всего объёма; успешная проверка доступа или
  получение только первой страницы не завершают синхронизацию.

## 10. Предлагаемая техническая структура

Целевая граница `Channels` владеет подключениями, настройками синхронизации,
внешним состоянием источников и представлениями товаров. `Catalog` хранит
канонические CatalogItem (`simple`, `variable`, `variant`), переводы и контент.
Стратегии, сопоставления
категорий и внешние идентификаторы находятся на стороне Channels; сопоставления
атрибутов добавляются после MVP. Коннекторы реализуют
взаимодействие с API платформ. Детали этой границы описаны в [плане Catalog](catalog.md).

Новый Catalog MVP хранит SKU-код, цену, размеры и вручную заданные настройки
наличия; подключение удалённого Inventory не является условием этого среза.
Представления получают effective snapshot CatalogItem, включая stock source ID;
общий источник родителя не становится несколькими остатками при разбиении семьи.
Склады, движения и резервы в эти проекции не входят. Будущий владелец складского
учёта подключается через отдельный публичный контракт.
Локаль публикации настраивается в Channels независимо от Tenancy. Код берётся из
глобального `reference_data`; наличие подходящего перевода проверяется через
контракт Catalog. Catalog не выполняет межъязыковой fallback; иной явный выбор
locale в Channels должен быть виден в preview.

| Сущность или контракт | Назначение |
| --- | --- |
| Каталог платформ | Тип источника, категория, доступность, причины ограничений и схема подключения |
| Возможности коннектора | Доступные компоненты и операции, ограничения платформы и текущей реализации |
| Channel / Connection | Название источника, платформа, внешний scope, ссылка на секреты, статус подключения |
| SyncProfile | Выбранные компоненты; позднее — направления и правила синхронизации |
| ProductRepresentation / RepresentationItem | Представление в канале: несколько source CatalogItem ID, независимая topology, роли parent/variant/single и внешние связи |
| Overrides и mappings | Переопределения representation/item и сопоставления категорий по connection; сопоставления атрибутов и значений — после MVP |
| ExternalResource | Сохранённое внешнее состояние публикации |
| ExternalBinding | Внешний ресурс → representation item → CatalogItem ID либо synthetic parent; область включает channel/connection revision |
| SyncRun | Запуск, прогресс, результат, ошибки и время синхронизации |
| Connector | Проверка доступа и взаимодействие с API конкретного источника |

Целевые topology: SINGLE_ITEM, PARENT_WITH_VARIANTS, VARIANTS_AS_ITEMS,
ITEMS_AS_VARIANTS. Они покрывают одну SIMPLE-публикацию, семью с внешними
вариантами, VARIABLE → несколько простых публикаций и несколько SIMPLE →
внешний вариативный товар. Во втором направлении parent может быть synthetic
в Channels, без фиктивного VARIABLE в Catalog. Источники общих полей и внешние
selection задаются явно, одинаковые SKU/названия не создают bindings.
Catalog parent_id и внешний parent ID не обязаны совпадать.

Mappings адресуют kind, effective field/block, locale и schema version вместо
раздельных внутренних PRODUCT/VARIANT owners. Item/representation overrides
сохраняются поверх разрешённых Catalog значений и не записываются в Catalog.
Импорт имеет отдельный mapping и preview; экспорт не считается автоматически
обратимым. Подробные контракты и правила — в разделе 12 [плана Catalog](catalog.md).
Это развитие после существующего read-среза, а не заявление о готовности
исходящего обмена или Catalog bindings.

Бэкенд должен предоставлять сценарии получения каталога платформ, списка и дашборда
каналов, проверки подключения, добавления канала и изменения данных подключения.
Добавление успешного канала инициирует первичную синхронизацию.
Конкретные HTTP-маршруты и DTO проектируются после уточнения сценариев.

Коннекторы работают через общие контракты; добавление платформы не должно требовать
изменения основного мастера подключения. Каждая платформа объявляет собственные
поля подключения и доступность компонентов.

Секреты хранятся защищённо и не возвращаются в открытом виде в дашборде или логах.
Каналы, публикации и запуски изолируются по tenant; операции учитывают права пользователя.
Проверка доступа, пагинация, ограничения API и повторы относятся к адаптеру платформы.
В MVP не создаются `AttributeMapping` и `AttributeValueMapping`, их API и редактор;
коннектор не получает внутренние атрибуты Catalog для формирования внешнего payload.
До реализации конкретных операций возможности подтверждаются официальной документацией
и проверкой на тестовом подключении.

## 12. Критерии приёмки первой версии

1. На фронтенде есть вкладка «Каналы»; каталог платформ приходит с бэкенда
   и содержит все источники из раздела 2.
2. Добавление доступно только для Prom.ua и WooCommerce.
3. Мастер запрашивает название и данные подключения, показывает результат проверки.
4. В обоих каналах можно выбрать товары; остальные компоненты видны и отключены.
5. Бэкенд отклоняет попытку включить недоступную платформу или компонент.
6. После успешного добавления автоматически загружаются все товарные публикации
   согласованного scope, включая источники с несколькими страницами.
7. Повторная обработка не создаёт дубли; пустой источник завершает загрузку успешно.
8. Дашборд показывает состояние каждого компонента; товары переходят из
   «В процессе» в «Синхронизировано» только после полной успешной загрузки.
9. Неверные данные доступа и ошибки загрузки видны пользователю; частичный результат
   не выдаётся за успешную синхронизацию.
10. Данные подключения существующего канала можно изменить и проверить повторно.
11. Публикации и история одного канала не смешиваются с другим; данные разных tenant изолированы.
12. В MVP нет внешних сопоставлений атрибутов и отправки значений атрибутов в
    Prom.ua или WooCommerce; импортированные поля не изменяют Catalog без
    отдельного правила преобразования.

## 15. Rozetka: следующий Read-коннектор

Статус: Read-коннектор реализован по документированному контракту. Проверка
реального кабинета ещё не выполнена. `kind=rozetka`, `type=marketplace` доступны
в реестре; конфигурация и импорт включены в коде. Цель этапа — подключить кабинет
продавца, сохранить доступные товарные позиции и показывать их в Console через
вкладки «Публикации» и «Настройки подключения».

Первый срез включает авторизацию, первоначальный и ручной повторный импорт,
пагинацию, получение деталей карточек, native JSON, типизированный Read документ,
прогресс и ошибки. Заказы, изменение цен/остатков, создание и редактирование
публикаций, XML-обмен, расписание и привязка Catalog относятся к последующим
этапам. Наличие методов записи в API не включает их в этот срез.

### 15.1. Подтверждённый внешний контракт

Проверено 2026-10-07 по [официальной документации Seller API](https://api-seller.rozetka.com.ua/apidoc/),
на которую ссылается [справочный центр продавца](https://sellerhelp.rozetka.com.ua/p170-general.html).
Проверка выполнена по документации; запросы к реальному кабинету не выполнялись.

| Операция | Контракт | Использование |
| --- | --- | --- |
| Авторизация | `POST /sites`, `username`, пароль в base64; ответ содержит `access_token` | Получение Bearer-токена внутри адаптера |
| Список | `GET /goods/all`, `page`, `pageSize`; `content.items` и `content._meta` | Обход позиций кабинета |
| Детали | `GET /goods/details`, `item_id` либо `rz_item_id`, при необходимости `sync_source_id` | Полная Read-карточка и характеристики |
| Архив | `GET /goods/archive` | Отдельный поток, если архив не покрывается списком |

Базовый адрес фиксирован: `https://api-seller.rozetka.com.ua`. Для товарных
запросов используются Bearer и `Content-Language`; в первом срезе выбирается
`uk`, локализованные native поля сохраняются. Источник может выполнять свой
fallback названия; мы отображаем возвращённые поля и не создаём переводы Catalog.

Актуальная документация использует `/goods/*`. Реализацию не строить на старом
`/items/search` без отдельного подтверждения. Проверять не только HTTP-статус,
но и `success`, структуру `content` и безопасную классификацию `errors`.

### 15.2. Настройки и авторизация

- В реестре добавить явную JSON Schema подключения: обязательные `username`
  (текст) и `password` (секрет, `writeOnly`, password-widget).
- Пароль хранится существующим Fernet-хранилищем Channels. Base64 используется
  только при отправке запроса Rozetka и не заменяет шифрование хранения.
- Пользователь не задаёт API host и не копирует временный Bearer-токен в форму.
  Токен не сохраняется в Channel, native карточке, checkpoint, job payload,
  query cache или логах.
- Авторизация выполняется за пределами UoW. Один токен используется для всех
  запросов текущей ограниченной порции. Для следующего задания можно получить
  новый токен; межзаданийный cache не обязателен в первом срезе.
- При подтверждённой ошибке истечения токена повторить авторизацию и исходный
  GET один раз. Ошибка пароля/прав завершает запуск безопасным кодом; временные
  отказы используют существующие retries shared jobs.
- Сохранение настроек сохраняет существующую семантику `connection_revision`.
  Worker со старой ревизией или утраченным lease не записывает карточки.

Текущий helper `connection()` считает каждое публичное поле URL. Его нужно
расширить явным описанием типа/widget/format либо задать схему Rozetka отдельно:
`username` должен быть обычной строкой без `https-store-url`. Renderer уже
поддерживает text-widget. Форму и контракты Prom/WooCommerce сохранить совместимыми.

### 15.3. Идентичность, охват и обход

1. Область канала — аккаунт магазина, доступный данным подключения; не задавать
   необязательный фильтр одного `sync_source_id` для всего запуска.
2. Внешнюю идентичность строить по стабильному native `item_id` в пределах
   канала/ревизии подключения: `resource_type=product`, `external_id=str(item_id)`.
   До реализации подтвердить уникальность и стабильность ID на фикстурах и
   тестовом кабинете. `rz_item_id` и `price_offer_id` сохранять отдельно в native
   данных. Отсутствие `rz_item_id` у позиции на модерации не делает её ошибочной.
   Не переключать ключ между `item_id` и `rz_item_id` при изменении статуса.
3. Получать все страницы списка. Использовать `_meta` для продолжения, проверять
   повтор страницы, отсутствие прогресса и некорректные ID. Изменения набора между
   запросами не выдавать за гарантированный snapshot маркетплейса.
4. Подтвердить охват активных, скрытых, неактивных, новых, модерации, удалённых
   из прайса и архивных позиций. У `available` документирован default `0,1`;
   `2` означает удаление из прайса. Поэтому `/goods/all` без проверки фильтров
   недостаточно для заявления «загружены все позиции».
5. Зафиксировать проверенную матрицу фильтров/потоков. Если нужны дополнительные
   обходы, включить их в тот же run и устранить пересечения по `item_id`.
   Недоступный по правам поток не выдавать за полный успех согласованного scope.
6. Для каждой позиции получать детали по `item_id`; поля списка использовать
   для дополнения отсутствующих полей. Сохранять оба native фрагмента без
   произвольного удаления неизвестных полей. При конфликте полей приоритет
   деталей подтвердить фикстурами.
7. Не делать до 100 detail-запросов в одном задании. Checkpoint хранит текущий
   поток/страницу и оставшиеся позиции страницы; token/пароля там нет. Начальная
   порция — одна карточка. Бюджет login/list/detail должен укладываться в lease;
   размер порции повышать только после проверки timeout и лимитов API.
8. Позицию сохранять один раз после успешного получения её деталей, вместе с
   продвинутым checkpoint и следующим job. Не записывать сначала урезанную,
   затем полную карточку при каждом повторном импорте: одинаковый результат
   должен сохранять ID и ревизию.
9. При сбое детали checkpoint не продвигается; ранее сохранённые карточки
   остаются. Итог — partial/failed, как у существующих каналов. Пустой полный
   обход — succeeded с нулём ресурсов. Успех наступает после всех потоков,
   страниц и запланированных деталей.

Проверить обёртку ответа деталей: официальный пример содержит массив
`content.item`, тогда как описание относится к одной позиции. Допустимые формы
разобрать явно, проверить совпадение запрошенного ID; не брать первый элемент
произвольного массива. На случай исчезновения позиции между list/detail отдельно
согласовать результат; молча считать карточку успешно импортированной нельзя.

### 15.4. Read-карточка

Использовать существующие `ExternalPublication` и `PublicationReadDocumentVO`.
Новый Aggregate Root не нужен. Native JSON сохраняется полностью, HTTP Read API
по-прежнему выдаёт поля DTO. Формат для будущей записи проектируется отдельно.

| Данные Rozetka | Поля Read документа / правило |
| --- | --- |
| `name`, `article`, `url` | Название, SKU, внешняя ссылка |
| `description`, `description_ua`, `docket`, `docket_ua` | Очищенные полное и краткое описания по выбранной локали |
| `photo`, `photo_preview` | Изображения и preview; учитывать nullable/array формы и безопасные URL |
| `price`, `price_old`, `price_promo`, `prices` | Decimal-цены; исходную цену сохранять, правило обычной/скидочной цены подтвердить с учётом `price_type` и `new_flow_old_price` |
| `stock_quantity`, `available` | Остаток и наличие; ноль отличается от отсутствия |
| `rz_category`, `price_category` | Категории с внешними ID и подписями |
| `params` | Название, скалярное/списочное значение, единица; Boolean и ноль не теряются |
| `upload_status`, `rz_status`, `rz_sell_status` | Не смешивать модерацию, состояние регистрации и продаж; выбрать публичное представление и сохранить исходные коды |
| `rz_group_id` | Native связь группы; не трактовать как parent/variation без подтверждения topology |

Пустые/неизвестные поля остаются `None` с предупреждением. Семантику нулевого
`price_old`/`price_promo` и валюту подтвердить до реализации; не вычислять скидку
из несовместимых полей и не назначать валюту без подтверждённого контракта.
Не группировать товары по совпадающему SKU или названию. Если нужны дополнительные
Read поля статусов/идентификаторов, сначала определить совместимое расширение
документа, отдельного DTO `get_publication` и HTTP response. Это не требует
выдавать raw JSON вместо карточки.

- `application/publication_import_run/service.py` и
  `application/channel/command/create_channel/handler.py`: заменить проверки
  только Prom/Woo проверкой возможностей из `ChannelRegistryPort`; Domain не
  импортирует реестр Infrastructure. Проверку активности сохранить.

SQL-схему и migrations не менять, если существующих полей достаточно. Новый
state/cursor помещается в текущий checkpoint. Сеть выполняется между короткими
UoW, repositories не делают commit, shared jobs подключаются через публичный
порт и внешний composition root.

### 15.6. Console

- Сделать Rozetka доступной в существующем мастере через конфигурацию backend.
- Переиспользовать вкладки, список, карточку, кнопку обновления, ошибки и
  существующую форму настроек. Показывать label платформы из реестра.
- Убрать проверки `[prom, woocommerce]` из `ChannelPublicationsPage.vue` и
  `ChannelEditorPage.vue`; доступность чтения брать из capabilities backend.
  Обновить подпись платформы в `ChannelPage.vue`.
- Статусы Rozetka показывать осмысленными подписями с сохранением неизвестного
  кода, без подмены статуса канала результатом импорта.
- Console читает сохранённые карточки; открытие вкладки или карточки не вызывает
  внешний API. Секреты не попадают в cache и защищены существующим renderer.

### 15.7. Очерёдность и приёмка

1. Зафиксировать реальные list/detail/auth fixtures тестового кабинета: права,
   формы ответов, identity, статусы/архив, сортировку, пагинацию, цены, валюту,
   nullable поля, rate limits и бюджет lease. Ответы обезличить.
2. Реализовать схему и общий механизм capabilities, затем HTTP POST/auth,
   источник и отдельную нормализацию Rozetka.
3. Подключить фоновые порции и действующие Read-контракты. Включить конфигурацию
   Rozetka после готовности всего пути создания и повторного импорта.
4. Проверить Console и регрессии Prom/WooCommerce. Обновить описание реализованного
   функционала в `docs/modules/channels.md`.

Критерии приёмки:

- Активный канал Rozetka создаётся и запускает импорт; выключенный не запускает.
- Получены все доступные позиции согласованной матрицы статусов, страниц,
  источников и архива; карточки без `rz_item_id` сохраняются по `item_id`.
- Каждая позиция имеет сохранённые native данные и Read поля; фото, HTML,
  характеристики, цены/скидки и нулевые остатки проходят через HTTP до UI.
- Повтор одинакового импорта сохраняет ID и ревизию; пересечения потоков не
  создают дубли. Пустой источник завершается успешно.
- Ошибки HTTP и `success=false`, отказ прав, истечение токена, 429, timeout,
  некорректные ответы и сбой detail дают корректный retry/partial/failed.
- PostgreSQL-тесты подтверждают rollback карточки/checkpoint/следующего job,
  параллельный старт, tenant isolation, смену credentials и потерю lease.
- Контрактные тесты проверяют fixtures нескольких источников, отсутствие
  публичного ID, price_old/price_promo, Boolean/list params и nullable фото.
- Browser QA проверяет создание, обе вкладки, открытие карточки, обновление,
  ошибку/частичный результат и мобильную ширину. Prom/WooCommerce не регрессируют.
- Архитектурные и статические проверки проходят. Пароль и токен не попадают
  в Read API или логи; логин возвращается только в публичных настройках подключения.

Для подтверждения реальной интеграции требуется тестовый кабинет с правом чтения
товаров. Контрактная часть реализована на документации и синтетических fixtures;
поддержка полного scope и готовность реального подключения остаются
неподтверждёнными до проверки. Фактические решения и ограничения описаны
в [Channels](../modules/channels.md#rozetka).
