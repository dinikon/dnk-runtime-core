# Currency: план реализации MVP

Статус: запланирован, реализация не начата.

## Назначение и принятые решения

Модуль `currency` регулярно получает официальные курсы NBU, сохраняет их и
предоставляет HTTP API и Application-контракты для других модулей.
Единственный источник MVP — NBU. Выбор источника и резервный провайдер отсутствуют.

- Базовая валюта задаётся при создании Tenant и неизменна в MVP. Default — `UAH`.
- Валюта отображения принадлежит профилю пользователя. Отсутствие выбора означает
  использование базовой валюты Tenant.
- Денежный снимок фиксирует оригинальную и внутреннюю суммы при создании документа.
- Устаревший курс доступен для отображения с соответствующим статусом; новый
  денежный снимок требует свежего курса.
- Все валюты справочника допустимы как значения; пересчёт доступен только для пар,
  покрываемых NBU.
- MVP включает backend, денежные VO, настройки Tenant и профиль пользователя.
  Подключение к документам, миграция прайс-листов, выбор валюты в UI и пересчёт
  денежных экранов выполняются следующим этапом.

Справочник кодов, названий, numeric-кодов и точности валют остаётся в
`reference_data`. Currency владеет котировками и правилами пересчёта.

## Доменная модель и архитектурные требования

### Aggregate Roots

`ExchangeRateBook` — единственный Aggregate Root Currency. В MVP существует одна
глобальная книга NBU: текущий согласованный набор котировок, идентификатор снимка,
дата действия и время успешной проверки. Котировки являются внутренними
неизменяемыми значениями; отдельных репозиториев для них нет.

Фабрики `create/restore` проверяют состав снимка. Доменный метод обновления
запрещает замену новыми результатами запроса, содержащими более старые данные.
Публикация всего набора котировок атомарна.

`Tenant` продолжает владеть своей базовой валютой. Она задаётся через фабрику
создания и восстанавливается вместе с агрегатом; операции её изменения в MVP нет.

`User` владеет nullable-предпочтением `display_currency`; обновление выполняется
через доменный метод. Домен не загружает настройки Tenant для вычисления default:
эффективную валюту отображения определяет Application через порт Tenancy.

### Shared Value Objects

| VO | Содержимое и поведение |
| --- | --- |
| `CurrencyVO` | Нормализованный трёхбуквенный код. Поддержка конкретного кода проверяется через Application-контракт `reference_data`. |
| `MoneyVO` | `amount: Decimal`, `currency: CurrencyVO`. Конечное знаковое значение в диапазоне `NUMERIC(19,4)`, округление `ROUND_HALF_UP`. Сложение и вычитание требуют одинаковой валюты. |
| `ExchangeRateVO` | Исходная и целевая валюты, положительный конечный коэффициент: количество целевой валюты за единицу исходной. |
| `ConvertedMoneyVO` | `original: MoneyVO`, `internal: MoneyVO`, применённый курс и метаданные: источник, ID снимка, дата действия и время проверки. |

`ConvertedMoneyVO` проверяет соответствие валют и равенство внутренней суммы
округлённому результату пересчёта. VO не обращаются к источникам или БД.
Запрет отрицательных сумм, когда он нужен, относится к агрегату потребителя.

Существующий ограниченный enum `CurrencyCodeVO` заменить общей реализацией
валютного VO. Сохранить совместимость имени через alias на `CurrencyVO`,
метода `from_value` и свойства `value`; устранить жёсткий список пяти валют.
Новые импорты направлять в файл определения VO.

Локальный MoneyVO прайс-листов пока сохраняется: его массовая замена выходит
за выбранный объём MVP.

### Архитектурный перечень

Нормативный источник — [архитектурные правила](../architecture/AGENTS.md).

- Четыре слоя: `domain`, `application`, `infrastructure`, `presentation`.
  Поскольку Aggregate Root один, дополнительные каталоги с его именем не нужны.
- Domain Repository хранит агрегат; Application Query Repository возвращает
  проекции, не восстанавливая агрегат ради чтения API.
- Внутренние слои не импортируют SQLAlchemy, HTTP-клиенты, FastAPI или Pydantic.
- Межмодульное взаимодействие проходит через Application-порты и адаптеры;
  чужие агрегаты и SQL-модели не импортируются.
- UoW открывается в Depends или внешней сборке worker/CLI. Репозитории используют
  общую сессию и не выполняют commit/rollback. Application не получает session.
- Каждый сценарий имеет отдельные Command/Query, Handler и DTO результата.
  Для результата `None` отдельного DTO нет; handlers не вызывают друг друга.
- Aggregate и Entity используют фабрики `create/restore` и доменные методы.
  `__post_init__` разрешён только VO; mapper не содержит бизнес-инвариантов.
- Все методы полностью аннотированы, включая `__init__ -> None` и `execute`;
  классы и методы имеют русские docstrings.
- HTTP-контроллеры, Request и Response разделены по сценариям. GET без тела
  не требует Request; `204` не требует Response schema.
- Новые пакеты имеют пустые `__init__.py`, импорты идут из файлов определений.
- Domain не логирует. Логи и метрики успешного сохранения записываются после commit.

## Источник, актуализация и пересчёт

### NBU

Получать официальный курс на текущую дату `Europe/Kyiv`, передавая дату явно.
Хранить дату действия отдельно от времени загрузки; будущий курс не использовать
раньше его даты. Формат и параметры сверять с
[официальной инструкцией NBU](https://bank.gov.ua/admin_uploads/article/Instr_API_KURS_VAL_Full_eng.pdf).

Адаптер переводит котировки NBU в единый контракт: количество UAH за единицу
исходной валюты. Numeric-коды, допустимость валют и исключение металлов проверять
через контракт `reference_data`, без чтения его SQL-моделей.

### Фоновые задания

- Опрос глобальный, раз в пять минут, независимо от количества Tenant.
- Переиспользовать shared scheduled jobs. Регистрацию Currency выполнять отдельным
  циклом с проверкой каждые 30 секунд; ID задания определяется пятиминутным окном.
- При запуске worker ставить текущее задание сразу. Параллельные обновления
  сериализовать распределённой блокировкой; повторная обработка идемпотентна.
- HTTP timeout — 10 секунд. Повторы выполняются механизмом jobs;
  для `429` учитывать `Retry-After`.
- Числа ответа разбирать сразу в `Decimal`, без промежуточного `float`.
- Неверные коэффициенты, дубликаты, пустой набор после фильтрации и некорректный
  снимок отклонять целиком. Металлы и записи вне валютного справочника исключать
  с диагностикой.
- Сбой сохраняет предыдущий набор и не обновляет время успешной проверки.
  Успешный ответ с прежними котировками обновляет время проверки.
- Сетевой запрос выполнить до SQL-чтения и блокировок книги курсов, чтобы
  не удерживать транзакцию БД во время обращения к NBU.

### Свежесть и расчёт

Курс свежий, если успешная проверка NBU выполнена не более 15 минут назад,
а дата действия равна текущей дате `Europe/Kyiv`. На выходных применяется тот же
критерий: адаптер запрашивает официальный курс на текущую календарную дату.

- Использовать прямую пару, затем обратную, затем путь через UAH.
  Все компоненты брать из одного снимка.
- Для NBU кросс-курс A → B равен `rate(A → UAH) / rate(B → UAH)`.
- Коэффициент хранить как `NUMERIC(38,18)`; вычисления выполнять с достаточной
  Decimal-точностью. Сначала зафиксировать коэффициент до 18 знаков с HALF_UP,
  затем по нему округлить сумму до четырёх знаков.
- Для одинаковых валют курс равен `1`, суммы совпадают; источник и снимок
  не требуются, метаданные происхождения nullable.
- Непокрытая пара, отсутствие снимка и устаревший курс — разные ошибки.
- HTTP-чтение возвращает сохранённый курс со статусом свежести и не обращается
  к NBU на каждый пользовательский запрос.
- `ConvertMoney` требует свежий курс и создаёт самодостаточный денежный снимок.
  Обновление книги курсов не изменяет ранее созданные снимки.

Полная история котировок и пересчёт на произвольную прошлую дату в MVP не входят.
Денежный снимок содержит данные для воспроизведения расчёта без текущей книги.

## Use cases, контракты и сборка

| Сценарий | Вход | Возвращаемый тип | Transport / сборка |
| --- | --- | --- | --- |
| `RefreshExchangeRates` | Пустая команда для обновления NBU | `RefreshExchangeRatesResultDTO`: источник, снимок, число котировок, дата действия, время проверки | Worker и management CLI |
| `GetExchangeRate` | Исходная и целевая валюты | `GetExchangeRateResultDTO`: коэффициент, происхождение, дата и свежесть | GET rate / межмодульный адаптер |
| `ListExchangeRates` | Базовая и целевые валюты | `ListExchangeRatesResultDTO`: курсы и отсутствующие пары | GET rates |
| `ConvertMoney` | `MoneyVO`, внутренняя валюта | `ConvertMoneyResultDTO`: свежий `ConvertedMoneyVO` | Application-контракт для потребителей, без HTTP endpoint |
| `GetTenantCurrencySettings` в Tenancy | Доверенный Tenant ID | `GetTenantCurrencySettingsResultDTO`: базовая валюта | GET settings / межмодульный адаптер |
| `ValidateCurrency` в Reference Data | Код валюты | `ValidateCurrencyResultDTO`: нормализованный код, numeric-код, minor units | Адаптеры проверки валют |

Для каждого нового сценария создать
`command|query/<scenario>/command.py|query.py`, `handler.py` и `dto.py`.
`ConvertMoney` является Query: он вычисляет результат, не сохраняет документ
и не изменяет состояние Currency.

Добавить:

- Domain Repository для `ExchangeRateBook`.
- Application-порты источника, чтения курсов, проверки валют и clock.
- NBU HTTP-адаптер; SQL-репозитории; отдельные persistence/query mappers.
- Application-контракт чтения базовой валюты в Tenancy и адаптеры потребителей.
- Общие операции чтения и расчёта в небольших Application services.
- Depends для HTTP и внешнюю сборку worker/CLI с собственным UoW.

Расширить существующие `CreateTenant`, `UpdateCurrentUserProfile` и
`GetCurrentUser` их собственными полями и DTO. Изменяемые сценарии привести к
нормативной структуре и требованиям аннотаций без общего рефакторинга модулей.

Базовую валюту передавать через onboarding/CLI; default — UAH. Неподдержанный
код отклонять до создания Tenant и внешних ресурсов. Эффективную валюту профиля
получать через Application-порт Tenancy, без импорта чужого агрегата.

При отсутствии поля валюты в старом запросе обновления профиля сохранять текущий
выбор; явный `null` сбрасывает его к наследованию. Оба варианта отличать в Request
и передавать явно в Command. Каждый профильный сценарий использует свой DTO.

### HTTP-контракты

Под общим `/api/console`:

- `GET /currency/rate?from=UAH&to=USD`.
- `GET /currency/rates?base=USD&targets=UAH,EUR`.
- `GET /tenants/current/currency-settings`.
- Существующие endpoints профиля получают `display_currency`; чтение также
  возвращает `effective_display_currency`.

Tenant ID определяется доверенным контекстом Identity. Чтение доступно
аутентифицированному пользователю; изменение собственного профиля использует
существующие authentication и CSRF dependencies.

Коэффициенты и суммы сериализуются строками. Ответы курсов содержат `is_stale`
и метаданные снимка. Непокрытая пара возвращает `404`, неверный код — `422`,
отсутствие пригодного сохранённого снимка — `503`. Сохранённый устаревший курс
возвращается с `200` и `is_stale=true`. Bulk-ответ отдельно перечисляет
непокрытые пары. Неизвестный код отклоняется для всего запроса.

Обновление NBU доступно через worker и management CLI, без публичного endpoint.
Настройка источника на Tenant и endpoint её изменения в MVP не создаются.

## Хранение и миграции

Все валютные и денежные значения хранить отдельными колонками, без JSON:

- В `public`: таблица книги курсов с источником, ID снимка, датой действия и временем
  проверки; дочерняя таблица котировок с валютами пары и коэффициентом.
  Источник книги фиксирован как `nbu`; ID снимка обновляется при изменении
  котировок или даты действия, а повторная проверка меняет только её время.
- В глобальной таблице Tenant: `base_currency VARCHAR(3)`, backfill `UAH`,
  затем `NOT NULL`.
- В tenant-таблице пользователей: nullable `display_currency VARCHAR(3)`.
- Контракт хранения `ConvertedMoneyVO`: `original_amount`, `original_currency`,
  `internal_amount`, `internal_currency`, `exchange_rate`, `rate_source`,
  `rate_snapshot_id`, `rate_effective_date`, `rate_checked_at`.

Суммы — `NUMERIC(19,4)`, курс — `NUMERIC(38,18)`. Метаданные источника nullable
только для пересчёта валюты в саму себя. Валюты и суммы всегда обязательны.

Денежный снимок принадлежит агрегату документа; Currency не создаёт отдельную
таблицу денежных сумм. Его поля сохраняются атомарно с документом и не требуют
FK на текущую книгу курсов. Таблицы документов в этом MVP не добавляются.

Добавить global- и tenant-миграции, регистрацию моделей и первоначальную загрузку
NBU. SQL-миграции не выполняют сетевых обращений. Перед активацией сценариев
проверки валют обеспечить заполненный справочник `reference_data`.
Tenant-миграция применяется и к существующим схемам, и при новом onboarding.

## Проверки и критерии готовности

- VO: нормализация, совместимость `CurrencyCodeVO`, знаковые суммы, переполнение,
  NaN/Infinity, округление, несовместимые валюты, согласованность двух сумм.
- Расчёты: прямая, обратная и кросс-пара; единичный курс; использование одного
  снимка; отсутствие пары; устойчивость ранее созданного денежного снимка.
- NBU: mocked HTTP, numeric-коды, исключение металлов, дата действия, выходные,
  полночь Kyiv, timeout, `429`, неверный или пустой ответ.
- Свежесть: граница 15 минут, сохранение времени проверки при сбое, успешное
  подтверждение прежних котировок, блокировка конвертации устаревшего курса.
- Jobs: запуск, повтор задания, несколько worker, конкурирующие ответы,
  rollback и сохранение предыдущих данных при сбое.
- API/настройки: authentication, изоляция Tenant, неизменная базовая валюта,
  наследование валюты профиля, явный reset и совместимость старых запросов.
- PostgreSQL: обе группы миграций, отдельные колонки, точный Decimal round-trip
  и атомарная публикация котировок.
- Архитектура: направления импортов, отсутствие инфраструктурных типов внутри,
  фабрики агрегатов, аннотации, docstrings, обязательные файлы сценариев,
  разделение HTTP-контрактов и границы транзакций.
- Выполнить соответствующие unittest-наборы, PostgreSQL integration tests,
  `compileall` и `black --check`; проверить весь diff по архитектурному перечню.

Добавить метрики успешных/неуспешных обновлений, времени последней успешной
проверки и доступности свежего снимка NBU. Логи содержат безопасные метаданные,
но не полные ответы источника. Успех регистрируется только после commit.

MVP готов, когда NBU обновляется фоновыми заданиями, API выдаёт курсы со статусом
свежести, Tenant и профиль сохраняют валютные настройки, а Application-контракт
создаёт воспроизводимый денежный снимок. Подключение снимка к документам и
пересчёт интерфейса остаются отдельным этапом.
