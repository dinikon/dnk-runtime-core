# Core: текущая identity и развитие управляющего сервиса

**Реализовано:** глобальная `User(AbstractUser)` с UUID, allauth account/social/MFA,
email и Telegram OTP, passkeys, управление сессиями, сессионный Django API и
Nuxt-приложение с публичной SSR-главной. Инструкции запуска находятся в
[README](README.md). **Далее описана целевая архитектура:** Tenant/Membership,
OIDC, DNS и lifecycle/provisioning пока не реализованы. Runtime остаётся независимым.

## Реализованная структура CORE

Конфигурация загружается единожды перед инициализацией Django: `dnk_core/config.py`
читает `core/.env` через Pydantic Settings, а `configuration/` группирует типы,
валидацию и проекцию в Django. Переменные процесса имеют приоритет над dotenv.
`CORE_ENV_FILE=` отключает файл для тестов. Прикладной код читает
`django.conf.settings`, поэтому `override_settings` продолжает работать.

| Модуль | Ответственность |
| --- | --- |
| `accounts/views/` | HTTP, формы, ответы и координация стадий allauth |
| `accounts/forms/` | Валидация ввода и ограниченные расширения форм allauth |
| `accounts/services/` | Политика способов входа, контакты, reauth и доступность функций |
| `accounts/models.py` | Существующая UUID-модель `User(AbstractUser)` |
| `accounts/adapters/` | Точки расширения account/social/MFA allauth |
| `accounts/integrations/` | SMTP, Telegram Gateway и Telegram OIDC |
| `accounts/presentation/` | Безопасная сериализация полей для Vue |
| `accounts/templatetags/` | Тонкие привязки данных и ресурсов к шаблонам |
| `dnk_core/api.py` | Сессия, профиль и публичный контракт capabilities |

Views координируют сценарии через сервисы и Django ORM; адаптеры связывают этот
код со стадиями allauth. Внешние запросы сосредоточены в integrations. Публичные
импорты сохранены реэкспортами, включая `accounts.mail.SMTPEmailBackend`.

Границы транзакций не меняются при сохранении пользователя и телефона, проверке
владельца OTP-контакта под блокировкой и завершении passkey signup вместе с
созданием резервных кодов. Сессии завершает allauth. Миграции, app label, UUID,
хеши паролей и шифрование существующих MFA-секретов сохраняются.

ФИО хранится отдельно от уникальной identity: `first_name`, `last_name` и
необязательное `middle_name`. При `CORE_AUTH_USERNAME_MODE=generated` адаптер
создаёт внутренний username из UUID нового пользователя. Общие поля регистрации
находятся в `forms/profile.py`, редактирование собственного профиля проходит
через `views/profile.py` и `services/profile.py` с сохранением только полей ФИО.
Миграция `0002_user_middle_name` добавляет отчество без изменения старых данных.

`services/capabilities.py` определяет доступность для форм, шаблонов, API и
проверки последнего метода входа. Первичный вход отделён от повторного
подтверждения: в режиме `passwordless` существующий пароль продолжает защищать
чувствительные действия. Enrollment-переключатели ограничивают создание новых
факторов, сохраняя обязательную проверку уже подключённых. Запрет способа входа
проверяется также на прямых запросах и незавершённых стадиях.

Nuxt получает только безопасные флаги `/api/capabilities/`; credentials остаются
в Django. API не меняет контракт сессионной авторизации. Все переключатели
глобальны для CORE и применяются перезапуском, без горячей перезагрузки.
Подробнее о режимах и Compose: [конфигурация](README.md#конфигурация-и-режимы-авторизации).

## Назначение и границы

В целевой архитектуре Core — единый управляющий сервис платформы. Он владеет глобальными учетными
записями, реестром тенантов, доступом пользователей, доменами, конфигурацией
OIDC и операциями жизненного цикла. Runtime исполняет бизнес-операции тенанта
и хранит его прикладные данные.

| Ответственность | Владелец после перехода |
| --- | --- |
| Глобальная identity, социальные аккаунты, глобальная сессия | Core |
| Tenant, Membership, домены, желаемое состояние ресурсов | Core |
| Tenant OIDC issuer, клиенты, выдача и отзыв токенов | Core |
| Оркестрация DNS/TLS и системных писем | Core через адаптеры провайдеров |
| Схемы прикладных данных, Alembic migrations, tenant API | Runtime |
| Фактическое обслуживание DNS, сертификатов и SMTP | Внешняя инфраструктура |

Core и runtime используют существующую общую PostgreSQL-базу. Core владеет
схемой `core` и своими Django migrations; его соединения используют
`search_path=core` без `public`. Core не импортирует модули runtime и не меняет
его таблицы или tenant-схемы напрямую. Общие ORM-модели не вводятся.
В локальном Compose подключение использует ту же роль, что и runtime;
это разделение пространства имен, а не ограничение прав общей роли.
Для раздельных прав в последующем развертывании можно назначить Core отдельную
роль с доступом к схеме `core` в этой же базе.

Реализован app `accounts`; будущие Django apps разделяются по предметным областям: `tenancy`,
`oidc`, `domains`, `notifications`, `operations`. Это отдельное архитектурное
решение для Django-приложения: Django ORM хранит состояние, явные сервисы
реализуют сценарии, views/admin остаются тонкими, внешние вызовы идут через
адаптеры. Структуру FastAPI DI и его SQLAlchemy UnitOfWork сюда не переносим.
Бизнес-переходы не прячем в `save()` или неявные цепочки сигналов.

## Глобальный пользователь и доступ

| Сущность | Назначение и связи |
| --- | --- |
| `User` | Глобальная учетная запись с неизменяемым UUID, профилем и состоянием |
| `SocialAccount` / `EmailAddress` allauth | Внешняя identity и статус подтверждения email, связанные с User |
| `Tenant` | UUID, имя, состояние и ссылка на текущую операцию жизненного цикла |
| `Membership` | Связь User–Tenant, роль `owner`, `admin` или `member`, состояние доступа |
| `TenantDomain` | Нормализованный уникальный host, назначение, проверка владения, DNS/TLS status |
| `TenantIssuer` | Один стабильный issuer на Tenant, состояние и ссылки на ключи |
| OIDC application | Клиент, закрепленный за issuer, тип клиента и точные redirect URI |
| `LifecycleOperation` | Тип операции, идемпотентность, шаги, попытки и результат |
| `AuditEvent` | Кто, когда и для какого тенанта выполнил действие; correlation ID |

Связь User–Tenant уникальна. Владелец тенанта выражается через Membership;
перед удалением последнего активного owner требуется передача владения.
Роли относятся к конкретному тенанту, а Django `is_staff` и `is_superuser` —
к администрированию платформы. Они не заменяют tenant Membership.

Глобальный пользователь может иметь несколько социальных аккаунтов и состоять
в нескольких тенантах. Один успешный вход не дает доступ ко всем тенантам.
UUID пользователя стабилен; email может измениться и не используется как
первичный идентификатор или единственное основание для объединения аккаунтов.

`accounts.User(AbstractUser)` и `AUTH_USER_MODEL` введены в начальной миграции
до allauth. UUID задан явно, стандартный тип автоидентификатора остальных моделей —
BigAutoField. Прежний временный каркас с `auth.User` переводится через отдельный
`prepare_database.py --reset-scaffold`, только в development и только при отсутствии
новых таблиц. Автоматического удаления при запуске нет. Общая база и runtime сохраняются.
[Рекомендации Django](https://docs.djangoproject.com/en/6.0/topics/auth/customizing/#using-a-custom-user-model-when-starting-a-project).

## Вход через Google и другие провайдеры

Allauth отвечает за вход в глобальную учетную запись. Nuxt и Django работают на
одном origin: `/` и `/app/` обслуживает Nuxt, `/api/` и `/accounts/` — Django.
Браузер использует host-only HttpOnly session cookie и CSRF, без JWT.
Google/GitHub подключаются при наличии credentials; доступны также пароль,
email OTP, телефонный OTP через Telegram, TOTP и passkeys.

Toolkit установлен как зависимость для будущей выдачи OIDC credentials клиентам
тенантов, но не подключён. Следующий tenant flow относится к дальнейшему этапу;
встроенный OIDC provider allauth одновременно с Toolkit не включается.

1. Пользователь открывает tenant-приложение, которое начинает OIDC flow своего issuer.
2. Если глобальной сессии Core нет, Core переводит пользователя на вход Google.
3. Allauth обрабатывает callback на едином auth-host, проверяет ответ провайдера
   и связывает внешнюю identity с глобальным User.
4. Core создает сессию на auth-host и возвращает пользователя к сохраненной
   авторизационной операции. Проверяются активность User, Tenant и Membership.
5. После успешной проверки tenant-приложение получает authorization code.

Приложения allauth/account/socialaccount/MFA/usersessions, backend и middleware
подключены. Google и GitHub используют client ID/secret из окружения и точные
callback `/accounts/google/login/callback/` и `/accounts/github/login/callback/`
на публичном origin Core. Запрашиваются только scopes для входа; provider tokens
не сохраняются. Для production требуются HTTPS и настроенные credentials.
[Подключение allauth](https://docs.allauth.org/en/latest/installation/quickstart.html),
[Google provider](https://docs.allauth.org/en/latest/socialaccount/providers/google.html).

Автоматическое объединение пользователей по совпадающему email отключено.
`SOCIALACCOUNT_EMAIL_AUTHENTICATION` и
`SOCIALACCOUNT_EMAIL_AUTHENTICATION_AUTO_CONNECT` сохраняют значение `False`.
Подключение второго провайдера требует уже подтвержденной глобальной сессии
и явного действия пользователя. Внешний subject проверяет allauth; один
provider/subject не может принадлежать двум глобальным пользователям.
[Настройки социальных аккаунтов](https://docs.allauth.org/en/latest/socialaccount/configuration.html).

Глобальная session cookie остается host-only на auth-host, без общего cookie
domain для tenant-доменов. Все issuer размещаются на этом host под разными
путями, поэтому глобальная сессия позволяет повторный вход в другой tenant.
Состояние авторизационной операции хранится на сервере; `next` не превращается
в произвольный внешний redirect. Социальный login запускается через POST с CSRF,
а проверку OAuth state выполняет библиотека. Tenant-приложение независимо
проверяет собственные state и OIDC nonce.

## OIDC: отдельный issuer каждого тенанта

Один Django-сервис обслуживает все tenant issuer. Новый tenant не требует
нового процесса или контейнера. Его неизменяемый UUID входит в issuer:

```text
https://auth.example.com/oidc/tenants/<tenant_uuid>
```

`example.com` — пример, не выбранный домен платформы. Issuer не зависит от
названия, slug или пользовательского домена tenant. Issuer хранится и сравнивается
в точной канонической форме без завершающего `/`.

| Будущий endpoint относительно issuer | Назначение |
| --- | --- |
| `/.well-known/openid-configuration` | Discovery с точным issuer и tenant endpoint URLs |
| `/.well-known/jwks.json` | Только публичные ключи этого issuer |
| `/authorize/` | Authorization Code flow с PKCE S256 |
| `/token/` | Обмен кода и обновление токенов |
| `/userinfo/` | Минимальный профиль в рамках scopes |
| `/revoke_token/` | Отзыв credentials данного issuer |
| `/introspect/` | Проверка access token доверенным resource server |

Это проектируемые маршруты, а не уже подключенный стандартный URLconf Toolkit.
Для issuer с путем discovery должен возвращать именно tenant endpoints.

### Расширения Toolkit и изоляция

Toolkit предоставляет OIDC primitives, discovery/JWKS и точки расширения
validator/backend/models. Сама установка пакета не дает tenant isolation.
Для этой архитектуры потребуется собственный слой, покрывающий все endpoints:

- Resolver находит TenantIssuer по UUID в маршруте и сверяет его с реестром.
  Публичный host для issuer берется из доверенной конфигурации, не из произвольного
  `Host` или forwarded-заголовка запроса.
- OAuth application обязательно принадлежит одному issuer. Публичная регистрация
  клиентов выключена; создание клиента проходит через разрешения Core.
- Grants, access tokens, refresh tokens и ID tokens имеют однозначную связь
  с issuer через проверяемую application и, где нужно, явную tenant-связь.
  Изоляция проверяется также при refresh, userinfo, introspection и revocation.
- Контекст issuer явно передается из Django request в OAuthLib request и validator.
  Middleware само по себе не гарантирует, что этот контекст дойдет до OAuthLib.
- Discovery и JWKS формируются для выбранного issuer. Validator и signing path
  выбирают tenant issuer и ключи для текущей операции. Кэш разделяется по issuer
  и версии ключей.
- Нельзя менять глобальные `OAUTH2_PROVIDER`, issuer settings или общий приватный
  ключ во время обработки запроса: параллельные запросы разных тенантов не должны
  разделять изменяемый контекст.

Перед включением endpoints выполнить отдельный технический прототип на
зафиксированной версии Toolkit: подтвердить возможность tenant-scoped discovery,
подписи, проверки grants/tokens и параллельных запросов без изменения глобальных
settings. Расширения моделей и настройка swappable models определяются до их
первых постоянных миграций.
[OIDC в Toolkit](https://django-oauth-toolkit.readthedocs.io/en/latest/oidc.html),
[настройки](https://django-oauth-toolkit.readthedocs.io/en/latest/settings.html),
[расширение моделей и validator](https://django-oauth-toolkit.readthedocs.io/en/latest/advanced_topics.html).

### Токены и доступ

Используется Authorization Code + PKCE S256, одноразовый code, точное совпадение
redirect URI и проверка nonce клиентом. Implicit и password grants не включаются.
Confidential clients дополнительно аутентифицируются при обмене кода; секрет
не размещается в браузере. Разрешения ограничиваются зарегистрированными scopes.

В ID token: `iss` — tenant issuer, `sub` — UUID глобального User, `aud` — client ID;
`tenant_id` — дополнительный claim, проверяемый против issuer. Клиент проверяет
подпись, issuer, audience, срок действия и nonce. Связь локального пользователя
с глобальной identity хранится по `(iss, sub)`, не по email. Профиль выдаётся только
для разрешенных scopes; доступ и роли вычисляются из текущего Membership.

ID token подтверждает вход клиента и не используется как bearer token для
runtime API. Toolkit по умолчанию выдает opaque access tokens; наличие JWKS
не означает, что их можно валидировать как JWT. Для первого варианта интеграции
runtime проверяет access token через аутентифицированный tenant introspection
endpoint Core и сверяет tenant и назначение токена с контекстом запроса.
Учетные данные resource server и разрешения на introspection также ограничены
соответствующим issuer. Неактивный token не раскрывает чужие данные.

Перед выдачей/обновлением credentials и при userinfo/introspection проверяются
состояния User, Tenant и Membership. При блокировке членства, приостановке
тенанта или компрометации клиента отзываются соответствующие grants/tokens,
прекращается refresh. Глобальный logout завершает сессию Core; logout из одного
tenant-приложения по умолчанию завершает его локальную сессию. Завершение всех
tenant-сессий — отдельная явная операция с отзывом и уведомлением runtime.

Отзыв credentials сам по себе не завершает уже созданную автономную сессию
runtime и не отменяет ранее выданный ID token. Runtime должен проверять состояние
доступа при защищенных запросах и обрабатывать события блокировки; до определения
и тестирования допустимого окна отзыва положительные introspection-ответы
не кэшируются. При недоступности проверки новый доступ не разрешается.

Каждый issuer имеет собственный асимметричный ключ с `kid`. В базе хранятся
метаданные и ссылка на секрет, приватный ключ — в защищенном хранилище.
При ротации новые ID tokens подписываются новым ключом, предыдущий публичный ключ
сохраняется в JWKS до истечения выданных токенов и периода обновления клиентских
кэшей. Приватные ключи и токены не попадают в журналы или audit payload.

## Жизненный цикл Tenant

| Состояние | Смысл / следующий переход |
| --- | --- |
| `draft` | Tenant и owner Membership зарегистрированы; запуск подготовки |
| `provisioning` | Создаются ресурсы runtime, домен/TLS, issuer и клиент |
| `active` | Обязательные ресурсы готовы, вход и runtime-доступ разрешены |
| `suspended` | Новый вход и использование tenant-ресурсов запрещены; возможно восстановление |
| `deleting` | Доступ отозван, выполняется освобождение внешних ресурсов |
| `deleted` | Завершенное удаление; UUID и audit tombstone не переиспользуются |
| `failed` | Первичная подготовка не завершена; доступны повтор или отмена |

Операция имеет собственное состояние и историю шагов. Ошибка DNS при создании
ведет в `failed`, ошибка уведомления не переводит готовый tenant в `failed`.
Ошибка удаления оставляет его в `deleting` с закрытым доступом; неудавшаяся
попытка восстановления оставляет tenant в `suspended`.

### Создание и согласованность

1. В одной транзакции Core создать Tenant, owner Membership, резервирование
   домена, LifecycleOperation и outbox-запись на подготовку.
2. Worker получает операцию и идемпотентно запрашивает runtime provisioning
   со стабильным tenant UUID и operation ID.
3. Подготовить issuer/client/ключи и DNS/TLS. Порядок зависимых шагов фиксируется
   в операции; готовность внешней инфраструктуры подтверждается отдельными проверками.
4. После готовности обязательных ресурсов атомарно активировать Tenant,
   зарегистрировать audit/event и поставить уведомление в очередь.

Нельзя держать SQL-транзакцию открытой во время сетевых обращений. Core и runtime
используют независимые соединения и транзакции даже при общей PostgreSQL-базе;
вызовы другого сервиса, DNS и SMTP не входят в транзакцию Core. Outbox
публикуется с повторной доставкой, consumers ведут inbox/deduplication по event ID.
Управляющие события несут tenant ID, operation ID и версию состояния, чтобы
запоздавшее событие не восстановило уже приостановленный tenant.

Idempotency key ограничен инициатором, типом операции и tenant. Повтор с тем же
входом возвращает прежнюю операцию; повтор ключа с другим входом отклоняется.
Конкурирующие переходы одного tenant сериализуются блокировкой/версией записи.
На каждом шаге сохраняются внешний resource ID и результат. После timeout worker
сначала выясняет фактическое состояние, а затем повторяет действие. Временные
ошибки повторяются с ограничением попыток и увеличением интервала; постоянные
сохраняются для исправления и ручного возобновления.

Компенсация снимает резервирование и удаляет только ресурсы, созданные именно
этой операцией. Ошибка SMTP не должна откатывать tenant, а ошибка DNS не должна
приводить к удалению существующих бизнес-данных runtime. Неудавшаяся компенсация
видна в операции и требует reconciliation.

### Приостановка, восстановление и удаление

Приостановка сначала закрывает доступ в Core, отзывает credentials и передает
версионированное состояние runtime. Runtime обязан применять блокировку
к существующим сессиям и защищенным операциям. Данные и резервирование доменов
при этом сохраняются. Восстановление проверяет готовность ресурсов и активирует
tenant; отозванные credentials не оживают, требуется новый вход.

Удаление проходит через отдельную авторизованную операцию: блокировка доступа,
отзыв credentials, удаление runtime-ресурсов по согласованной политике хранения,
снятие DNS/TLS и освобождение остальных ресурсов. Переход в `deleted` возможен
после подтверждения обязательных шагов. До реализации разрушительных действий
продуктовая политика хранения/восстановления должна быть зафиксирована отдельно;
каркас не задает срок хранения и не запускает удаление данных.

## DNS, TLS и системная почта

Модуль domains резервирует уникальные нормализованные hostnames и выдает
поддомены из управляемой зоны. DNS provider adapter умеет создать, проверить
и удалить нужные записи; записи и внешние IDs связываются с tenant и операцией.
Настоящим DNS-сервером Django не является.

Пользовательский домен требует доказательства владения через уникальный TXT
challenge, проверки маршрутизации и готового сертификата. До подтверждения
владения его нельзя активировать или использовать как redirect URI. При удалении
привязки выполняется проверка освобождения DNS/TLS, чтобы не оставить чужому
ресурсу действующее имя. Переименование приложения или смена домена не меняют issuer.

Notifications отправляет приглашения, сообщения об активации, приостановке
и результатах операций через SMTP/provider adapter. Очередь использует outbox,
у письма есть deduplication ID, статус доставки и безопасная обработка повторов.
Статус отправки не равен подтвержденной доставке; при поддержке провайдера
отдельно учитываются bounce и delivery events. Приглашение содержит одноразовый
ограниченный по времени token, а не полномочия доступа в открытом виде.

Домены отправителя проверяются отдельно от web-доменов, включая необходимые
SPF/DKIM/DMARC записи. Секреты SMTP и подписи хранятся вне репозитория.
Почтовые ящики, IMAP и прием писем в объем этого модуля не входят.
Провайдеры DNS, TLS и почты выбираются на этапе соответствующей интеграции.

## Переход от текущего FastAPI runtime

Сейчас [tenancy](../docs/modules/tenancy.md) создает tenant/domain и физическую
схему с Alembic в одной runtime-транзакции, а
[identity](../docs/modules/identity.md) хранит пользователей тенантов и выполняет
вход по email OTP. Это поведение не меняется добавлением глобальных аккаунтов Core.

1. Глобальная identity уже отдельная. Ввести Core registry без переключения
   существующего входа. Импортируемым тенантам сохранить их UUID; для новых
   UUID будет назначать Core. Инвентаризацию и перенос проводить отдельной миграцией.
2. Определить новую версию внутреннего provisioning-контракта runtime:
   принять tenant UUID, operation ID/idempotency key и требуемый домен;
   вернуть состояние и ссылки на ресурсы. Текущий `POST /api/admin/create-tenant`
   генерирует UUID в runtime и создает локального администратора, поэтому его
   нельзя считать готовой реализацией этого контракта.
3. Оставить создание tenant schema и Alembic в runtime. Core получает результат
   через внутренний API/events; общей транзакции между сервисами не будет.
4. Подключить runtime как OIDC client/resource server. Ввести соответствие
   глобальной identity и локальных пользователей по подтвержденному связыванию
   аккаунтов или приглашениям. Совпадения email недостаточно для автоматического
   слияния текущих пользователей разных тенантов.
5. Переключать вход по одному tenant после проверки owner Membership, issuer,
   клиента и mapping пользователей. До переключения работает прежний OTP flow;
   режим входа задается явно для каждого tenant. Откат режима не должен обходить
   состояние блокировки или восстанавливать отозванные сессии.
6. После перехода Core становится единственным источником lifecycle/access
   команд. Runtime хранит необходимые локальные проекции; старые управляющие
   пути выводятся из эксплуатации отдельно, после миграции потребителей.

Внутренние API и события аутентифицируют сервис, проверяют полномочия и tenant
назначения. Пользовательские runtime API по-прежнему получают tenant из
проверенного request context, а не доверяют `tenant_id` из payload.

## Порядок реализации

1. Custom User, initial migrations и глобальная сессия реализованы; далее Tenant/Membership и правила доступа.
2. Allauth + Google/GitHub, MFA/passkeys и контролируемое связывание реализованы; далее tenant-доступ.
3. Прототип tenant-aware Toolkit; затем модели issuer/application, ключи,
   tenant endpoints, validator и negative tests до подключения клиентов.
4. Lifecycle operations/outbox, версионированный runtime provisioning и аудит.
5. DNS/TLS adapters и системные письма с независимым учетом ошибок.
6. Поэтапная миграция runtime identity/tenancy и проверка блокировок/отзыва.

Для операций нужны наблюдаемость и reconciliation: длительность provisioning,
зависшие шаги, число повторов и ошибок, задержка outbox, отказ доступа/refresh,
готовность DNS/TLS и результат отправки уведомлений. Correlation IDs соединяют
Core, runtime и провайдеров. Логи не содержат credentials или содержимое токенов.

## Приемочные сценарии будущей реализации

- Один Google-пользователь входит в два своих тенанта через общую глобальную
  сессию; новый глобальный User при втором входе не создается.
- Неактивный User, Tenant или Membership блокирует authorize, refresh и доступ
  через userinfo/introspection. В чужой tenant нельзя войти через подмену UUID.
- Клиент, code, access/refresh token и ключ tenant A не работают на endpoint B;
  discovery/JWKS и параллельные запросы не смешивают issuer и ключи.
- Неверные state/nonce, redirect URI, PKCE verifier, повтор code и отсутствующие
  полномочия отвергаются. ID token не принимается runtime API как access token.
- Подключение другого провайдера не объединяет аккаунты только по email;
  приглашение проверяет назначение, срок действия и одноразовость.
- Приостановка и отзыв Membership закрывают текущий runtime-доступ; refresh
  и восстановление tenant не оживляют старые credentials. Недоступность Core
  не приводит к разрешению непроверенного доступа.
- Ротация ключей сохраняет проверку еще действующих ID tokens и изоляцию JWKS.
- Повтор create/provisioning после timeout не создает второй tenant, домен,
  runtime schema или OIDC client; конфликтующие операции сериализуются.
- Частичный сбой DNS/runtime приводит к наблюдаемой ошибке и корректному повтору
  или компенсации; сбой письма не отменяет успешно подготовленный tenant.
- Повторные и запоздавшие события не возвращают устаревшее состояние доступа.
- Переключение существующего tenant сохраняет UUID и подтвержденные связи
  пользователей; сценарий отката проверяется вместе с блокировкой доступа.

Текущие smoke-проверки каркаса описаны в [README](README.md#проверки-каркаса).


## Реализованный CORE UI и новые способы входа

Nuxt продолжает SSR публичной главной и SEO, Django остаётся владельцем
account-форм. Общие Shadcn Vue компоненты находятся в `@dnk/ui`; отдельная
Vite-сборка подключает их к HTML Django. Браузерные формы используют обычный
POST/CSRF и серверную сессию, контракты `/api/session/` и `/api/me/` не меняются.

Telegram Login использует allauth OpenID Connect с небольшим адаптером,
обязательно проверяющим RS256 по Telegram JWKS даже при серверном обмене кода.
`sub` служит идентификатором связи, scopes ограничены `openid profile`, PKCE S256
и session state остаются в allauth. Gateway не участвует в этом сценарии.

Passkey signup использует штатные login stages: email verification затем
WebAuthn с UV/resident key. После успешного stage exit создаются резервные коды
allauth и показываются однократно. Пользователь до окончания WebAuthn остаётся
неавторизованным. Пользовательские таблицы и схема БД не изменяются.

Подробнее: [реализация и запуск](README.md#telegram-login-и-регистрация-с-passkey),
[UI Kit](../frontends/packages/ui/README.md).
